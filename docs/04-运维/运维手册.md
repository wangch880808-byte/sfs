# 师砺平台运维手册

> 面向：负责学校服务器的同学（会用 Linux 命令行，但不熟悉本项目），以及协助他们的 AI 智能体。
> 适用版本：V1.0.1.10（数据库迁移版本 Flyway 21）。
> 最后核对：2026-10-14。命令、路径、参数已逐条对照 `deploy/` 下的脚本核实；脚本没有的功能标为“手动方法”或“待开发”。

出了问题先看 [故障排查](故障排查.md)。每个版本改了什么、升级时要注意什么，看 [版本说明](../05-发布/版本说明/)。

## 0. 阅读约定（先读这一节）

### 0.1 占位符

文中用尖括号表示要替换成实际值的内容，**不要原样照抄**：

| 占位符 | 含义 |
| --- | --- |
| `<学校站点地址>` | 师生访问平台的地址，例如 `https://` 开头的学校域名 |
| `<服务器内网地址>` | 学校服务器在内网的 IP 或主机名 |
| `<监控地址>` | SkyWalking 监控入口地址 |
| `<版本号>` | 例如 `V1.0.1.11`，以升级包里的 `release.env` 为准 |
| `<运维账号>` | 你在服务器上可以 `sudo` 的账号 |
| `<备份机地址>` | 存放异地备份的机器 |

### 0.2 基本规则

- 所有 `nusctl`、`install.sh`、`upgrade.sh` 都必须用 `sudo` 执行，否则报 `must run as root`。
- **正式环境的任何改动操作，先告诉指导老师、先记录、先备份**（见第 12 章“红线”）。
- 屏幕输出里出现 `[nus] ERROR:` 就是失败，要停下来看原因，不要继续往下执行。
- 长时间的操作（安装、升级、恢复）放在 `tmux` 里执行，SSH 断开也不会中断：

  ```bash
  tmux new -s nus        # 新开一个会话
  tmux attach -t nus     # 断线后重新连上
  ```

- 让 AI 智能体帮忙时：把本手册给它看；它提出的删除、恢复、回滚、改数据库命令，**你自己确认后再执行**。

### 0.3 两个辅助函数

`nusctl` 已经覆盖了日常操作。少数手动操作（查数据库、进容器）需要直接调用 Docker Compose。**不要直接执行不带参数的 `docker compose up -d`**：它不读 `/srv/nus/config/.env`，也不带域名配置，会把平台起坏。

需要时，先在当前终端里粘贴下面两个函数（关掉终端就失效，需要时再粘贴一次）：

```bash
# 与 nusctl 内部完全相同的 Compose 调用方式：读 .env，有域名配置时自动带上
nus_compose() {
  if [ -f /srv/nus/config/domain-nginx/nginx.conf ] && [ -f /srv/nus/config/domain-nginx/compose.override.yaml ]; then
    sudo docker compose --project-name nus --env-file /srv/nus/config/.env \
      -f /srv/nus/current/runtime/compose.yaml -f /srv/nus/config/domain-nginx/compose.override.yaml "$@"
  else
    sudo docker compose --project-name nus --env-file /srv/nus/config/.env \
      -f /srv/nus/current/runtime/compose.yaml "$@"
  fi
}

# 在 MySQL 容器里执行 SQL（从标准输入读）。口令只走容器内的环境变量，不出现在命令行上。
nus_sql() {
  nus_compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysql --protocol=socket -uroot --default-character-set=utf8mb4 --table "$MYSQL_DATABASE"'
}
```

用法示例：

```bash
nus_compose ps
echo "SELECT COUNT(*) AS 用户数 FROM system_users WHERE deleted = 0;" | nus_sql
```

**`nus_sql` 用的是数据库 root 账号，只用来执行 `SELECT`。** 任何 `UPDATE`、`DELETE`、`ALTER` 都属于“直接改线上数据库”，见第 12 章。

## 1. 系统总览

### 1.1 服务组成

平台运行在一台 Ubuntu 24.04 服务器上，由 Docker Compose 管理 7 个容器（项目名 `nus`，容器名形如 `nus-backend-1`）：

| 服务名 | 作用 | 停了会怎样 |
| --- | --- | --- |
| `frontend` | Nginx：提供网页，把 `/admin-api/` 转给后端，转发监控页面 | 页面打不开 |
| `backend` | Java 后端（Spring Boot），平台的全部业务逻辑、定时任务、AI 调用 | 页面能打开但所有操作失败 |
| `mysql` | MySQL 8.4，业务数据库 `nus` | 后端起不来 |
| `redis` | Redis 7.4，登录状态、验证码、缓存 | 后端起不来或无法登录 |
| `elasticsearch` | SkyWalking 的存储 | 只影响监控 |
| `skywalking-oap` | SkyWalking 链路追踪的收集端 | 只影响监控 |
| `skywalking-ui` | SkyWalking 的页面（Horizon） | 只影响监控 |

后端是**唯一写数据库和 Redis 的程序**。所以升级、恢复、回滚时，脚本只停前端和后端。

### 1.2 网络与端口

服务器上只对外开放两个端口，其余端口都只在容器内部网络里：

| 宿主机端口 | 对应 | 用途 | 修改方式 |
| --- | --- | --- | --- |
| 80 | `frontend` 的 8080 | 平台网页和接口 | `.env` 里的 `HTTP_PORT`（默认 80，一般不改） |
| 8082 | `frontend` 的 8082 | SkyWalking 页面，经平台登录校验后才能看 | `.env` 里的 `NUS_SKYWALKING_UI_PORT` |

- MySQL（3306）、Redis（6379）、后端（48080，管理端口 48081）、Elasticsearch（9200）都**不映射到宿主机**，从服务器外面连不上，这是有意的。
- 后端接入了 `nus-egress` 网络，可以访问互联网。外部 AI 模型和校园资讯抓取需要服务器有出网能力；没有出网时这两项不可用，其他功能不受影响。

### 1.3 目录布局（`/srv/nus`）

```text
/srv/nus/
├── config/                     配置（目录 0755，文件 0600，只有 root 能读）
│   ├── .env                    全部口令、密钥、镜像标签、站点地址。最重要的文件
│   ├── .env.before-<版本>-<时间>   每次升级前自动保存的旧 .env（回滚要用）
│   ├── .env.before-rollback-from-<版本>-<时间>   回滚前保存的 .env
│   ├── .admin-bootstrap-complete  首次安装已设置管理员密码的标记
│   └── domain-nginx/           切换域名后才有：nginx.conf、compose.override.yaml、origins.json
├── data/
│   ├── mysql/                  MySQL 数据文件（不要直接拷贝运行中的这个目录当备份）
│   ├── redis/                  Redis 持久化文件（登录状态、缓存）
│   ├── uploads/                **上传的附件、图片、头像、课程资源**（属主 10001:10001）
│   ├── tmp/                    后端临时目录（AI 初评处理附件用）
│   ├── elasticsearch/          监控数据，按天自动过期
│   └── horizon/                SkyWalking 页面的数据
├── logs/
│   ├── backend/                后端日志文件 nus-server.log、nus-server.log.error 及按天滚动的 .gz
│   └── upgrade/                每次升级的日志，以及失败时新容器的日志
├── backups/                    数据库备份 db-nus-<UTC时间>.sql.gz 和 .sha256
├── upgrades/                   每次升级的记录 <UTC时间>-<版本>.env（不含口令，回滚靠它找备份）
├── releases/<版本>/            每个装过的版本的脚本和 Compose 文件（很小，见第 10 章）
└── current -> releases/<版本>  当前运行的版本
```

另外：

- `/usr/local/bin/nusctl` 是指向 `/srv/nus/current/nusctl` 的链接，所以 `nusctl` 永远是当前版本的那一份。
- `/etc/sysctl.d/99-nus-observability.conf` 设置 `vm.max_map_count=262144`（Elasticsearch 需要）。
- Docker 镜像存放在 Docker 自己的数据目录（通常 `/var/lib/docker`），不在 `/srv/nus`。

### 1.4 数据在哪里、哪些必须备份

| 内容 | 位置 | 必须备份 | 现有工具 |
| --- | --- | --- | --- |
| 业务数据（用户、课程、任务、提交、成绩、通知、配置、AI 密钥密文） | MySQL 库 `nus` | **是** | `nusctl backup` |
| 上传的文件（作业附件、图片、课程资源、头像） | `/srv/nus/data/uploads/` | **是** | **没有**，见 4.3 手动方法 |
| 口令与密钥 | `/srv/nus/config/.env` | **是**（单独、加密保存） | **没有**，见 4.3 |
| 域名配置 | `/srv/nus/config/domain-nginx/` | 建议 | 不在 `nusctl backup` 范围内，单独加密保存（4.3） |
| 登录状态、缓存 | `/srv/nus/data/redis/` | 否（丢了只是大家要重新登录） | — |
| 监控数据 | `/srv/nus/data/elasticsearch/`、`horizon/` | 否 | — |
| 日志 | `/srv/nus/logs/` | 否（排查需要时手动保存） | — |

> **特别注意 `.env` 里的 `NUS_MYBATIS_ENCRYPTOR_PASSWORD`**：AI 平台的 API 密钥在数据库里是用它加密的。这个值丢了或被改了，数据库备份里的 API 密钥就再也解不开。**任何时候都不要删除或重新生成它。**

## 2. 首次安装

只在**全新的服务器**上做一次。已经装过的服务器用第 5 章的升级，不要重新安装。

### 2.1 服务器要求

| 项目 | 要求 | 说明 |
| --- | --- | --- |
| 操作系统 | **Ubuntu 24.04，amd64（x86_64）** | 安装脚本会检查，不符合直接退出 |
| CPU / 内存 / 磁盘 | 建议 16 vCPU、16 GiB 内存、120 GiB 以上磁盘 | 各容器内存上限合计约 11.5 GiB（MySQL 2.5G、ES 3G、OAP 1.5G、后端 2.5G、其他约 2G） |
| 权限 | 一个能 `sudo` 的账号 | |
| 软件 | 不需要预装 Docker | 全量包里带了 Docker 的离线 deb；`configure-domain.sh` 需要系统自带的 `python3` |
| 网络 | 校园网能访问服务器的 80 端口（和 8082，如需要监控） | 外部 AI 需要出网，可以以后再开 |
| 时间 | 时区和时间同步配好 | 见第 11 章，**装之前就配好** |

先确认系统：

```bash
cat /etc/os-release | grep -E '^(ID|VERSION_ID)='   # 应为 ID=ubuntu、VERSION_ID="24.04"
uname -m                                            # 应为 x86_64
df -h /srv 2>/dev/null || df -h /                   # 剩余空间
timedatectl                                         # 时区、时间同步
```

### 2.2 用全量安装包安装

**什么时候做**：新服务器第一次部署。

全量安装包是一个目录 `nus-offline-<版本号>-ubuntu24.04-amd64/`（结构见附录 C）。把它复制到服务器上任意目录，例如 `<运维账号>` 的家目录。

**命令**：

```bash
cd ~/nus-offline-<版本号>-ubuntu24.04-amd64
sha256sum --check SHA256SUMS          # 全部应为 OK
tmux new -s nus-install
sudo NUS_SITE_URL=http://<服务器内网地址> ./install.sh
```

- `NUS_SITE_URL` 是平台的访问地址，会写进 `.env`、文件下载地址和部署记录。不填时脚本用服务器的第一个 IP。
- 学校网关负责 HTTPS 时，**先用 `http://<服务器内网地址>` 装好、验收，再按 2.4 切换域名**。这是历史上走通的做法。
- 如果要改监控端口，在命令前加 `NUS_SKYWALKING_UI_PORT=<端口>`；如果监控有独立的 HTTPS 地址，加 `NUS_SKYWALKING_URL=<监控地址>/`。不加时监控地址是 `http://<站点主机>:8082/`。

安装脚本依次做这些事（以 `install.sh` 为准）：

1. 检查 root、Ubuntu 24.04 amd64，用 `SHA256SUMS` 校验整个包；
2. 没有 Docker 时，用包里 `apt/*.deb` 离线安装；
3. 建 `/srv/nus` 下的目录，设置 `vm.max_map_count`；
4. 没有 `.env` 时生成一份，所有口令、密钥都用 `openssl rand` 随机生成；
5. 导入镜像，启动 MySQL、Redis、Elasticsearch、SkyWalking 并等健康检查；
6. 空库时导入基线 SQL 并登记 Flyway 基线（V21），然后执行 Flyway 迁移；
7. 写入站点地址、文件存储路径；
8. **设置管理员密码**（见 2.3）；
9. 启动后端、前端，等健康检查，建立 `/srv/nus/current` 和 `/usr/local/bin/nusctl`。

**怎么确认成功**：

- 屏幕最后一行是 `[nus] Installation completed`；
- 执行：

  ```bash
  sudo nusctl status                              # 7 个服务都是 Up，带 (healthy)
  sudo nusctl doctor                              # Flyway schema version 显示 21
  curl --noproxy '*' -fsS http://127.0.0.1/nginx-health    # 输出 ok
  readlink /srv/nus/current                       # releases/<版本号>
  ```

- 在校园网里的电脑上用浏览器打开 `http://<服务器内网地址>/`，用 `admin` 和刚设的密码登录。

**失败怎么办**：

- 校验失败（`release checksum failed`）：包不完整，重新复制。
- `Ubuntu 24.04 is required` / `amd64 host is required`：换服务器。
- `non-empty database without trusted Flyway history`：`/srv/nus/data/mysql` 里已有别的数据。**停下来联系指导老师**，不要删目录。
- 管理员密码相关报错：见 2.3。
- 其他报错：保存屏幕输出，执行 `sudo nusctl status` 和 `sudo nusctl logs backend --since 30m --error`，按[故障排查](故障排查.md)处理。修好后**可以重新执行同一条 `install.sh` 命令**：已有的 `.env` 会沿用，已导入的数据库不会重复导入，已设置过的管理员密码不会再设置。

### 2.3 首个管理员（改掉基线默认口令）

基线数据库里自带一个 `admin` 超级管理员账号，口令是一个公开的默认值。安装时脚本会**强制替换它**：

- 交互安装时，屏幕出现 `New admin password:` 和 `Confirm admin password:`，输入两次（不显示字符）。
- 无人值守安装时，先准备一个口令文件：

  ```bash
  umask 077
  vi ~/nus-admin-password          # 只写一行口令，保存退出
  chmod 600 ~/nus-admin-password
  sudo NUS_SITE_URL=http://<服务器内网地址> NUS_ADMIN_PASSWORD_FILE=$HOME/nus-admin-password ./install.sh
  rm -f ~/nus-admin-password       # 装完立即删除
  ```

**口令要求**（脚本和后端都会检查）：12～16 位；只用 ASCII，不能有空格和中文；必须同时有大写字母、小写字母、数字、特殊字符；不能包含 `admin`，不能是常见弱口令。

**机制说明**：脚本用一次性参数启动后端，后端只在 `admin` 的口令仍是基线默认值时才替换，成功后写 `/srv/nus/config/.admin-bootstrap-complete`，临时口令文件 `config/admin-password` 随即删除。所以这个步骤**只能用一次**，以后忘记密码不能靠它（见 8.1）。

**失败怎么办**：

| 报错 | 原因 | 处理 |
| --- | --- | --- |
| `admin passwords do not match` | 两次输入不一致 | 重新执行安装命令 |
| `admin password length must be between 12 and 16 characters` | 长度不对 | 同上 |
| `administrator password bootstrap failed` | 口令不满足复杂度，或 `admin` 口令已不是默认值 | 看上面几行的具体原因；口令问题就换个口令重跑 |
| `interactive admin password input required` | 不在终端里运行又没给口令文件 | 在终端里运行，或用 `NUS_ADMIN_PASSWORD_FILE` |

**装好之后**：

1. 用 `admin` 登录，在“系统管理 > 用户管理”里给每位真正的管理员**各建一个账号**（见 8.2），日常不要共用 `admin`。
2. `admin` 的口令交给指导老师，通过约定的私密方式保管，不发群聊、不写进文档或截图。

### 2.4 域名与 HTTPS（学校网关负责证书）

学校的做法是：**学校网关持有证书、负责 HTTPS**，再用 HTTP 回源到本服务器的 80 端口。本服务器不放证书。

**什么时候做**：内网地址验收通过后，学校分配了正式域名、网关已配置好回源时。

**需要和学校网络管理员确认的网关设置**：

| 项目 | 要求 | 原因 |
| --- | --- | --- |
| 回源地址 | `http://<服务器内网地址>:80` | 平台入口 |
| 请求体大小 | 不小于平台的附件上限（平台 Nginx 允许 520 MB；附件默认单个 100 MB、合计 300 MB，可在参数里调） | 否则大附件上传失败 |
| 超时 | 读写超时不小于 300 秒 | AI 生成、导入等长请求 |
| 缓冲 | 路径以 `-stream` 结尾的接口不要缓冲 | AI 对话是流式输出 |
| 监控 | 如需从外网看 SkyWalking，**另配一个独立的 HTTPS 域名或端口**回源到 8082，不能和平台同一个地址 | 脚本会拒绝同源 |

**命令**：域名切换脚本 `configure-domain.sh` **不在升级包里**，在仓库的 `deploy/offline/` 目录，详细说明见同目录的 `configure-domain.README.md`。把这个脚本复制到服务器，在脚本所在目录执行：

```bash
# 1. 先备份（脚本自己不做任何备份）
sudo nusctl backup
# 2. 只读预检查：读部署和数据库、校验 Compose，不改任何东西
sudo bash configure-domain.sh --site-url <学校站点地址> --keep-monitor --dry-run
# 3. 正式执行（会短暂停前后端）
sudo bash configure-domain.sh --site-url <学校站点地址> --keep-monitor --yes
```

- **一定要写 `--site-url`**。脚本里内置了一个默认站点地址和一个历史内网地址，只适用于当初那台服务器。
- `--old-url http://旧地址` 可以重复写，补充以前用过的站点地址，脚本会把这些地址开头的文件链接改成新地址。当前 `.env` 里的旧地址会自动包括在内。
- 监控已有独立 HTTPS 入口时，用 `--monitor-url <监控地址>` 代替 `--keep-monitor`。
- 不加 `--yes` 时，脚本最后会要求输入大写的 `YES`。

脚本做了什么：

1. 把 `.env` 的 `NUS_SITE_URL` 改成新地址；
2. 在一个数据库事务里：改文件存储的域名、部署记录，并把附件、头像、图片、富文本字段里旧地址开头的文件链接（`/admin-api/infra/file/`、`/app-api/infra/file/`）改成新地址；
3. 生成平台 Nginx 配置 `/srv/nus/config/domain-nginx/nginx.conf`，固定告诉后端“外部是 HTTPS、域名是这个”；
4. 重建前后端并检查服务器本机的首页。

**怎么确认成功**：

- 屏幕显示 `主平台切换完成：<学校站点地址>`；
- `ls /srv/nus/config/domain-nginx/` 能看到 `nginx.conf`；
- **从校外或校内另一台电脑**用浏览器打开 `<学校站点地址>`：登录、打开一个旧附件、看一张旧图片、上传一个新文件。服务器本机检查通过不能代替这一步。

**失败怎么办**：

- 修改开始后报错，脚本**不会自动回滚，也不会重新启动前后端**。保存错误输出，排除原因后**重复执行同一条命令**即可（数据库更新在一个事务里，可以重复）。
- 仍然恢复不了：用第 1 步的备份 `sudo nusctl restore <备份文件>`，把 `.env` 的 `NUS_SITE_URL` 改回原值，再联系指导老师。

**以后升级会不会丢域名配置**：不会。升级脚本发现 `domain-nginx/nginx.conf` 时会生成 `compose.override.yaml`，`nusctl` 和升级脚本都会自动带上它。但这份 Nginx 配置是切换那一刻的快照：**新版本前端镜像里的 Nginx 配置改动不会生效**。版本说明里提到 Nginx 改动时，见[故障排查](故障排查.md)的“域名切换后”一节。

## 3. 日常巡检

### 3.1 看状态：`nusctl status`

**什么时候做**：每天一次；有人反映问题时第一件事。

```bash
sudo nusctl status        # 不带参数的 sudo nusctl 也是 status
```

**怎么判断正常**：7 个服务都是 `Up ... (healthy)`。

| 看到 | 含义 | 处理 |
| --- | --- | --- |
| `(health: starting)` | 刚启动，还在等健康检查 | 后端最多要 3～5 分钟，等一会再看 |
| `(unhealthy)` | 健康检查失败 | 看该服务日志，见[故障排查](故障排查.md) |
| `Exited` / `Restarting` | 容器退出或在反复重启 | 同上 |
| 少了某个服务 | 容器被删了 | `sudo nusctl start` |

### 3.2 综合体检：`nusctl doctor`

**什么时候做**：每周一次；升级前后；排查问题时。

```bash
sudo nusctl doctor
```

它依次输出（以 `nusctl` 脚本为准）：

1. Docker 版本；
2. 各服务状态（同 `status`）；
3. `/srv/nus` 所在分区的磁盘使用（`df -h`）；
4. 内存（`free -h`）；
5. `vm.max_map_count`，应为 `262144`；
6. `SkyWalking storage:` Elasticsearch 集群健康，`"status"` 为 `green` 或 `yellow` 都正常（单节点通常是 yellow 或 green）；
7. `Flyway schema version:` 数据库迁移版本，V1.0.1.10 应为 `21`；
8. 后端、OAP、Elasticsearch 最近 40 行日志里的 `ERROR` / `Exception`（最多 20 行）。

各版本对应的 Flyway 版本：V1.0.1.6 → 17，V1.0.1.7 → 18，V1.0.1.8 / V1.0.1.8.1 → 19，V1.0.1.9 → 20，V1.0.1.10 → 21。

### 3.3 磁盘、内存、备份

## 4. 备份与恢复

### 4.1 完整备份：`nusctl backup`

**什么时候做**：任何改动操作之前（升级、恢复、切换域名、改配置、学期收尾）；日常由定时任务每天做（4.4）。

```bash
sudo nusctl backup
# 只需要数据库时（保持原来只输出数据库路径的行为）：
sudo nusctl backup --db-only
```

默认在 `$DATA_ROOT/backups`（默认 `/srv/nus/backups`）生成三份文件，每份都有 `.sha256`，屏幕汇总路径和大小：

| 文件 | 内容 |
| --- | --- |
| `db-nus-<时间>.sql.gz` | 数据库一致快照 |
| `files-<时间>.tar.gz` | `$DATA_ROOT/data/uploads` 上传附件，包内以 `uploads/` 开头 |
| `env-<时间>.env` | `$CONFIG_ROOT/.env`（默认 `/srv/nus/config/.env`）的逐字节副本 |

文件名时间为 **UTC**（北京时间减 8 小时）。汇总中的开始时间标识本次备份；数据库先备份，附件和配置文件采用开始时间，数据库文件名可能略晚。**异地拷贝时三份文件及各自校验文件一起拷。`env-*.env` 含口令和密钥，权限 0600，异地保存时要加密。**

脚本保证：

- 数据库仍由原来的 `backup.sh` 执行 `mysqldump --single-transaction`，含存储过程、事件、触发器；gzip 校验和完成标记校验不变；升级、恢复、回滚中的安全备份仍只备份数据库。
- 附件包保留权限和修改时间，执行 `gzip -t`、`tar -tzf`，核对普通文件数量；目录不存在或为空时生成空包并提示。配置副本用 `cmp` 逐字节校验，不打印配置内容。
- 文件先暂存，附件和配置全部校验通过后才改为正式文件；失败清理半成品，同一时间戳重复执行会加序号，避免覆盖。
- 默认不停服务。数据库与附件并非同一时刻的原子快照：打包期间有上传时可能数量校验失败，低峰期重试；需要严格一致时，经指导老师同意先停后端再备份，完成后启动。

自己再验一次（将文件名替换为汇总中的实际名称）：

```bash
cd /srv/nus/backups
sudo sha256sum -c db-nus-<时间>.sql.gz.sha256
sudo sha256sum -c files-<时间>.tar.gz.sha256
sudo sha256sum -c env-<时间>.env.sha256
sudo gzip -t files-<时间>.tar.gz
sudo tar -tzf files-<时间>.tar.gz | head
```

**失败怎么办**：数据库失败时不会继续备份附件；附件或配置失败时，命令返回非零，并打印“数据库备份已成功”及路径，此时不能把数据库文件当作完整备份。检查附件、配置的可读性和空间，修复后重做。`mysql is not running` → `sudo nusctl start` 后重试；空间不够 → 第 10 章；其他 → [故障排查](故障排查.md)。

### 4.2 数据库备份里有什么、没有什么

| 有 | 没有 |
| --- | --- |
| `nus` 库的全部表：用户、角色、课程、班级、任务、提交、成绩、通知、参数、定时任务、AI 密钥（密文）、文件记录（只是记录和路径） | 上传文件本身（在 `data/uploads/`） |
| | `.env`（口令、`NUS_MYBATIS_ENCRYPTOR_PASSWORD`） |
| | MySQL 的账号和口令（`mysql` 系统库） |
| | Redis（登录状态） |

所以**只有数据库备份时**：能恢复全部业务记录，但附件、图片打不开；换了 `.env` 的服务器上 AI 密钥解不开。

### 4.3 附件与 `.env` 的保存和恢复

`nusctl backup` 已包含附件与 `.env`。后端容器 `/app/uploads` 对应宿主机 `$DATA_ROOT/data/uploads`。完整恢复时选择同一次备份的三份文件；数据库记录依赖附件，只有数据库备份仍不能恢复图片和上传文件。

**附件恢复**（需要指导老师同意；先在演练环境核对）：先校验 `.sha256`、`gzip -t`，检查 `tar -tzf` 中路径都在 `uploads/` 下，再停后端，将现有目录改名留底，解包到 `$DATA_ROOT/data/`。以下按默认目录举例：

```bash
cd /srv/nus/backups
# 先记录备份里的普通文件数（GNU tar 的 - 表示普通文件，h 表示硬链接）
sudo sha256sum -c /srv/nus/backups/files-<时间>.tar.gz.sha256
sudo gzip -t /srv/nus/backups/files-<时间>.tar.gz
sudo tar -tzf /srv/nus/backups/files-<时间>.tar.gz
sudo tar -tvzf /srv/nus/backups/files-<时间>.tar.gz | awk '/^[-h]/ {n++} END {print n+0}'
nus_compose stop backend
# 目录不存在时跳过这一行；留底名称不可与已有目录重复
sudo mv /srv/nus/data/uploads /srv/nus/data/uploads.before-$(date -u +%Y%m%dT%H%M%SZ)
sudo tar -xzpf /srv/nus/backups/files-<时间>.tar.gz -C /srv/nus/data
sudo find /srv/nus/data/uploads -type f -printf '.' | wc -c  # 必须与包内普通文件数相同，再继续
sudo chown -R 10001:10001 /srv/nus/data/uploads
nus_compose up -d backend
```

核对文件数时用 `sudo find /srv/nus/data/uploads -type f -printf '.' | wc -c`（每个普通文件一个点，支持文件名换行），应与包内普通文件数一致；**相同后再启动后端**。启动后检查 `sudo nusctl status`，登录打开几个附件；不一致时先停在原地排查，原目录已留底，不要直接删掉。`nus_compose` 的定义见本手册前文。

**`.env` 保存**：备份副本含数据库口令及 `NUS_MYBATIS_ENCRYPTOR_PASSWORD`；丢失后数据库里的 AI 密钥可能无法解密。离开服务器前单独加密，例如：

```bash
sudo gpg --symmetric --cipher-algo AES256 -o /srv/nus/backups/env-<时间>.env.gpg /srv/nus/backups/env-<时间>.env
sudo sh -c 'cd /srv/nus/backups && sha256sum env-<时间>.env.gpg > env-<时间>.env.gpg.sha256'
```

加密口令由指导老师保管，不放在命令行或脚本里。异地传加密文件及其另行生成的校验和，原始 `.env.sha256` 一起保存，留作解密后的核验（校验文件不含配置内容）。`config/domain-nginx/` **不在本命令备份范围内**，有域名配置时仍需单独加密保存。

**`.env` 恢复**：只在配置误删、损坏、整机灾难恢复，或确认需要对应历史加密密钥时使用；普通数据库恢复不要盲目覆盖配置。先解密到受保护目录（`umask 077`），用原 `.sha256` 核验；经指导老师确认版本镜像、站点配置、数据库和 Redis 的**当前**口令及加密密钥后，停服务（`sudo nusctl stop`），将现有 `.env` 改名留底，把副本复制到 `$CONFIG_ROOT/.env` 并设 `root:root`、0600，再 `sudo nusctl start` 并检查登录、附件和 AI 配置读取。**恢复 `.env` 不会恢复数据库账号口令**，改过口令时旧副本可能已不匹配；不要打印内容，也不要重新生成加密密钥。

### 4.4 定时备份（crontab 示例与保留策略）

**现状**：现有脚本**没有定时备份**（待开发）。下面是手动配置的方法：在服务器上建一个脚本，由 root 的 cron 每天执行。这个脚本是你自己装的，**不随升级包更新**，升级后也不会被覆盖。

**第 1 步：建脚本** `sudo vi /usr/local/sbin/nus-daily-backup.sh`，内容：

```sh
#!/bin/sh
# 师砺平台每日备份：数据库 + 附件 + 配置 + 数量快照 + 清理过期备份。由运维手动安装，见 docs/04-运维/运维手册.md 4.4。
set -eu
umask 077
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
BACKUP_DIR=/srv/nus/backups
KEEP_DAYS=14            # 普通每日备份保留天数
stamp=$(date -u +%Y%m%dT%H%M%SZ)

echo "==== $(date '+%F %T') start"

# 1. 完整备份；三份路径和大小直接写入 cron 日志，不再把输出当成单个路径
nusctl backup

# 2. 记下备份后的数量，恢复演练时对照（完整备份结束后的数字，可能比数据库快照多出期间新增的记录）
mysql_cid=$(docker ps -q -f label=com.docker.compose.project=nus -f label=com.docker.compose.service=mysql)
docker exec -i "$mysql_cid" sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysql --protocol=socket -uroot "$MYSQL_DATABASE"' \
  > "$BACKUP_DIR/daily-$stamp.counts" <<'SQL'
SELECT 'users', COUNT(*) FROM system_users WHERE deleted = 0;
SELECT 'homework', COUNT(*) FROM edu_homework WHERE deleted = 0;
SELECT 'submissions', COUNT(*) FROM edu_homework_record WHERE deleted = 0 AND submit_time IS NOT NULL;
SELECT 'latest_submit', MAX(submit_time) FROM edu_homework_record WHERE deleted = 0;
SQL
cat "$BACKUP_DIR/daily-$stamp.counts"

# 3. 清理超过 KEEP_DAYS 天的数据库备份；升级记录引用的备份（回滚要用）一律保留
referenced=$(grep -h '^DB_BACKUP=' /srv/nus/upgrades/*.env 2>/dev/null | sed "s/^DB_BACKUP=//; s/^'//; s/'\$//" || true)
find "$BACKUP_DIR" -maxdepth 1 -name 'db-nus-*.sql.gz' -mtime +"$KEEP_DAYS" | while IFS= read -r f; do
  if printf '%s\n' "$referenced" | grep -qxF "$f"; then continue; fi
  rm -f "$f" "$f.sha256" "$f.counts"; echo "removed $f"
done
# 附件、配置与数量快照采用相同保留天数；先确保三份已完成异地保存，再启用清理。
find "$BACKUP_DIR" -maxdepth 1 -type f \( -name 'files-*.tar.gz' -o -name 'env-*.env' -o -name 'daily-*.counts' \) \
  -mtime +"$KEEP_DAYS" | while IFS= read -r f; do
  rm -f "$f" "$f.sha256"; echo "removed $f"
done

echo "==== $(date '+%F %T') done"
```

```bash
sudo chmod 0700 /usr/local/sbin/nus-daily-backup.sh
sudo /usr/local/sbin/nus-daily-backup.sh       # 先手动跑一次，确认没有报错
```

**第 2 步：加定时任务** `sudo vi /etc/cron.d/nus-backup`，内容（每天凌晨 2:30，按服务器本地时区）：

```text
SHELL=/bin/sh
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
30 2 * * * root /usr/local/sbin/nus-daily-backup.sh >> /var/log/nus-backup.log 2>&1
```

- 避开凌晨 03:20～03:35，那时平台自己在清理日志（定时任务）；也避开 00:05、00:15 的学期自动更新、公共课同步。
- 文件放在 `/etc/cron.d/` 时必须写用户名 `root`，文件名不能带点。

**怎么确认成功**：第二天看 `tail -n 30 /var/log/nus-backup.log`，有 `done` 且没有 `ERROR`；`ls -lt /srv/nus/backups | head` 有当天的新文件。

**保留策略建议**：

| 类型 | 本机保留 | 异地保留 |
| --- | --- | --- |
| 每日完整备份（三份及校验和） | 14 天 | 30 天以上，配置加密 |
| 升级时自动做的备份（升级记录引用的） | 至少保留最近两次升级的，旧的按第 10 章手动清 | 每学期至少留一份 |
| 学期末 | — | 每学期末留一份数据库 + 附件 + 加密配置，长期保留 |

每日完整备份包含全部附件，大小取决于附件和数据库的数据量，配好后看几天的实际大小再调整 `KEEP_DAYS`。

### 4.5 异地拷贝

备份和平台在同一块盘上，盘坏了一起丢。**至少有一份副本在另一台机器上。** 学校有统一备份服务时优先用学校的；没有时按下面做（手动方法）。

备份文件属主是 root、权限 0600，所以要以 root 身份推送。在服务器上为 root 准备一个**只用于备份**的 SSH 密钥，并在 `<备份机地址>` 上授权（具体账号由学校或指导老师分配）：

```bash
sudo ssh-keygen -t ed25519 -N '' -f /root/.ssh/nus-backup
sudo cat /root/.ssh/nus-backup.pub        # 把这一行交给备份机管理员加进授权列表
```

推送（可以加进 4.4 脚本的末尾，或另配一条 cron）：

```bash
# 先按 4.3 加密各份 env-*.env；只推送加密副本，不推送明文
sudo rsync -a --exclude='env-*.env' --exclude='*.lock/' -e 'ssh -i /root/.ssh/nus-backup' /srv/nus/backups/ <备份账号>@<备份机地址>:/backup/nus/backups/
```

- 同一次备份的数据库、附件包、加密配置及校验和必须一起推送；确认命令已成功结束再同步。**不要加 `--delete`**，避免删除备份机上的历史副本。
- 没有备份机时，最低限度：每周把同一次的数据库、附件包和加密的 `.env` 用 `scp` 拷到指导老师指定的位置。

**怎么确认成功**：在备份机上 `ls -lt /backup/nus/backups | head`，并对最新文件执行 `sha256sum -c <文件>.sha256`。

### 4.6 恢复演练

**什么时候做**：每学期至少一次；更换备份方案后。**演练不在正式服务器上做。**

#### 方法 A：只验证备份能恢复、数据对得上（任何有 Docker 的机器）

在一台不是正式服务器的机器上（测试服务器或你的电脑），用一次性 MySQL 容器导入备份。容器名用一个不会和别人撞的名字，**不要动这台机器上已有的容器**：

```bash
f=db-nus-<时间>.sql.gz                       # 从异地备份取来的文件，同目录有 .sha256，另取同一次每日备份的 daily-<时间>.counts
sha256sum -c $f.sha256
docker run -d --rm --name nus-restore-drill --network none \
  -e MYSQL_ROOT_PASSWORD=drill-only-$(openssl rand -hex 8) mysql:8.4.6
sleep 40                                     # 等 MySQL 初始化完成
gzip -dc $f | docker exec -i nus-restore-drill sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot'
docker exec -i nus-restore-drill sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot --table nus' <<'SQL'
SELECT COUNT(*) AS 用户数 FROM system_users WHERE deleted = 0;
SELECT COUNT(*) AS 任务数 FROM edu_homework WHERE deleted = 0;
SELECT COUNT(*) AS 提交数 FROM edu_homework_record WHERE deleted = 0 AND submit_time IS NOT NULL;
SELECT MAX(submit_time) AS 最新提交时间 FROM edu_homework_record WHERE deleted = 0;
SELECT MAX(CAST(version AS UNSIGNED)) AS Flyway版本 FROM flyway_schema_history WHERE success = 1;
SQL
docker stop nus-restore-drill                # --rm 会自动删除容器和数据
```

**怎么判断成功**：导入没有报错；四个数字和 `daily-<时间>.counts` 文件里的一致（数量快照在完整备份后记录，可能比数据库快照多出备份期间新增的记录）；最新提交时间接近备份时间；Flyway 版本和备份时平台的版本一致。

#### 方法 B：完整恢复（测试服务器）

在装了**同一版本**平台的测试服务器上（测试服务器由指导老师维护）：

```bash
sudo nusctl restore /path/to/db-nus-<时间>.sql.gz      # 输入 yes
sudo nusctl status
```

然后用 4 条核对 SQL（同上，改用 `nus_sql`）对照，再登录看几份提交、打开几个附件（附件需要同时把附件包解到测试服务器的 `/srv/nus/data/uploads/`）。注意：

- 测试服务器的 `.env` 和正式服务器不同，**AI 密钥解不开是正常的**；
- 备份里的文件存储域名是正式站点的，测试服务器上附件链接会指向正式站点，这是演练环境的预期现象。

**演练记录**：日期、备份文件名、核对的 4 个数字、耗时、遇到的问题。

### 4.7 正式环境恢复数据库：`nusctl restore`

**什么时候做**：数据库损坏、误操作导致大量数据错误，且**指导老师同意**用备份覆盖时。这是最后手段：**备份之后产生的所有数据都会丢失**。

```bash
sudo nusctl restore /srv/nus/backups/db-nus-<时间>.sql.gz
```

`nusctl restore` 依次（以脚本为准）：

1. 校验备份：gzip 完整性、`.sha256`（存在时）、mysqldump 完成标记、备份的库名是否为 `nus`。不通过时什么都不动；
2. 要求输入 `yes`（在脚本里调用、没有终端时必须加 `--yes`）；
3. 停止前端和后端；
4. **安全备份**：先把当前数据库另存一份，路径会打印出来（`--no-safety-backup` 可跳过，不建议）；
5. 删除并重建数据库，导入备份（备份之后新建的表也会消失；数据库账号授权不受影响）；
6. 清理 Redis 里的菜单、权限、角色、部门、模板等缓存，登录状态保留；
7. 启动后端和前端，等健康检查。

**怎么确认成功**：最后一行 `Restore completed: database nus now holds ...; backend and frontend are healthy`；`sudo nusctl status` 全部 healthy；用 4.6 的核对 SQL 确认数字。

**失败怎么办**：中途失败时平台保持停止，屏幕会打印一条**可以重复执行**的命令（`sudo '.../nusctl' restore '<文件>' --no-safety-backup --yes`），修好原因后照着执行。安全备份的路径也会打印，务必记下。

> `nusctl restore` 只恢复数据库。附件及 `.env` 的恢复必须另按 4.3 执行：停服务、留底、校验、恢复、检查，再启动。

## 5. 升级与回滚

### 5.1 两种安装包

| | 全量安装包 | 升级包（增量包） |
| --- | --- | --- |
| 目录名 | `nus-offline-<版本号>-ubuntu24.04-amd64` | `nus-update-<版本号>-ubuntu24.04-amd64`（另有同名 `.tar.gz` 和 `.tar.gz.sha256`） |
| 内容 | Docker deb、全部镜像、基线 SQL、迁移、脚本 | 后端 jar、前端 dist、全部迁移、脚本，压缩包约 150 MB |
| 用途 | 新服务器首次安装（也能用来升级） | **日常升级**，基于服务器上现有的镜像离线重建前后端 |

两种包都用同一个 `upgrade.sh` 升级。结构见附录 C。

### 5.2 跨多个版本升级

- 升级包里带着**全部**迁移文件，Flyway 只执行数据库还没有的版本，所以可以跳版本升级，例如 V1.0.1.8.1 直接升到 V1.0.1.10，会依次执行 V20、V21。
- **跳过的每个版本的版本说明都要读**（`docs/05-发布/版本说明/`）：里面有“升级前必读”“升级后需要学校确认的事项”，例如要求老师核对数据、重新登录、调整参数。这些不会因为跳版本而消失。
- 跳版本升级后如果回滚，回到的是**升级前的那个版本**（跳之前的版本）。

查看当前版本：

```bash
readlink /srv/nus/current                               # releases/<版本号>
sudo grep RELEASE_VERSION /srv/nus/current/release.env
sudo nusctl doctor | grep -A1 'Flyway schema version'
```

### 5.3 升级前检查清单

| # | 检查 | 怎么做 |
| --- | --- | --- |
| 1 | 指导老师已同意，时间已定 | 选没课、没有作业截止的时段 |
| 2 | 已读完当前版本到目标版本之间**每个版本**的版本说明 | 见 5.2 |
| 3 | 升级包已在测试服务器上升级成功过 | 问指导老师 |
| 4 | 已通知师生停机时段 | 正常停机约 1～2 分钟（测试服务器实测 67～84 秒）；升级失败自动回滚时可能 5 分钟左右 |
| 5 | 近几小时没有作业截止 | 下面的 SQL |
| 6 | 平台当前健康 | `sudo nusctl status` 全部 healthy，`sudo nusctl doctor` 无异常 |
| 7 | 磁盘够 | 至少“数据库大小 × 2 + 新镜像”且不低于 2 GiB，脚本会检查；建议使用率 < 70% |
| 8 | 已做额外备份 | `sudo nusctl backup` 生成三份，配置加密后一起拷到异地（4.3、4.5） |
| 9 | 升级包已校验 | 见 5.4 |
| 10 | 在 `tmux` 里操作 | 见 0.2 |
| 11 | 记录开始 | 运维记录写下：时间、原版本、目标版本、执行人 |

检查接下来 3 小时内有没有任务截止：

```bash
echo "SELECT COUNT(*) AS 三小时内截止的任务数 FROM edu_homework WHERE deleted = 0 AND deadline BETWEEN NOW() AND NOW() + INTERVAL 3 HOUR;" | nus_sql
```

### 5.4 升级步骤

**命令**：

```bash
# 1. 把 .tar.gz 和 .tar.gz.sha256 复制到服务器家目录后
cd ~
sha256sum --check nus-update-<版本号>-ubuntu24.04-amd64.tar.gz.sha256      # OK
tar -xzf nus-update-<版本号>-ubuntu24.04-amd64.tar.gz
cd nus-update-<版本号>-ubuntu24.04-amd64
sha256sum --check SHA256SUMS                                                # 全部 OK
cat release.env                                                             # 确认 RELEASE_VERSION 是目标版本
less 更新说明.md                                                            # 有这个文件时再读一遍

# 2. 在 tmux 里升级
tmux new -s nus-upgrade
sudo ./upgrade.sh "$PWD"
```

`upgrade.sh` 分四个阶段（以脚本为准）：

1. **预检**，什么都不改，平台照常服务：包校验；目标版本没有装过；新镜像标签没被占用；MySQL、Redis 健康；当前前后端镜像还在（回滚要用）；磁盘空间；用 Flyway `info` 和 `validate` 检查线上库。
2. **准备**，平台照常服务：构建（增量包）或导入（全量包）新镜像；生成待用的新 `.env`（`.env.next-<时间>`，补齐新增配置）；启动并检查 Elasticsearch、SkyWalking。
3. **切换**，**停机从这里开始**：保存 `.env` 为 `.env.before-<版本>-<时间>`；停前端和后端；**在没有写入时备份数据库**；换上新 `.env`；执行 Flyway 迁移；写站点配置；清理 Redis 里的菜单、权限、通知模板、参数、学期、指标、字典缓存（登录状态保留）。
4. **启动**：启动新后端、新前端并等健康检查（后端最多等约 3 分钟）；通过后才把 `/srv/nus/current` 指向新版本。

停机之后的任何失败（包括按 Ctrl-C、SSH 断开）都会**自动回滚**。

**看屏幕最后一段判断结果**：

| 最后一段 | 含义 | 怎么办 |
| --- | --- | --- |
| `Upgrade to <版本号> completed; backend and frontend are healthy` | 成功 | 做 5.5 验收 |
| `... stopped during preflight checks` 或 `... during prepare ...`，并有 `Nothing was stopped` | 预检或准备没通过，**平台没停，什么都没变** | 按上面的报错处理（如清理磁盘），然后重新执行 |
| `UPGRADE FAILED - <原版本> IS RUNNING AGAIN` | 停机后失败，已自动回滚，原版本在运行，数据库恢复到停机时的备份，**不丢数据** | 见[故障排查](故障排查.md)“升级失败” |
| `AUTOMATIC ROLLBACK DID NOT FINISH`（退出码 3） | 自动回滚也失败，**平台处于停止状态** | 按屏幕列出的命令依次执行（每条可重复），立即联系指导老师 |

**升级产生的文件**：

- 升级日志：`/srv/nus/logs/upgrade/<UTC时间>-<版本号>.log`
- 升级记录：`/srv/nus/upgrades/<UTC时间>-<版本号>.env`，记录原版本、新版本、数据库备份、`.env` 备份、状态（`completed`、`failed-rolled-back`、`rolled-back` 等），不含口令；
- 停机后做的数据库备份：`/srv/nus/backups/db-nus-<时间>.sql.gz`（路径在屏幕上和升级记录里）。

### 5.5 升级后验收

**免登录检查**（在服务器上执行；`--noproxy '*'` 避免系统代理干扰）：

```bash
sudo nusctl status                                          # 全部 healthy
sudo nusctl doctor | grep -A1 'Flyway schema version'       # 目标版本对应的 Flyway 版本
readlink /srv/nus/current                                   # releases/<新版本号>
curl --noproxy '*' -fsS http://127.0.0.1/nginx-health       # ok
curl --noproxy '*' -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/          # 200
curl --noproxy '*' -fsS http://127.0.0.1/admin-api/system/auth/social-login-config  # JSON，"code":0
curl --noproxy '*' -s http://127.0.0.1/admin-api/system/user/page                 # JSON，"code":401，"账号未登录"
sudo nusctl logs backend --since 15m --error                # 没有新的 ERROR，或都能解释
```

说明：平台的接口在未登录时返回 HTTP 200，但 JSON 里的业务码是 `401`，这是正常的。

**从外部检查**：在校园网的电脑上打开 `<学校站点地址>`，用管理员登录；再请一位老师、一位学生（或用指导老师给的测试账号）看常用页面。版本说明里要求的检查逐条做。

**收尾**：

- 运行 `sudo nusctl backup`，按 4.3 加密新的配置副本，再将三份备份一起异地保存；
- 运维记录写下：结束时间、结果、升级日志路径、升级时的数据库备份路径；
- 升级包目录**先保留**（升级记录里写着它的路径，排查要用），按第 10 章再清。

### 5.6 回滚

#### 先读：回滚的后果

**回滚会用升级时（停机后）做的数据库备份覆盖当前数据库。升级之后产生的所有数据——新提交、批改、留言、通知、新建的课程和账号——都会丢失。** 它们只保存在回滚前自动做的“安全备份”里，要找回只能人工逐条补录。

所以：

- **正式环境原则上不回滚。** 升级后发现问题，先保存现场（日志、截图、trace-id），**联系指导老师**，优先由开发方修复后发新版本。
- 只有在升级后**马上**发现严重问题（例如大家都登录不了、数据显示明显错误），还没有多少新数据，且指导老师同意时，才回滚。

升级**失败**时脚本已经自动回滚，不需要做这一节。

#### 回滚步骤

```bash
sudo nusctl rollback previous
```

也可以写版本号：`sudo nusctl rollback V1.0.1.9`。命令（以脚本为准）：

1. 从 `/srv/nus/upgrades/` 的升级记录找到离开原版本时的数据库备份和 `.env.before-*`；
2. 检查原版本的镜像还在本机、发布目录完整、备份完整；
3. 打印计划（用哪个备份、哪个 `.env`、哪个镜像），要求输入 `yes`；
4. 停前端和后端，把当前数据库另存为安全备份（**路径会打印，务必记下**）；
5. 删除并重建数据库，导入升级时的备份；
6. 把当前 `.env` 另存为 `.env.before-rollback-from-<版本>-<时间>`，恢复原来的 `.env`；
7. 清理 Redis 缓存，用原版本的镜像和 Compose 文件启动，等健康检查；
8. 把 `/srv/nus/current` 指回原版本。

**怎么确认成功**：最后显示 `Rollback completed: <原版本> is running, backend and frontend are healthy`；`readlink /srv/nus/current` 是原版本；按 5.5 做免登录检查（Flyway 版本应回到原版本的值）。

**失败怎么办**：

- 中途失败时平台保持停止，屏幕打印一条可以重复执行的 `nusctl rollback ... --no-safety-backup --yes` 命令，修好原因后照着执行。
- 提示 `no completed upgrade to <版本> is recorded`：这个版本是很早的升级脚本装的，没有升级记录。命令会列出已有的发布目录、`.env.before-*` 和备份，需要明确指定：

  ```bash
  sudo nusctl rollback <原版本号> --backup /srv/nus/backups/db-nus-<时间>.sql.gz --env /srv/nus/config/.env.before-<版本>-<时间>
  ```

- 提示 `image ... is not on this server any more`：原版本镜像被清理掉了，无法回滚。所以第 10 章清理镜像时一定要保留上一个版本。

> 改过数据库或 Redis 口令（8.3）之后，旧的 `.env.before-*` 里还是旧口令，直接回滚会导致后端连不上数据库。回滚前先联系指导老师。

## 6. 构建与打包（在开发机上）

这一章在**开发用的电脑**上做，不在学校服务器上做。前提：已按 [环境搭建](../03-开发/环境搭建.md) 装好 JDK 17、Maven、Node.js、pnpm、Docker；完整的发版流程（版本号、版本说明、测试、合并）见 [发版流程](../05-发布/发版流程.md)，这里只讲打包命令。

### 6.1 构建后端 jar 和前端 dist

```bash
# 在仓库根目录 shili-platform/
cd NUS-backend
TZ=Asia/Shanghai mvn clean verify          # 装了 mvnd 也可以用 mvnd；会跑全部测试
ls -l nus-server/target/nus-server.jar     # 约 160 MB
cd ../NUS-front
pnpm install --frozen-lockfile
pnpm check:type
pnpm build:production                      # 产物在 apps/web-antd/dist/
ls apps/web-antd/dist/index.html
cd ..
```

前端生产构建统一用 `pnpm build:production`，在 `NUS-front` 根目录执行。

### 6.2 打升级包：`build-update.sh`

**前提**（脚本会检查，不满足就拒绝打包）：

- 当前目录是 `shili-platform` 的 git 仓库；
- `NUS-backend/`、`NUS-front/` 里**没有任何**未提交或未跟踪的文件（被 `.gitignore` 忽略的构建产物除外）；
- 仓库其他目录没有已跟踪文件的改动（`NUS-doc/` 的未跟踪文件不影响，也不会进包）；
- jar 里有 `application.yaml`、`application-prod.yaml`，**没有** `application-local` / `application-dev` 配置；
- 版本号只含字母、数字、`.`、`_`、`-`；镜像必须是带明确标签的 `名字:标签`，不能是 `latest`、不能带摘要；
- 输出目录、压缩包都还不存在；本机有 `unzip`、`sha256sum`。

**命令**（在仓库根目录）：

```bash
VERSION=<版本号>                                   # 例如 V1.0.1.11，每次都要新号，不能重复
BACKEND_IMAGE=nus-backend:$VERSION \
FRONTEND_IMAGE=nus-front:$VERSION \
RELEASE_NOTES=docs/05-发布/版本说明/$VERSION.md \
CLEAN_BACKEND_BUILD=true \
./deploy/offline/build-update.sh "$VERSION"
```

- `RELEASE_NOTES` 指定的文件会以 `更新说明.md` 放进包里；不指定时只给警告，但**正式发布必须带**。
- `CLEAN_BACKEND_BUILD=true` 只在 jar 来自 `mvn clean ...` 的干净构建时设置，它只是记进 `BUILD-METADATA.json`。
- 镜像标签必须和服务器上正在用的不同，否则服务器上的预检会拒绝（`already in use`）。习惯上用 `V<版本号>`。

**输出**（脚本最后打印这三行）：

```text
releases/nus-update-<版本号>-ubuntu24.04-amd64/
releases/nus-update-<版本号>-ubuntu24.04-amd64.tar.gz
releases/nus-update-<版本号>-ubuntu24.04-amd64.tar.gz.sha256
```

`releases/` 在仓库根目录，已被 `.gitignore` 忽略，**包不进 git**。

### 6.3 核对校验值和构建来源

```bash
cd releases
sha256sum -c nus-update-<版本号>-ubuntu24.04-amd64.tar.gz.sha256        # macOS 没有 sha256sum 时：shasum -a 256 -c ...
(cd nus-update-<版本号>-ubuntu24.04-amd64 && sha256sum -c --quiet SHA256SUMS && echo 包内文件全部一致)
cat nus-update-<版本号>-ubuntu24.04-amd64/BUILD-METADATA.json
git rev-parse HEAD                                                     # 应等于 BUILD-METADATA.json 里的 repository.head
```

`BUILD-METADATA.json` 记录：版本号、构建时间、镜像标签、仓库提交号、jar / 前端首页 / 最新迁移的 SHA-256、是否干净构建。服务器上 `/srv/nus/current/BUILD-METADATA.json` 是同一份，可以用来确认线上跑的是哪次提交（V1.0.1.10 及更早的包记录的是旧仓库提交号，对照表见[当前状态](../06-交接/当前状态.md)）。

### 6.4 包放在哪里

- 开发机：`shili-platform/releases/`（不进 git）。
- 正式归档位置按[交接清单](../06-交接/交接清单.md)的约定（**待确认**：由指导老师指定统一存放位置）。至少保留学校服务器上装过的每个版本的升级包和 `.sha256`，回溯问题时要用。
- 先交指导老师在测试服务器上升级验证，再上学校服务器。

### 6.5 全量安装包：`build-release.sh`（很少用）

只有给新服务器首次安装时才需要。它要求：

- 已经构建好 `linux/amd64` 的后端、前端镜像（后端 `NUS-backend/nus-server/Dockerfile`、前端 `NUS-front/scripts/deploy/Dockerfile`，构建时**需要联网**下载语音模型和 SkyWalking Agent），以及 MySQL、Redis、Flyway、Elasticsearch、SkyWalking 的 `linux/amd64` 镜像都已 `docker pull` 到本机（具体版本见脚本开头的默认值）；
- `APT_CACHE_DIR` 指向一个目录，里面有 Ubuntu 24.04 amd64 的 `docker.io`、`docker-compose-v2`、`containerd`、`runc` 及其依赖的 `.deb`（获取方法**待演练**：可在一台干净的 Ubuntu 24.04 amd64 上用 `apt-get install --download-only` 取 `/var/cache/apt/archives/*.deb`）；
- 最高迁移版本、基线 SQL 顶部的 `-- Flyway baseline version:` 标记、脚本里的 `BASELINE_VERSION`（当前 21）三者一致。

```bash
VERSION=<版本号>
BACKEND_IMAGE=nus-backend:$VERSION FRONTEND_IMAGE=nus-front:$VERSION \
APT_CACHE_DIR=/absolute/path/to/apt-cache \
./deploy/offline/build-release.sh "$VERSION"
```

输出目录 `releases/nus-offline-<版本号>-ubuntu24.04-amd64/`。注意：这个脚本**不生成 `.tar.gz`，也不检查工作区是否干净、不写 `BUILD-METADATA.json`**。需要压缩包时自己打包并生成校验值。

## 7. 日志与监控

### 7.1 `nusctl logs`

```text
sudo nusctl logs [服务名] [--follow|-f] [--since 时间] [--error] [--trace-id ID]
```

- 服务名：`backend`（默认）、`frontend`、`mysql`、`redis`、`elasticsearch`、`skywalking-oap`、`skywalking-ui`；
- `--since`：`30m`、`2h`、`24h`，或时间点 `2026-10-14T08:00:00`；**不写时输出该容器全部日志**，可能很长；
- `--error`：只看含 ` ERROR ` 的行（注意：异常堆栈的后续行不含 ERROR，会被过滤掉，要看完整堆栈用 `--trace-id` 或日志文件）；
- `--trace-id`：只看某一次请求的日志（见 7.2）；
- `--follow`：持续输出新日志，Ctrl-C 退出。

常用：

```bash
sudo nusctl logs backend --since 30m --error          # 最近半小时后端错误
sudo nusctl logs backend --since 10m --follow         # 盯着后端实时日志
sudo nusctl logs frontend --since 30m                 # Nginx 访问日志（每行带状态码、耗时）
sudo nusctl logs mysql --since 1h
sudo nusctl logs skywalking-oap --since 30m --error
sudo nusctl logs backend --since 2h | grep -i 'AiReview' | tail -n 50    # 再配合 grep 缩小范围
```

**日志保存多久**：

| 日志 | 位置 | 保留 |
| --- | --- | --- |
| 容器日志（`nusctl logs` 看到的） | Docker 管理 | 每个容器最多 5 个文件 × 50 MB（Redis、前端、UI 为 20 MB）；**容器被重建（升级、回滚）后旧容器日志就没了** |
| 后端日志文件 | `/srv/nus/logs/backend/nus-server.log`（全部）、`nus-server.log.error`（只有 ERROR） | 按天和 50 MB 滚动成 `.gz`，保留 30 天、每类最多 2 GB |
| 升级日志 | `/srv/nus/logs/upgrade/` | 不自动清理 |

容器日志没了（比如升级之后）时查文件：

```bash
sudo ls -lt /srv/nus/logs/backend | head
sudo grep ' ERROR ' /srv/nus/logs/backend/nus-server.log | tail -n 50
sudo sh -c "zgrep -h ' ERROR ' /srv/nus/logs/backend/nus-server.log.2026-10-13.*.gz | tail -n 50"
```

### 7.2 用 trace-id 追查一次请求

后端给每个请求一个 trace-id，写在每行日志的 `[traceId=...]` 里，并通过响应头 `X-Trace-Id` 返回给浏览器。

**拿到 trace-id 的方法**：

1. 请出问题的用户（或你自己复现）在浏览器按 F12 → “网络/Network”，点出错的那个请求，在“响应头”里找 `X-Trace-Id`；
2. 或在平台“基础设施 > API 日志 > 错误日志”（和“访问日志”）里按时间、接口找到那条记录，列表里有链路追踪编号；
3. “系统管理 > 审计日志 > 操作日志 / 登录日志”里也有。

**查日志**：

```bash
sudo nusctl logs backend --since 24h --trace-id <trace-id>
# 超出容器日志范围时查文件（含完整堆栈，用 -A 多看几行）
sudo sh -c 'zgrep -h -A 30 "traceId=<trace-id>" /srv/nus/logs/backend/nus-server.log*'
```

**查链路**：在 SkyWalking 里用同一个 trace-id 搜索，可以看到这个请求调用了哪些 SQL、各花了多少时间（见 7.3）。

### 7.3 SkyWalking 与其他监控

平台自带的监控入口都在“**基础设施 > 监控中心**”下，需要 `infra:monitor:access` 权限（超级管理员默认有），从菜单点进去不用再登录：

| 菜单 | 看什么 |
| --- | --- |
| 链路追踪 | SkyWalking：接口耗时、慢请求、按 trace-id 搜索链路。数据保留：明细 7 天、指标 15 天（`.env` 的 `NUS_SKYWALKING_RECORD_TTL_DAYS`、`NUS_SKYWALKING_METRICS_TTL_DAYS`） |
| SQL 与连接池监控 | Druid：慢 SQL（超过 500 ms 记为慢）、连接池使用 |
| Java 监控 | Spring Boot Admin：JVM 内存、线程、健康 |
| Redis 监控 | Redis 内存、键数量 |

SkyWalking 页面走 8082 端口（`<监控地址>`，即 `.env` 的 `NUS_SKYWALKING_URL`），未登录平台或没有权限的人打不开。

**监控相关命令**：

```bash
sudo nusctl monitor-status        # ES、OAP、UI、后端的状态 + ES 集群健康
sudo nusctl monitor-restart       # 依次重启 ES、OAP、UI 并等健康（不影响平台业务）
sudo nusctl monitor-credentials   # 打印 SkyWalking 页面的内部应急账号和口令
```

- `monitor-credentials` 只在“从平台菜单进不去 SkyWalking”的应急排查时用。**输出含口令，不要截图、不要贴到聊天里。**
- 监控服务全部停掉也不影响师生使用平台。

## 8. 账号与安全

### 8.1 管理员忘记密码

**首选**：请另一位管理员在“**系统管理 > 用户管理**”里找到该账号，点“更多 > 重置密码”（需要 `system:user:update-password` 权限，超级管理员默认有）。重置后本人登录，在个人中心再改成自己的密码。

**所有管理员都登录不了时**：现有脚本**没有**重置管理员密码的命令（待开发：`nusctl reset-admin-password`）。安装时的 bootstrap 只能用一次（2.3），不能再用。只能用下面的**应急手动方法**，它直接改线上数据库，属于红线操作：**必须经指导老师同意、先备份、先在测试服务器上走一遍**（这个方法尚未在测试服务器演练）。

```bash
sudo nusctl backup
# 1. 在后端容器里用 Python 生成 bcrypt 哈希（输入新密码，屏幕不显示）
nus_compose exec backend python3 -c 'import crypt,getpass; print(crypt.crypt(getpass.getpass("新密码: "), crypt.mksalt(crypt.METHOD_BLOWFISH, rounds=4096)))'
# 输出形如 $2b$12$...... 的一行，复制它
# 2. 先确认账号存在
echo "SELECT id, username, status FROM system_users WHERE username = 'admin' AND deleted = 0;" | nus_sql
# 3. 写入新哈希（把 <哈希> 换成上一步的输出，注意整串放在单引号里）
nus_sql <<'SQL'
UPDATE system_users SET password = '<哈希>' WHERE username = 'admin' AND deleted = 0;
SQL
```

然后用新密码登录验证，并在运维记录里写明原因、时间、执行人、指导老师的同意。

### 8.2 新增管理员

1. 用超级管理员登录，进入“**系统管理 > 用户管理**”，点“新增”，填写账号、姓名、初始密码；
2. 在该用户行点“更多 > 分配角色”，按职责选：
   - `超级管理员`（super_admin）：全部权限，只给少数人；
   - `学校教务管理员`（school_admin）：全校教务，含公共课审批；
   - `学院教务管理员`（college_admin）：本学院范围；
3. 请对方登录后自己修改密码。

账号停用（例如人员离开）在同一页面把“状态”改为停用，不要直接删除账号（删除会影响历史记录的显示）。

### 8.3 更换数据库、Redis 口令（手动方法）

**现状**：现有脚本**没有**更换口令的命令（待开发）。下面的方法**尚未在测试服务器演练，必须先在测试服务器上走一遍**，再在正式环境的维护时段执行，并提前通知指导老师。

**什么时候做**：口令可能泄露时（例如曾经出现在聊天记录、截图里）；人员交接时按指导老师要求。

**注意事项**：

- `NUS_MYBATIS_ENCRYPTOR_PASSWORD`、`NUS_API_ENCRYPT_*` **不要换**：换了以后已保存的 AI 密钥解不开。
- 换口令之后，旧的 `.env.before-*` 里仍是旧口令。之后如果要回滚，需要先把恢复用的 `.env` 里的口令改成新的，否则后端连不上（见 5.6）。数据库备份里不含 MySQL 账号，恢复备份不会把口令改回去。

**更换业务账号 `nus` 的口令**（`NUS_DB_PASSWORD`）：

```bash
sudo nusctl backup
sudo cp -p /srv/nus/config/.env /srv/nus/config/.env.before-dbpass-$(date -u +%Y%m%dT%H%M%SZ)
sudo -i                                   # 以下在 root shell 里执行；先重新粘贴 0.3 的两个函数
nus_compose stop frontend backend         # 停机开始
NUS_NEW=$(openssl rand -hex 24)
nus_sql <<SQL
ALTER USER 'nus'@'%' IDENTIFIED BY '$NUS_NEW';
SQL
umask 077
NUS_NEW="$NUS_NEW" awk 'index($0, "NUS_DB_PASSWORD=") == 1 { print "NUS_DB_PASSWORD=" ENVIRON["NUS_NEW"]; next } { print }' \
  /srv/nus/config/.env > /srv/nus/config/.env.new
cat /srv/nus/config/.env.new > /srv/nus/config/.env && rm -f /srv/nus/config/.env.new
unset NUS_NEW
nusctl start                              # 后端以新口令重建，前端在后端健康后启动
nusctl status
exit
```

**更换 Redis 口令**（`NUS_REDIS_PASSWORD`）：与上面相同，但不需要 `ALTER USER`：停前后端后，把 `.env` 里 `NUS_REDIS_PASSWORD=` 一行换成新值（同样用 `awk` 方法），然后 `nusctl start`（Redis 和后端都会以新口令重建）。

**更换 MySQL root 口令**（`NUS_DB_ROOT_PASSWORD`）：需要 `ALTER USER 'root'@'%' ...` 和 `ALTER USER 'root'@'localhost' ...` 两条，再改 `.env`，然后 `nusctl stop` 再 `nusctl start` 让 MySQL 容器以新口令重建（容器的健康检查用的是这个口令）。改完 `.env` 到 MySQL 重建之前，`nus_sql` 会因为口令不匹配而失败，这是预期的。

**怎么确认成功**：`sudo nusctl status` 全部 healthy；能登录平台；`sudo nusctl backup` 能成功（验证 root 口令）。

**失败怎么办**：后端起不来、日志里有 `Access denied`：说明数据库里的口令和 `.env` 不一致。用刚保存的 `.env.before-dbpass-*` 里的旧口令再执行一次 `ALTER USER` 改回去，恢复 `.env`，再 `nusctl start`。

### 8.4 更换 AI 平台的 API 密钥

**在平台界面里改，不涉及服务器。** 位置（从 `NUS-backend` 的 AI 模块和菜单数据核实）：

1. “**AI 大模型 > 控制台 > API 密钥**”：每个模型平台一条记录，字段有所属平台、名称、密钥、自定义 API URL、状态。点“编辑”，把“密钥”换成新的，保存。
2. “**AI 大模型 > 控制台 > 模型配置**”：列表里每个模型选用了哪个 API 密钥；点模型行的“测试”按钮，确认能连通。页面上方的“业务模型绑定”决定 AI 初评、AI 出题等各项业务用哪个模型，改了要点“保存全部”。
3. 用量和失败情况看“**AI 大模型 > 控制台 > 调用日志**”。

说明：

- 密钥在数据库里加密保存（加密密钥就是 `.env` 的 `NUS_MYBATIS_ENCRYPTOR_PASSWORD`）。
- 外部 AI 需要服务器能访问模型平台的地址。“教育 AI 外发学生数据”和“自动初评”由 `.env` 的 `NUS_AI_EXTERNAL_STUDENT_DATA_ENABLED`、`NUS_AI_REVIEW_ENABLED` 控制，默认开启，使用前确认学校的数据合规要求。改这两项需要编辑 `.env` 后 `sudo nusctl stop` 再 `sudo nusctl start`。
- 费用控制参数（每日令牌上限、每人每日调用次数）在“基础设施 > 配置管理”（参数配置）里，参数名见 V1.0.1.7 版本说明第十节。

### 8.5 离职交接：清除公共课认领

公共课由教师“认领”班级（V1.0.1.10 起）。老师离职或不再教这门课时，要把他认领的班级释放出来，让接手的老师认领。

**界面操作**（管理员或公共课审批人可以清除任一班级的认领）：

1. 进入“**能力培养 > 实训课程 > 实训课程管理**”，打开那门公共课的课程详情；
2. 在“班级”页按“负责人”筛选出离职的老师；
3. 每一行点“清除认领”并确认。已布置的任务仍归原布置者，不会删除。

现有界面**只能逐行清除**，没有按老师批量清除（待开发）。先用下面的只读 SQL 列出他认领的全部班级，再逐个处理：

```bash
nus_sql <<'SQL'
SELECT c.course_name AS 课程, cl.class_name AS 班级, cc.semester_name AS 学期, cc.claim_time AS 认领时间
FROM edu_class_course cc
JOIN capacity_course c ON c.id = cc.course_id AND c.deleted = 0
JOIN edu_class cl ON cl.id = cc.class_id AND cl.deleted = 0
WHERE cc.deleted = 0
  AND cc.claim_teacher_id = (SELECT id FROM system_users WHERE username = '<教师账号>' AND deleted = 0)
ORDER BY cc.semester_name DESC, c.course_name;
SQL
```

**其他交接事项**：

- 在“系统管理 > 用户管理”里把离职账号**停用**；
- 他负责的专属课程、课程团队成员如何移交，由教务和指导老师决定（**待确认**移交的界面操作）；
- 负责服务器的同学交接时：更换服务器登录口令/密钥，按指导老师要求考虑是否更换数据库口令（8.3）；把运维记录、备份位置、`admin` 口令的保管方式交给下一位。

## 9. 学期操作

学期相关的界面操作通常由教务管理员做，运维负责提前备份和事后检查。

### 9.1 学期切换

**位置**：“**教务组织 > 学期管理**”。

**两种方式**（从 `EduSemesterServiceImpl` 核实）：

| 方式 | 规则 |
| --- | --- |
| 自动更新（默认开启） | 每年 **2 月 1 日**切到“`<上一年>-<当年>` 下学期”（2 月 1 日～7 月 31 日），**8 月 1 日**切到“`<当年>-<下一年>` 上学期”（8 月 1 日～次年 1 月 31 日）。由定时任务“当前学期自动更新”每天 00:05 检查，后端每次启动时也会检查一次 |
| 手动设置 | 关闭自动更新后，填学年、学期和起止日期，保存后立即生效。**手动保存会自动关闭自动更新** |

切换后，后台会自动做公共课同步（通常几分钟内完成）：为当前学期建立公共课与班级的关联，给新班级补发未截止的公共课任务；上学期系统自动建立、且没有进行中任务的公共课关联会被封存（可恢复）。相关参数：`edu.public-course.archive-previous-semester`、`edu.public-course.backfill-enabled`。

**运维要做的**：

1. 切换前一天 `sudo nusctl backup`，三份备份照常一起异地保存（配置加密）；
2. **确认服务器时间正确**（第 11 章）：自动切换按服务器日期判断；
3. 切换后检查：页面顶部栏显示的学期；“基础设施 > 定时任务”里“当前学期自动更新”“公共课班级同步”的调度日志为成功；`sudo nusctl logs backend --since 1h --error` 没有同步相关的错误。

### 9.2 学期收尾封存

**什么时候做**：学期结束、成绩全部确认之后，新学期开始之前。

**位置**：“教务组织 > 学期管理”页面上的“**学期收尾**”。向导会列出所选学期还在用的班课、进行中的任务、待批改的提交和公共课关联；勾选后批量**封存**。

- 封存后只读：不能修改、批改，学生待办里不再出现；**可以随时恢复**；
- 封存的数据**照常计入**合格率、成绩趋势、课程分析、学生排名（V1.0.1.10 起）；
- 还有“待批改”的提交时，先请老师批完再封存。

**运维要做的**：封存前做一次完整备份（数据库 + 附件 + 配置），并在异地留一份“学期末备份”长期保存（4.4 保留策略）。

### 9.3 公共课每学期重新认领

认领按学期分开：**新学期开始后，教师要在公共课的课程详情里重新“认领班级”**，上学期的认领不会自动带过来。

- 教务可以在课程详情的“班级”页按负责人筛选“未认领”，提醒老师认领；
- 下面的只读 SQL 列出当前学期还没人认领的公共课班级：

```bash
nus_sql <<'SQL'
SELECT c.course_name AS 公共课, cl.class_name AS 班级, cc.semester_name AS 学期
FROM edu_class_course cc
JOIN capacity_course c ON c.id = cc.course_id AND c.deleted = 0 AND c.is_public_course = 0
JOIN edu_class cl ON cl.id = cc.class_id AND cl.deleted = 0
WHERE cc.deleted = 0 AND cc.status = 0 AND cc.claim_teacher_id IS NULL
  AND cc.semester_name = (SELECT value FROM infra_config WHERE config_key = 'edu.current.semester.name' AND deleted = 0)
ORDER BY c.course_name, cl.class_name;
SQL
```

（`capacity_course.is_public_course` 的取值是 `0` 表示公共课，与直觉相反，以代码为准。）

## 10. 磁盘与旧版本清理

### 10.1 空间都花在哪里

先看清楚再删：

```bash
df -h /srv/nus /var/lib/docker
sudo du -sh /srv/nus/data/* /srv/nus/backups /srv/nus/logs /srv/nus/releases 2>/dev/null
sudo docker system df
du -sh ~/nus-update-* ~/nus-offline-* 2>/dev/null
```

关于“每个版本约 150 MB”，核实脚本后的结论：

- **`/srv/nus/releases/<版本>/` 很小**：只有脚本、`release.env`、Compose 文件、迁移 SQL、更新说明（`activate_release` 只复制这些），每版通常不到 1 MB；
- 约 150 MB 的是**升级包本身**：`.tar.gz` 约 145 MB，解压后目录约 170 MB，通常放在运维账号的家目录；
- 每次增量升级还会在 Docker 里新增一层**镜像层**（新的后端 jar 约 160 MB + 前端 dist）。增量包是在当前镜像之上构建新镜像（`BASE_IMAGE` 为当前镜像），新旧镜像层层叠加，**删掉旧镜像的标签只能释放很少的空间**，因为新镜像还在引用这些层。实际占用以 `sudo docker system df` 为准（**待确认**：在学校服务器上实测）。

### 10.2 安全清理的原则

**必须保留**：

- 当前版本和**上一个版本**的：`/srv/nus/releases/<版本>/`、`nus-backend` / `nus-front` 镜像、升级时的数据库备份、`.env.before-<版本>-*`。少了任何一样都不能回滚；
- 所有非业务镜像：`mysql`、`redis`、`flyway`、`elasticsearch`、`skywalking-oap-server`、`skywalking-horizon-ui`。**Flyway 镜像平时没有容器在用，但每次升级都要用，服务器离线，删了就没法升级。**

**绝对不要执行**：`docker system prune -a`、`docker image prune -a`（会删掉 Flyway 镜像和回滚要用的旧镜像）、删除 `/srv/nus/data` 下的任何东西。

### 10.3 清理步骤

**什么时候做**：磁盘使用率超过 80%；或每次升级稳定运行两周以后。先 `sudo nusctl backup`。

**1. 旧的升级包目录**（只保留最近两个版本的）：

```bash
ls -d ~/nus-update-*
rm -rf ~/nus-update-<旧版本号>-ubuntu24.04-amd64 ~/nus-update-<旧版本号>-ubuntu24.04-amd64.tar.gz*
```

**2. 旧的发布目录**（保留当前和上一个）：

```bash
readlink /srv/nus/current                       # 当前版本
ls /srv/nus/releases
sudo rm -rf /srv/nus/releases/<更早的版本号>
```

**3. 旧镜像标签和构建缓存**：

```bash
sudo docker image ls --format '{{.Repository}}:{{.Tag}}  {{.ID}}  {{.CreatedSince}}  {{.Size}}' | grep -E '^nus-(backend|front):'
sudo docker image rm nus-backend:<更早的版本号> nus-front:<更早的版本号>    # 不要删当前和上一个
sudo docker image prune -f        # 只删没有标签的悬空镜像，安全
sudo docker builder prune -f      # 删除增量升级时留下的构建缓存，安全
sudo docker system df
```

正在被容器使用或被其他镜像依赖的镜像，`docker image rm` 会报错拒绝，这是正常的保护。

**4. 旧的数据库备份**：每日备份由 4.4 的脚本自动清理。升级时的备份要手动清：先看哪些备份被升级记录引用：

```bash
sudo grep -H '^DB_BACKUP=\|^TO_RELEASE=\|^STATUS=' /srv/nus/upgrades/*.env
```

确认某次升级对应的版本已经不需要回滚（比当前版本早两个以上），并且**异地已有副本**后再删：

```bash
sudo rm -f /srv/nus/backups/db-nus-<时间>.sql.gz /srv/nus/backups/db-nus-<时间>.sql.gz.sha256
```

**5. 旧的 `.env` 备份**：`/srv/nus/config/.env.before-*` 很小，保留当前和上一个版本相关的即可；**删之前确认异地有加密的 `.env`**。

**6. 系统日志**：

```bash
journalctl --disk-usage
sudo journalctl --vacuum-size=500M
```

**怎么确认成功**：`df -h` 使用率下降；`sudo nusctl status` 全部 healthy；`ls /srv/nus/releases` 至少还有当前和上一个版本。

## 11. 时间与时区

截止时间判断、截止前提醒（每小时）、教师新提交汇总（每 10 分钟）、学期自动切换（按日期）、AI 初评排队超时、登录令牌过期，**全都依赖服务器的时钟**。所有容器共用宿主机的时钟。

### 11.1 现状（已从镜像和配置核实）

- 后端镜像设置了 `TZ=Asia/Shanghai`，数据库连接用 `serverTimezone=Asia/Shanghai`；MySQL 容器 `TZ` 默认 `Asia/Shanghai`。所以**平台内部按北京时间工作，与宿主机时区设置无关**。
- 宿主机时区影响的是：你看 `date` 的结果、`/etc/cron.d` 定时任务的执行时间。建议也设为北京时间，避免混淆。
- 备份文件名、升级日志和升级记录里的时间都是 **UTC**（带 `Z` 后缀），比北京时间早 8 小时。

### 11.2 检查

```bash
timedatectl                    # Time zone、System clock synchronized: yes、NTP service: active
nus_compose exec backend date  # 后端容器里的时间，应是北京时间（CST）
echo "SELECT NOW() AS 数据库时间, @@global.time_zone, @@system_time_zone;" | nus_sql
```

三处时间和你手机上的北京时间相差应在几秒之内。

### 11.3 设置时区和时间同步

```bash
sudo timedatectl set-timezone Asia/Shanghai
timedatectl show-timesync --all 2>/dev/null | head    # Ubuntu 24.04 默认用 systemd-timesyncd
```

学校内网通常不能访问公网时间服务器，需要向学校网络管理员要一个**内网 NTP 服务器地址**，写进配置：

```bash
sudo vi /etc/systemd/timesyncd.conf        # 在 [Time] 下写：NTP=<学校NTP服务器>
sudo systemctl restart systemd-timesyncd
timedatectl timesync-status                # 能看到 Server 和 Offset
```

（如果服务器装的是 chrony，则改 `/etc/chrony/chrony.conf` 并重启 `chrony`。）

**时间偏差较大时**（超过几分钟）：同步后在低峰时段执行 `sudo nusctl stop` 再 `sudo nusctl start`，让定时任务按正确时间重新排程。之后检查“基础设施 > 定时任务”的调度日志。时间错误期间可能已经误判的截止、提醒，见[故障排查](故障排查.md)“时间不对”一节。

## 12. 红线

这些规则没有例外。拿不准的时候，**停下来问指导老师**。

1. **e2e、性能测试脚本严禁对线上跑。** `deploy/tests/` 下的脚本（`e2e_v*.py`、`perf/` 下的造数和压测）会创建大量账号、课程、任务和提交，还会放大历史数据。它们只接受 `127.0.0.1` / `localhost`，**不要改掉这个限制，也不要用端口转发把线上服务器“变成” localhost**。
2. **不要直接改线上数据库。** 数据有问题，先用 `SELECT` 查清楚，交给开发方用迁移（Flyway）或界面功能修复。`nus_sql` 只用来执行 `SELECT`。本手册里少数例外（8.1 应急重置密码、8.3 改口令）必须经指导老师同意、先备份、先记录。
3. **任何线上操作先记录、先备份。** 记录写：时间、执行人、要做什么、为什么、执行的命令、结果。改动前 `sudo nusctl backup`。
4. **正式环境原则上不回滚**（5.6）。
5. **不要删除或重新生成 `.env`，尤其是 `NUS_MYBATIS_ENCRYPTOR_PASSWORD`**；不要删除 `/srv/nus` 或其中的 `data/`；不要用“重装”解决普通故障。
6. **不要执行不带参数的 `docker compose up -d`、`docker system prune -a`、`docker image prune -a`**（0.3、10.2）。
7. **不要修改已发布的迁移文件**，也不要在线上执行 `flyway repair`、`flyway clean`（`clean` 会清空数据库）。
8. **口令、密钥、`.env` 内容、`monitor-credentials` 的输出、真实 IP 和师生个人信息**，不发群聊、不贴进 Issue、不截图、不写进文档、不交给不受信任的 AI 服务。
9. 同一个版本号不能装两次。重新打的包必须用新版本号（例如 V1.0.1.8 之后的修正包叫 V1.0.1.8.1）。

## 附录 A：`nusctl` 子命令速查表

全部需要 `sudo`。来源：`deploy/offline/nusctl`。

| 命令 | 作用 | 备注 |
| --- | --- | --- |
| `nusctl` 或 `nusctl status` | 各服务状态（`docker compose ps`） | |
| `nusctl start` | 启动全部服务（`docker compose up -d`） | 配置变了的容器会被重建；前端等后端健康后才启动 |
| `nusctl stop` | 停止全部服务（含 MySQL） | |
| `nusctl restart` | 重启全部服务（`docker compose restart`） | 不等健康检查；之后若出现 502，用 `nusctl stop` + `nusctl start` |
| `nusctl doctor` | 综合体检 | 见 3.2 |
| `nusctl logs [服务] [--follow\|-f] [--since 时间] [--error] [--trace-id ID]` | 看日志，默认 `backend` | 见 7.1 |
| `nusctl backup [--db-only]` | 默认备份数据库、附件包、`.env` 到 `/srv/nus/backups/`，汇总路径和大小 | 不停服务；`--db-only` 只备份数据库并输出路径；配置含密钥，异地须加密 |
| `nusctl restore 文件 [--yes] [--no-safety-backup]` | 用备份**整体替换**数据库 | 先做安全备份；停前后端；见 4.7 |
| `nusctl rollback previous\|版本号 [--backup 文件] [--env 文件] [--yes] [--no-safety-backup]` | 回到已安装的旧版本，连同数据库 | **丢失升级后的数据**；见 5.6 |
| `nusctl monitor-status` | 监控服务状态与 ES 健康 | |
| `nusctl monitor-restart` | 依次重启 ES、OAP、UI | 不影响业务 |

## 附录 B：`.env` 配置项说明

位置 `/srv/nus/config/.env`，权限 0600。来源：`install.sh`（生成）、`upgrade.sh` 和 `lib/common.sh`（补齐）、`compose.yaml`（读取）。**这里只写含义，不写值。** 改了 `.env` 后要 `sudo nusctl stop` 再 `sudo nusctl start` 才生效。

**部署与镜像**

| 变量 | 含义 | 能否改 |
| --- | --- | --- |
| `DATA_ROOT`、`CONFIG_ROOT` | 数据目录 `/srv/nus`、配置目录 `/srv/nus/config` | 不要改（域名脚本只支持默认目录） |
| `COMPOSE_PROJECT_NAME` | Compose 项目名 `nus` | 不要改 |
| `BACKEND_IMAGE`、`FRONTEND_IMAGE` | 当前前后端镜像标签 | 由升级脚本写，不要手改 |
| `MYSQL_IMAGE`、`REDIS_IMAGE`、`FLYWAY_IMAGE`、`ELASTICSEARCH_IMAGE`、`SKYWALKING_OAP_IMAGE`、`SKYWALKING_UI_IMAGE` | 基础镜像标签 | 由安装/升级脚本写，不要手改 |
| `NUS_SITE_URL` | 平台访问地址 | 用 `configure-domain.sh` 改，不要手改 |
| `HTTP_PORT` | 平台对外端口，默认 80（默认不出现在 `.env` 里） | 一般不改 |

**数据库与 Redis**

| 变量 | 含义 | 能否改 |
| --- | --- | --- |
| `NUS_DB_NAME` | 数据库名 `nus` | 不要改 |
| `NUS_DB_USERNAME`、`NUS_DB_PASSWORD` | 后端连库的业务账号和口令 | 口令按 8.3 改 |
| `NUS_DB_ROOT_PASSWORD` | MySQL root 口令（备份、恢复、升级用） | 按 8.3 改 |
| `NUS_REDIS_PASSWORD` | Redis 口令 | 按 8.3 改 |

**密钥（绝对不要改）**

| 变量 | 含义 |
| --- | --- |
| `NUS_MYBATIS_ENCRYPTOR_PASSWORD` | 数据库里敏感字段（如 AI API 密钥）的加密密钥。改了或丢了，已保存的密钥全部解不开 |
| `NUS_API_ENCRYPT_REQUEST_KEY`、`NUS_API_ENCRYPT_RESPONSE_KEY` | 接口加密密钥（当前未启用接口加密，但要保留） |

**监控**

| 变量 | 含义 |
| --- | --- |
| `NUS_MONITOR_USERNAME`、`NUS_MONITOR_PASSWORD` | 监控内部账号（SkyWalking 页面、Java 监控），`monitor-credentials` 打印的就是它 |
| `NUS_HORIZON_AUTH_LOCAL_USERS` | 由监控口令生成的 SkyWalking 页面登录配置（含口令哈希），不要手改 |
| `NUS_MONITOR_COOKIE_SECURE` | 监控 Cookie 是否只走 HTTPS；站点是 https 时自动为 true |
| `NUS_MONITOR_TICKET_TTL`、`NUS_MONITOR_SESSION_TTL` | 从平台菜单进入监控的票据、会话有效期 |
| `NUS_DRUID_ENABLED`、`NUS_DRUID_ALLOW` | 是否启用 SQL 监控（Druid）及允许访问的内部地址段 |
| `NUS_SPRING_BOOT_ADMIN_ENABLED` | 是否启用 Java 监控 |
| `NUS_SKYWALKING_ENABLED` | 后端是否挂载 SkyWalking Agent |
| `NUS_SKYWALKING_SERVICE_NAME` | 在 SkyWalking 里显示的服务名 |
| `NUS_SKYWALKING_SAMPLE_N_PER_3_SECS` | 链路采样率（每 3 秒最多采多少条） |
| `NUS_SKYWALKING_RECORD_TTL_DAYS`、`NUS_SKYWALKING_METRICS_TTL_DAYS` | 链路明细、指标的保留天数 |
| `NUS_SKYWALKING_UI_PORT` | SkyWalking 页面的宿主机端口，默认 8082 |
| `NUS_SKYWALKING_URL` | SkyWalking 页面的访问地址（平台菜单跳转用） |

**AI**

| 变量 | 含义 |
| --- | --- |
| `NUS_AI_EXTERNAL_STUDENT_DATA_ENABLED` | 是否允许把学生提交内容发给外部模型（关掉后 AI 初评等教育 AI 功能不可用） |
| `NUS_AI_REVIEW_ENABLED` | 是否启用自动 AI 初评 |
| `NUS_AI_MAX_CONCURRENT` | 同时调用模型的最大数量 |
| `NUS_AI_CALL_TIMEOUT`、`NUS_AI_CONNECT_TIMEOUT` | 单次调用等待响应、建立连接的超时 |
| `NUS_AI_REVIEW_TASK_POOL_SIZE`、`NUS_AI_REVIEW_TASK_QUEUE_CAPACITY` | AI 初评后台线程数、队列长度 |

**只在执行命令时临时给、不写进 `.env` 的变量**

| 变量 | 用在 | 含义 |
| --- | --- | --- |
| `NUS_ADMIN_PASSWORD_FILE` | `install.sh` | 无人值守安装的管理员口令文件（0600） |
| `NUS_SKYWALKING_URL`、`NUS_SKYWALKING_UI_PORT` | `install.sh` | 首次安装时指定监控地址、端口 |
| `NUS_UPGRADE_MIN_FREE_MB` | `upgrade.sh` | 升级要求的最小剩余空间（MiB），默认 2048 |
| `NUS_BACKEND_HEALTH_ATTEMPTS`、`NUS_HEALTH_POLL_SECONDS` | 升级、恢复、回滚 | 等后端健康的次数（默认 90）和间隔秒数（默认 2） |

`NUS_ADMIN_BOOTSTRAP_*` 只在安装时一次性使用，安装脚本会主动从 `.env` 里删掉，**不要加进 `.env`**。
