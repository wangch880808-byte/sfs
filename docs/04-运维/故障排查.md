# 师砺平台故障排查

> 面向：负责学校服务器的同学，以及协助他们的 AI 智能体。
> 适用版本：V1.0.1.10（Flyway 21）。
> 最后核对：2026-10-14。检查命令已对照 `deploy/` 下的脚本、`compose.yaml` 和后端代码核实。

日常操作（安装、备份、升级、回滚）见 [运维手册](运维手册.md)，本文只讲“出了问题怎么查”。

## 开始之前

1. **先保留现场，再动手。** 记下：什么时候开始、谁反映的、影响多少人、具体页面和报错文字、截图、trace-id（运维手册 7.2）。
2. 下面很多检查要用两个辅助函数 `nus_compose` 和 `nus_sql`，**先按 [运维手册 0.3](运维手册.md#03-两个辅助函数) 把它们粘贴到终端里**。`nus_sql` 只执行 `SELECT`。
3. 每一节按“**现象 → 先看什么 → 可能原因 → 处理**”排列。命令都在服务器上执行。
4. 处理涉及停服务、恢复数据、改配置时，先告诉指导老师，先 `sudo nusctl backup`（运维手册第 12 章“红线”）。
5. **不要用这些办法“修”问题**：删除 `/srv/nus` 或其中的目录、重新生成 `.env`、重新安装、执行不带参数的 `docker compose up -d`、`docker system prune -a`、在线上 `flyway repair` / `flyway clean`、直接 `UPDATE` 数据库。

**任何问题的第一步**：

```bash
sudo nusctl status
sudo nusctl doctor
sudo nusctl logs backend --since 30m --error
df -h /srv/nus /var/lib/docker
```

## 1. 页面打不开

**现象**：浏览器显示“无法访问此网站”、一直转圈、502 Bad Gateway、504 Gateway Timeout；或者页面能打开但每个操作都报错。

**先看什么**：

```bash
sudo nusctl status                                                      # frontend、backend 是否 healthy
curl --noproxy '*' -fsS http://127.0.0.1/nginx-health                   # 服务器本机能否访问前端，应输出 ok
curl --noproxy '*' -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/                                   # 首页，应为 200
curl --noproxy '*' -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/admin-api/system/auth/social-login-config  # 后端，应为 200
sudo ss -ltnp | grep -E ':(80|8082) '                                   # 80 端口有没有在监听
sudo nusctl logs frontend --since 15m | tail -n 30                      # 看请求返回的状态码
sudo nusctl logs backend --since 15m --error
```

**可能原因与处理**：

| 判断 | 可能原因 | 处理 |
| --- | --- | --- |
| 本机 `nginx-health` 不通，`frontend` 不是 Up | 前端容器停了或起不来 | `sudo nusctl start`；还不行看 `sudo nusctl logs frontend --since 30m` |
| 本机 `nginx-health` 正常，但校园网里打不开 | 服务器防火墙、学校网关、网络问题 | `sudo ufw status`；从服务器所在网段另一台机器试 `curl http://<服务器内网地址>/nginx-health`；联系学校网络管理员。**不要自己改学校网关或防火墙** |
| 用域名打不开、用 `http://<服务器内网地址>` 能打开 | 学校网关、DNS、证书问题 | 联系学校网络管理员，提供时间和现象 |
| 首页 200，但后端接口 502 | 后端没有健康，或后端重启后前端还连着旧地址 | 看 `nusctl status` 里 backend；backend 是 healthy 时执行 `nus_compose up -d --force-recreate frontend`（Nginx 只在启动时解析一次后端地址） |
| `backend` 一直 `health: starting` 或 `unhealthy` | 后端启动失败 | 看 `sudo nusctl logs backend --since 30m`（不加 `--error`，看完整启动过程）；常见是连不上 MySQL/Redis（见第 7、8 节）、内存不足、磁盘满 |
| 504、页面很慢 | 后端负载高、慢 SQL、AI 调用卡住 | `sudo docker stats --no-stream`；平台“基础设施 > 监控中心 > SQL 与连接池监控”看慢 SQL；SkyWalking 看慢请求 |
| 刚执行过 `nusctl restart` 后出现 502 | `restart` 不等健康检查，前端可能先于后端起来 | `sudo nusctl stop` 后 `sudo nusctl start`（`start` 会等后端健康再启动前端） |
| 升级时间段内打不开 | 升级停机期间前端也是停的 | 这是预期，看升级终端的输出 |

## 2. 登录失败

**现象**：提示账号或密码不正确、验证码错误、账号被停用；登录后马上又回到登录页；学生登录后只能改密码。

**先看什么**：

```bash
# 最近的登录记录：result 0 成功、10 账号或密码不正确、20 用户被停用、30 验证码不存在、31 验证码不正确
nus_sql <<'SQL'
SELECT username, result, create_time, trace_id FROM system_login_log ORDER BY id DESC LIMIT 20;
SQL
# 账号状态：status 0 正常、1 停用
nus_sql <<'SQL'
SELECT id, username, status, deleted, update_time FROM system_users WHERE username = '<账号>';
SQL
sudo nusctl status                                       # redis 是否 healthy
sudo nusctl logs backend --since 30m --error | grep -i -E 'redis|captcha|auth' | tail -n 20
```

平台界面里也能看：“系统管理 > 审计日志 > 登录日志”。

**可能原因与处理**：

| 判断 | 可能原因 | 处理 |
| --- | --- | --- |
| `result = 10` | 密码错误 | 管理员在“系统管理 > 用户管理”里“重置密码”。管理员自己忘了见运维手册 8.1 |
| `result = 20` 或 `status = 1` | 账号被停用 | 确认是否应启用，在“用户管理”里改状态 |
| 查不到这个账号，或 `deleted = 1` | 账号不存在或已删除 | 确认账号名；需要时重新建账号 |
| `result = 30/31`，很多人同时出现 | 验证码依赖 Redis，Redis 有问题 | 见第 8 节 |
| `result = 30/31`，个别人 | 输入错误、页面停留太久验证码过期 | 刷新验证码重试 |
| 学生登录后只能看到改密码页面 | 学生首次登录必须改密码，这是设计行为 | 让学生按提示修改 |
| 登录成功后又跳回登录页 / 接口返回“账号未登录” | 登录状态没写进 Redis；浏览器拦截了 Cookie；服务器时间严重不准导致令牌立即过期 | 查第 8 节 Redis；查第 11 节时间；换浏览器试 |
| 刚升级完，菜单缺失或没有权限 | 浏览器里还是旧的登录信息 | 退出后重新登录（版本说明里常有这一条） |
| 用域名登录失败、内网地址正常 | 网关转发或域名配置问题 | 见第 12 节“域名切换后” |

## 3. 上传失败

**现象**：上传附件、图片、课程资源时报错、进度条卡住，或上传成功但打不开。

**先看什么**：

```bash
df -h /srv/nus                                                          # 磁盘是否满
sudo stat -c '%u:%g %a %n' /srv/nus/data/uploads /srv/nus/data/tmp      # 属主应为 10001:10001
sudo nusctl logs frontend --since 30m | grep -E '" (413|500|502|504) ' | tail -n 20   # 413 是请求太大
sudo nusctl logs backend --since 30m --error | tail -n 30
# 文件存储配置：storage 10 表示本机磁盘，basePath 应为 /app/uploads，domain 应为站点地址
nus_sql <<'SQL'
SELECT id, name, storage, master,
       JSON_UNQUOTE(JSON_EXTRACT(config, '$.basePath')) AS basePath,
       JSON_UNQUOTE(JSON_EXTRACT(config, '$.domain')) AS domain
FROM infra_file_config WHERE deleted = 0;
SQL
# 附件数量和大小限制（任务提交）
nus_sql <<'SQL'
SELECT config_key, value FROM infra_config WHERE config_key LIKE 'edu.homework.attachment.%' AND deleted = 0;
SQL
```

**可能原因与处理**：

| 判断 | 可能原因 | 处理 |
| --- | --- | --- |
| 页面提示文件太大、类型不对、个数超限 | 超出参数限制（默认 10 个、单个 100 MB、合计 300 MB） | 按页面提示处理；需要放宽时由管理员在“基础设施 > 配置管理”改 `edu.homework.attachment.*` |
| 前端日志有 413 | 超过平台 Nginx 上限（520 MB）或后端单文件上限（500 MB） | 这是平台上限，不能在服务器上随手改，联系开发方 |
| 内网上传正常、走域名上传大文件失败 | 学校网关限制了请求体大小或超时 | 请学校网络管理员调大（运维手册 2.4 的表格） |
| 磁盘使用率 100% | 磁盘满 | 见第 6 节 |
| 属主不是 `10001:10001` | 目录权限被改过（例如手动恢复附件后） | `sudo chown -R 10001:10001 /srv/nus/data/uploads /srv/nus/data/tmp` |
| 上传成功但链接打不开，链接里的地址不是当前站点 | 文件配置的 `domain` 不对，常见于切换域名或从备份恢复之后 | 不要手改数据库。切换域名用 `configure-domain.sh`（运维手册 2.4）；恢复备份后出现的，联系指导老师 |
| 旧附件打不开、新附件正常 | 文件本身不在 `/srv/nus/data/uploads/` 里（恢复了数据库但没恢复附件） | 按完整备份中的 `files-*.tar.gz` 恢复（运维手册 4.3：停后端、目录留底、解包、核对数量后再启动） |

## 4. AI 初评一直排队或失败

**现象**：学生提交后，AI 初评一直显示排队中或处理中；或显示“AI 初评没有完成”；老师收到初评失败通知。

**背景**：提交成功后，初评先在数据库里排队，后台每 15 秒扫描一次（参数 `edu.ai-review.dispatch-interval-seconds`），排队超过 120 分钟（`edu.ai-review.queue-timeout-minutes`）判为失败。服务重启后会自动续跑。`edu_homework_ai_review.status`：0 排队中、1 处理中、2 已生成、3 失败、4 已采纳、5 已拒绝、6 已跳过。

**先看什么**：

```bash
# 各状态数量和最早的更新时间
nus_sql <<'SQL'
SELECT status, COUNT(*) AS 数量, MIN(update_time) AS 最早, MAX(update_time) AS 最新
FROM edu_homework_ai_review WHERE deleted = 0 GROUP BY status;
SQL
# 最近失败的原因
nus_sql <<'SQL'
SELECT id, homework_id, update_time, LEFT(error_message, 200) AS 原因
FROM edu_homework_ai_review WHERE deleted = 0 AND status = 3 ORDER BY id DESC LIMIT 20;
SQL
# AI 开关（两项都应为 true）
sudo grep -E '^NUS_AI_(REVIEW_ENABLED|EXTERNAL_STUDENT_DATA_ENABLED)=' /srv/nus/config/.env
# AI 相关参数：额度、熔断、排队
nus_sql <<'SQL'
SELECT config_key, value FROM infra_config
WHERE deleted = 0 AND (config_key LIKE 'ai.%' OR config_key LIKE 'edu.ai-review.%');
SQL
sudo nusctl logs backend --since 1h --error | tail -n 40
```

再到平台里看：“AI 大模型 > 控制台 > 调用日志”（每次调用是否成功、耗时）；“AI 大模型 > 控制台 > 模型配置”点“测试”。

**检查服务器能否访问模型平台**（把地址换成“API 密钥”页面里该平台的 API 地址）：

```bash
nus_compose exec backend getent hosts <模型平台域名>                                       # 能否解析域名
nus_compose exec backend curl -sS -m 10 -o /dev/null -w '%{http_code}\n' https://<模型平台域名>/   # 有任何 HTTP 状态码就说明网络通
```

**可能原因与处理**：

| 判断 | 可能原因 | 处理 |
| --- | --- | --- |
| 大量 status 0，而且最早时间很久以前 | 后端初评调度没在跑，或开关关闭 | 检查两个 `.env` 开关；看后端日志；必要时低峰期 `sudo nusctl stop` 再 `sudo nusctl start`（启动时会续跑） |
| 解析不了域名或 curl 超时 | 服务器没有出网，或学校防火墙拦截 | 联系学校网络管理员开通到模型平台的出网；平台本身不需要改 |
| 调用日志里是认证失败（401/403） | API 密钥失效、欠费 | 运维手册 8.4 更换密钥，在“模型配置”里测试 |
| 调用日志里是 429、额度不足 | 模型平台限流或欠费；或平台自己的额度 `ai.daily-token-quota` 用完 | 联系密钥所属账号的负责人；调整额度参数要指导老师同意 |
| 提示“AI 服务暂时不可用，请稍后再试” | 同一模型连续失败触发熔断（默认 5 次后暂停 60 秒） | 先解决连续失败的根本原因 |
| 失败原因是附件读取、转写失败 | 附件格式、损坏、太大（AI 初评最多读 5 个附件、每个 20 MB） | 由老师人工批改，或让学生重交 |
| 失败原因是“已被重交取代” | 学生重交了，旧的初评作废 | 正常现象 |
| 某个任务根本没有初评 | 任务的批改方式是“仅人工批改” | 正常现象 |
| 模型配置里业务未绑定模型 | “业务模型绑定”没有为 AI 初评选模型 | 在“模型配置”页面上方绑定并“保存全部” |

单份可以在批改页“重新生成”；批量生成只补缺，不会覆盖已有的初评。

## 5. 定时提醒没发出（定时任务不执行）

**现象**：学生说没收到截止前提醒；老师没收到“新提交待批改”汇总；学期没有按时自动切换；公共课新班级没自动关联。

**背景**：这些都是后端里的定时任务（Quartz，存在数据库里），通知都是**站内信**（铃铛里的消息），不发短信、邮件。

| 定时任务 | 处理器 | 执行时间 |
| --- | --- | --- |
| 任务截止前提醒 | `eduHomeworkRemindJob` | 每小时第 5 分钟 |
| 教师新提交汇总 | `eduHomeworkTeacherDigestJob` | 每 10 分钟 |
| 当前学期自动更新 | `eduSemesterAutoUpdateJob` | 每天 00:05 |
| 公共课班级同步 | `eduPublicCourseSyncJob` | 每天 00:15 |
| 校园资讯定时抓取 | `eduNewsCrawlerJob` | 每天 07:15、17:15（需要出网） |
| 各类日志清理 | `accessLogCleanJob` 等 | 每天 03:20～03:35 |

截止前提醒的规则：实际截止时间（含个别延期）在 24 小时内（`edu.remind.before-hours`）、**还没提交**的学生，**每人每个任务只提醒一次**。已经提交、或者截止前不到一小时才发布的任务，可能收不到。

**先看什么**：

```bash
# 定时任务状态：status 1 开启、2 暂停
nus_sql <<'SQL'
SELECT id, name, handler_name, status, cron_expression FROM infra_job WHERE deleted = 0;
SQL
# 最近的执行记录：status 0 运行中、1 成功、2 失败
nus_sql <<'SQL'
SELECT j.name, l.begin_time, l.duration, l.status, LEFT(l.result, 150) AS 结果
FROM infra_job_log l JOIN infra_job j ON j.id = l.job_id
WHERE l.deleted = 0 ORDER BY l.id DESC LIMIT 30;
SQL
# 提醒相关参数
nus_sql <<'SQL'
SELECT config_key, value FROM infra_config
WHERE deleted = 0 AND (config_key LIKE 'edu.remind.%' OR config_key LIKE 'edu.notify.%');
SQL
# 截止前提醒最近一次真正发出的时间
nus_sql <<'SQL'
SELECT COUNT(*) AS 提醒条数, MAX(create_time) AS 最近一次 FROM system_notify_message
WHERE template_code = 'edu.student.homework.remind' AND deleted = 0;
SQL
sudo nusctl logs backend --since 3h | grep -E 'EduHomeworkRemindJob|任务截止前提醒' | tail -n 10
timedatectl                                   # 时间是否正确、是否同步
```

平台界面里：“基础设施 > 定时任务”看每个任务的状态和调度日志；“系统管理 > 通知中心 > 通知管理 > 通知记录”看发出的站内信。

**可能原因与处理**：

| 判断 | 可能原因 | 处理 |
| --- | --- | --- |
| 任务 `status = 2` | 有人在“定时任务”里暂停了 | 确认原因后在界面里开启 |
| `edu.remind.enabled = false` 或 `edu.notify.teacher-digest-minutes = 0` | 提醒或汇总被关闭 | 与学校确认是否要开，改参数在“基础设施 > 配置管理” |
| 执行记录 `status = 2`，结果里有错误 | 任务执行出错 | 按执行时间查后端日志 `sudo nusctl logs backend --since 2h --error` |
| 执行记录一直在、结果显示成功，但学生说没收到 | 学生已提交、已提醒过一次、或截止时间不在提醒窗口内 | 在“通知记录”里按学生查；属于规则行为时向老师解释 |
| 最近一段时间完全没有执行记录 | 后端停过；或服务器时间不对 | 看后端是否一直 healthy；查第 11 节 |
| 学期没切换 | 学期管理里关闭了自动更新（手动设置会自动关闭它） | “教务组织 > 学期管理”查看当前是“自动”还是“手动” |

## 6. 磁盘满

**现象**：上传失败、保存失败、后端或 MySQL 反复重启；`df -h` 使用率 100%；升级预检报 `not enough free disk space`。

**先看什么**：

```bash
df -h /srv/nus /var/lib/docker /
sudo du -sh /srv/nus/data/* /srv/nus/backups /srv/nus/logs 2>/dev/null
sudo du -sh /srv/nus/logs/* 2>/dev/null
sudo docker system df
du -sh ~/nus-update-* ~/nus-offline-* 2>/dev/null
journalctl --disk-usage
```

**可能原因与处理**（按“能安全释放多少”排序；每一步都看运维手册第 10 章的保留原则）：

| 占用大的地方 | 处理 |
| --- | --- |
| 家目录里旧的升级包 | 保留最近两个版本，其余删除（运维手册 10.3 第 1 步） |
| Docker 构建缓存、悬空镜像 | `sudo docker builder prune -f`、`sudo docker image prune -f` |
| `/srv/nus/backups` | 先确认异地已有副本，删旧的每日备份；**升级记录引用的、当前和上一个版本相关的备份不要删** |
| 旧的 `nus-backend` / `nus-front` 镜像 | 只删比上一个版本更早的（10.3 第 3 步） |
| 系统日志 | `sudo journalctl --vacuum-size=500M` |
| `/srv/nus/data/uploads` | **不能删**。附件确实多时，联系指导老师扩容 |
| `/srv/nus/data/mysql` | **不能删**，也不能手动删里面的 binlog 文件。联系指导老师扩容 |
| `/srv/nus/data/elasticsearch` | 监控数据，按天自动过期。可以在 `.env` 里调小 `NUS_SKYWALKING_RECORD_TTL_DAYS`、`NUS_SKYWALKING_METRICS_TTL_DAYS` 后 `sudo nusctl stop` 再 `sudo nusctl start` |

**绝对不要**：`docker system prune -a`、`docker image prune -a`（会删掉升级要用的 Flyway 镜像和回滚要用的旧镜像），删除 `/srv/nus/data` 下任何东西。

**释放空间之后**：

```bash
sudo nusctl status                 # 有服务不是 healthy 时：
sudo nusctl stop && sudo nusctl start
sudo nusctl doctor                 # ES 状态：磁盘超过 95% 时 ES 会把索引设为只读，空间降下来后会自动解除；仍为 red 时 sudo nusctl monitor-restart
```

**以后怎么避免**：每周检查（运维手册 3.4）；配好定时备份的自动清理（4.4）；使用率超过 80% 就处理。

## 7. MySQL 起不来

**现象**：`nusctl status` 里 mysql 是 `Restarting`、`Exited`、`unhealthy`；后端一直起不来；`nusctl backup` 报 `mysql is not running`。

**先看什么**：

```bash
sudo nusctl status
sudo nusctl logs mysql --since 1h | tail -n 80
sudo docker inspect -f 'status={{.State.Status}} oom={{.State.OOMKilled}} exit={{.State.ExitCode}} restarts={{.RestartCount}}' $(nus_compose ps -aq mysql)
df -h /srv/nus
sudo ls -ln /srv/nus/data/mysql | head          # 文件属主应为容器里的 mysql 用户（数字 ID，一般是 999）
free -h
```

**可能原因与处理**：

| 日志或检查结果 | 可能原因 | 处理 |
| --- | --- | --- |
| `No space left on device` | 磁盘满 | 第 6 节，释放空间后 `sudo nusctl start` |
| `oom=true` | 内存不够被杀（容器上限 2.5 GiB，或整机内存不足） | `free -h` 看整机；关掉占内存的其他程序；仍不够时联系指导老师扩内存 |
| `Permission denied`、`Operating system error number 13` | 数据目录权限被改过 | **不要自己 chown**，记下 `ls -ln` 的结果联系指导老师 |
| `InnoDB: ... corrupt`、`Database page corruption`、反复崩溃 | 数据文件损坏（常见于异常断电） | **立即停手，不要删除任何文件**，联系指导老师。最终可能要用最近的备份恢复（运维手册 4.7），这需要先把损坏的数据目录整体保留下来 |
| 健康检查一直失败但日志正常 | root 口令和容器里的不一致（改口令没做完整） | 见运维手册 8.3 的“失败怎么办” |
| 刚开机，日志显示在做崩溃恢复 | 正常的恢复过程 | 等几分钟再看 |

MySQL 恢复正常后：

```bash
sudo nusctl start
sudo nusctl status
sudo nusctl doctor | grep -A1 'Flyway schema version'
```

## 8. Redis 连接失败

**现象**：后端日志里有 `RedisConnectionFailureException`、`Unable to connect to Redis`、`NOAUTH`、`WRONGPASS`；大家都登录不了、验证码报错；后端起不来。

**先看什么**：

```bash
sudo nusctl status                                         # redis 是否 healthy
sudo nusctl logs redis --since 1h | tail -n 50
nus_compose exec redis sh -c 'REDISCLI_AUTH="$NUS_REDIS_PASSWORD" redis-cli ping'      # 应输出 PONG
nus_compose exec redis sh -c 'REDISCLI_AUTH="$NUS_REDIS_PASSWORD" redis-cli info memory' | grep -E 'used_memory_human|maxmemory_human'
sudo docker inspect -f 'status={{.State.Status}} oom={{.State.OOMKilled}} restarts={{.RestartCount}}' $(nus_compose ps -aq redis)
df -h /srv/nus
sudo nusctl logs backend --since 30m --error | grep -i redis | tail -n 10
```

**可能原因与处理**：

| 判断 | 可能原因 | 处理 |
| --- | --- | --- |
| redis 不是 Up | 容器停了 | `sudo nusctl start` |
| 日志 `NOAUTH` / `WRONGPASS` | `.env` 里的 `NUS_REDIS_PASSWORD` 改过，但 Redis 或后端还在用旧值 | `sudo nusctl stop` 后 `sudo nusctl start`，让两者都按 `.env` 重建 |
| `oom=true` 或内存接近 512 MB 上限 | 缓存太多 | 联系开发方评估；临时可以 `sudo nusctl stop` + `sudo nusctl start` |
| 日志 `Bad file format reading the append only file`、启动即退出 | 持久化文件损坏（常见于磁盘满、断电） | 见下面“最后手段” |
| 磁盘满 | Redis 写不了持久化文件 | 第 6 节 |

**最后手段（持久化文件损坏且无法启动时）**：Redis 里只有登录状态、验证码和缓存，业务数据都在 MySQL 里。经指导老师同意后，把 Redis 数据目录**移走（不是删除）**，让它以空数据启动，代价是所有人需要重新登录：

```bash
sudo nusctl stop
sudo mv /srv/nus/data/redis /srv/nus/data/redis.broken-$(date +%Y%m%d)
sudo mkdir /srv/nus/data/redis
sudo nusctl start
sudo nusctl status
```

确认平台正常运行一段时间后，再决定是否删除 `redis.broken-*`。

## 9. 升级卡住或失败

先读运维手册 5.4：`upgrade.sh` 分预检、准备、切换、启动四个阶段，**停机之后的任何失败都会自动回滚**。

### 9.1 看起来卡住了

**现象**：终端很久没有新输出。

**先看什么**（另开一个 SSH 窗口，**不要在升级终端里按 Ctrl-C**）：

```bash
ls -t /srv/nus/logs/upgrade/ | head -n 3
sudo tail -n 30 -f /srv/nus/logs/upgrade/<最新的>.log       # 当前阶段以 "==>" 开头
sudo nusctl status
ps aux | grep -v grep | grep -E 'upgrade.sh|docker (build|load)'
```

**正常的等待**（以脚本为准）：

| 阶段 | 可能等多久 | 在做什么 |
| --- | --- | --- |
| `prepare` | 几分钟 | 构建或导入镜像；分别等 Elasticsearch、OAP 最多约 3 分钟、UI 约 2 分钟健康 |
| `backup` | 取决于数据库大小 | 备份数据库 |
| `starting` | 后端最多约 3 分钟（90 次 × 2 秒） | 等新后端健康。超时后自动回滚，回滚再启动旧版本也要等，**失败时总共可能 5 分钟左右**（测试服务器的失败演练约 4 分 16 秒） |

**处理**：在上面的时间内耐心等。超过很多仍无变化，保存日志，联系指导老师；**不要强行杀进程**。终端断开时用 `tmux attach` 回去；脚本在停机后被中断也会自动回滚（日志里能看到）。

### 9.2 预检或准备阶段失败（平台没停）

**现象**：屏幕显示 `Nothing was stopped: the platform keeps running`。

平台照常运行，`.env`、数据库、当前版本都没变。看 `Nothing was stopped` 上面的 `ERROR` 行：

| 报错 | 原因 | 处理 |
| --- | --- | --- |
| `release checksum failed` | 包不完整或被修改 | 重新复制、校验 `.tar.gz.sha256` 后解压 |
| `<版本> is already installed` | 这个版本号已经装过 | 需要开发方用**新版本号**重新打包 |
| `new backend image ... is already in use` | 新镜像标签和当前的一样 | 需要开发方用新标签重新打包 |
| `current backend image is missing (needed for rollback)` | 当前版本的镜像被清理了 | 联系指导老师 |
| `mysql is not healthy` / `redis is not healthy` | 数据库或 Redis 有问题 | 第 7、8 节，修好后重新升级 |
| `not enough free disk space` | 空间不够 | 第 6 节，清理后重新升级 |
| `Flyway validation failed against the live database` | 数据库迁移记录有问题 | 第 10 节 |
| `backend update artifact is missing` | 升级包缺文件 | 重新获取升级包 |

修好原因后，在包目录重新执行 `sudo ./upgrade.sh "$PWD"`。

### 9.3 停机后失败，已自动回滚

**现象**：屏幕最后一段是 `UPGRADE FAILED - <原版本> IS RUNNING AGAIN`，退出码非 0。

这时：

- 原版本已经在运行；
- 如果迁移已开始，数据库已恢复到**停机后**做的备份，**没有丢数据**（屏幕上的 `Database:` 一行会说明）；
- 新版本的发布目录已删除，新镜像和升级包保留着供排查。

**先看什么**：

```bash
sudo nusctl status                                         # 原版本是否全部 healthy
readlink /srv/nus/current                                  # 应仍是原版本
ls -t /srv/nus/logs/upgrade/ | head -n 3                   # 升级日志、失败容器日志（*-failed-containers.log）
sudo grep -n -B 30 'FAILED' /srv/nus/logs/upgrade/<时间>-<版本>.log | head -n 80     # 失败原因在 FAILED 那一行之前
sudo tail -n 100 /srv/nus/logs/upgrade/<时间>-<版本>-failed-containers.log           # 新后端为什么起不来
sudo grep -E '^(STATUS|STAGE|DB_BACKUP)=' /srv/nus/upgrades/<时间>-<版本>.env       # STATUS 应为 failed-rolled-back
```

**处理**：

1. 确认原版本正常（`status`、免登录检查见运维手册 5.5），告诉师生平台已恢复；
2. 把升级日志和失败容器日志交给开发方（日志里不含口令，但发出前仍要看一遍有没有个人信息）；
3. **不要反复重试同一个包**。等开发方确认原因、需要时出新包后再升级。原因是外部的（例如磁盘满）且已解决的，可以用同一个包重新执行。

### 9.4 自动回滚也失败了

**现象**：屏幕显示 `AUTOMATIC ROLLBACK DID NOT FINISH (failed step: ...)`，退出码 3。**平台处于停止状态。**

**处理**：

1. 立即联系指导老师；
2. 屏幕上会列出需要以 root 依次执行的命令（每条都可以重复执行），大致是：
   1. 用 `.env.before-*` 恢复 `/srv/nus/config/.env`；
   2. 把 `/srv/nus/current` 指回原版本；
   3. 如果迁移已开始：用升级包里的 `nusctl restore <停机后的备份> --no-safety-backup --yes` 恢复数据库并启动；否则 `nusctl start`；
   4. `nusctl status`；`nusctl logs backend --since 30m --error`。
3. 先按屏幕上 `FAILED` 前的原因排除问题（例如磁盘满），再**按屏幕给出的原文命令**执行，不要自己改写。屏幕内容也在升级日志里：`sudo tail -n 40 /srv/nus/logs/upgrade/<时间>-<版本>.log`。

## 10. Flyway 校验失败

**现象**：升级预检报 `Flyway validation failed against the live database (see above); nothing was changed`，或 `flyway info failed`。平台没停。

**先看什么**：

```bash
# 升级日志里 Flyway 的原始报错
sudo grep -n -i -E 'validate|migration|checksum|failed' /srv/nus/logs/upgrade/<最新>.log | tail -n 30
# 迁移历史（最近 10 条），success 0 表示失败的迁移
nus_sql <<'SQL'
SELECT installed_rank, version, description, success, installed_on
FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 10;
SQL
# 用当前版本的迁移文件做一次只读的 flyway info（会临时启动一个 Flyway 容器，不改数据库）
sudo sh -c 'set -a; . /srv/nus/config/.env; set +a; FLYWAY_NETWORK=nus_nus-internal MIGRATIONS_DIR=/srv/nus/current/database/migrations /srv/nus/current/lib/flyway.sh info'
ls <升级包目录>/database/migrations/ | sort -V | tail -n 3      # 升级包里最高的迁移版本
```

**可能原因与处理**：

| Flyway 报错关键词 | 原因 | 处理 |
| --- | --- | --- |
| `Detected failed migration to version N` / 历史里 `success = 0` | 以前某次迁移失败留下了记录 | 联系开发方。**不要自己执行 `flyway repair`**，要先弄清那次迁移做了一半的改动 |
| `Migration checksum mismatch for migration version N` | 已发布的迁移文件被改过（打包错误） | 这是包的问题，交开发方用原始迁移文件重新打包 |
| `Detected applied migration not resolved locally: N` | 数据库比这个包新，拿了**旧版本的包** | 确认当前版本（`readlink /srv/nus/current`）和包的版本，换正确的包 |
| `Unable to obtain connection` / `Communications link failure` | Flyway 连不上 MySQL | 第 7 节；确认 `.env` 的 `NUS_DB_PASSWORD` 与数据库一致 |
| `Unable to find image` / `pull access denied` | 服务器上的 Flyway 镜像被删了（服务器离线拉不到） | 联系指导老师从全量包里重新导入镜像 |

## 11. 时间不对导致截止判断异常

**现象**：还没到截止时间学生却提交不了，或过了截止还能提交；提醒在奇怪的时间发出；学期提前或推后切换；登录后马上失效；页面显示的时间和手表差很多。

**先看什么**：

```bash
date; timedatectl                                     # 宿主机时间、时区、是否同步（System clock synchronized: yes）
nus_compose exec backend date                         # 后端容器时间，应为北京时间
echo "SELECT NOW() AS 数据库时间, @@global.time_zone, @@system_time_zone;" | nus_sql
timedatectl timesync-status 2>/dev/null | head        # 时间服务器和偏差
# 截止时间设置本身对不对（某个任务）
nus_sql <<'SQL'
SELECT id, homework_name, deadline, status FROM edu_homework WHERE id = <任务ID>;
SQL
```

三处时间应与北京时间相差几秒之内。平台内部固定用北京时间（后端镜像 `TZ=Asia/Shanghai`、数据库连接 `serverTimezone=Asia/Shanghai`），所以**宿主机时区设成别的不会直接影响截止判断，时钟本身不准才会**。

**可能原因与处理**：

| 判断 | 可能原因 | 处理 |
| --- | --- | --- |
| `System clock synchronized: no` 且时间偏差大 | 没有配置可用的时间服务器（学校内网通常访问不了公网 NTP） | 按运维手册 11.3 配置学校内网 NTP；同步后低峰期 `sudo nusctl stop` 再 `sudo nusctl start` |
| 三处时间都正确 | 不是时间问题，可能是任务的截止时间本身设错了，或学生有个别延期 | 查任务的 `deadline`，请老师确认；需要时老师在任务详情里给学生“个别延期” |
| 只有容器时间和宿主机差 8 小时 | 看错了时区（UTC 和北京时间） | 备份文件、升级日志的时间是 UTC，这是正常的 |
| 只有 `date` 显示的时区不对 | 宿主机时区不是北京时间 | `sudo timedatectl set-timezone Asia/Shanghai`（影响 cron 执行时间，不影响平台） |

**时间修正后的善后**：时间错误期间被误判为“已截止”、没能提交的学生，由老师在任务详情里用“个别延期”补救；已经发出的提醒无法撤回。把时间错误的起止时间记下来，告诉指导老师和相关老师。

## 12. 其他

### 12.1 SkyWalking（链路追踪）打不开

不影响平台使用，可以不急。

```bash
sudo nusctl monitor-status                     # elasticsearch、skywalking-oap、skywalking-ui 是否 healthy；ES 集群 status
sysctl vm.max_map_count                        # 应为 262144，否则 ES 起不来
df -h /srv/nus                                 # 磁盘超过 95% 时 ES 索引变只读
sudo nusctl logs elasticsearch --since 1h --error | tail -n 20
sudo nusctl logs skywalking-oap --since 1h --error | tail -n 20
sudo grep -E '^NUS_SKYWALKING_(URL|UI_PORT)=' /srv/nus/config/.env
```

处理：`vm.max_map_count` 不对时 `sudo sysctl -w vm.max_map_count=262144`（`/etc/sysctl.d/99-nus-observability.conf` 会在重启后再设置）；磁盘满按第 6 节；然后 `sudo nusctl monitor-restart`。从菜单进去提示没有权限：账号需要 `infra:monitor:access`。8082 端口从校园网访问不到：学校网络问题，或监控需要独立入口（运维手册 2.4）。

### 12.2 域名切换后的问题

| 现象 | 先看 | 处理 |
| --- | --- | --- |
| 用域名访问时跳转到 `http://`、登录后跳错地址 | `ls /srv/nus/config/domain-nginx/` 是否有 `nginx.conf`；`sudo docker inspect -f '{{.Config.Cmd}}' $(nus_compose ps -q frontend)` 是否含 `/etc/nus-domain/nginx.conf` | 切换脚本直接改了当前版本的 Compose，升级时再由升级脚本生成 `compose.override.yaml` 保留下来。前端没有用域名配置启动时，用同样的 `--site-url` 重新运行 `configure-domain.sh`（可重复执行） |
| 旧附件链接还是旧地址 | 切换时没把那个旧地址列进去 | 重新运行 `configure-domain.sh`，用 `--old-url` 补上旧地址（可重复执行） |
| 新版本说明提到改了 Nginx 配置，但已切换域名的站点没有生效 | 域名配置是切换时的快照，重跑脚本也会沿用已有的 `nginx.conf` | 手动方法（**未演练，先在测试服务器验证**）：`sudo nusctl backup`，`sudo mv /srv/nus/config/domain-nginx/nginx.conf /srv/nus/config/domain-nginx/nginx.conf.old-$(date +%Y%m%d)`，再按运维手册 2.4 用同样的 `--site-url` 重新运行脚本，它会从新前端镜像取配置重新生成 |

### 12.3 `nusctl` 自身报错

| 报错 | 原因 | 处理 |
| --- | --- | --- |
| `must run as root` | 没加 `sudo` | 加 `sudo` |
| `附件或配置备份失败；数据库备份已成功` | 数据库成功，但附件包或 `.env` 校验、读取、写入失败 | 保留打印的数据库路径；检查权限、剩余空间及备份期间是否有上传，修复后重跑 `sudo nusctl backup`，只拿数据库文件不能算完整备份 |
| `installation not found` | `/srv/nus/config/.env` 不存在 | **不要重新安装**。`sudo ls -la /srv/nus/config/` 看文件是否还在；被误删时从加密备份恢复 `.env`（运维手册 4.3），联系指导老师 |
| `nusctl: command not found` | `/usr/local/bin/nusctl` 链接丢了 | 用 `sudo /srv/nus/current/nusctl status`；链接会在下次升级时重建，或 `sudo ln -sfn /srv/nus/current/nusctl /usr/local/bin/nusctl` |
| `invalid --since value` / `invalid trace id` | 参数里有不允许的字符 | `--since` 只用 `30m`、`2h`、`2026-10-14T08:00:00` 这类写法 |
| `...; rerun with --yes to confirm without a terminal` | 在脚本或管道里执行，没法输入 `yes` | 在终端里直接执行；确实要无人值守时才加 `--yes` |

## 需要求助时提供什么

联系指导老师或开发方时，一次给全，能省很多来回：

- 现象、开始时间、影响范围、截图（遮住个人信息）；
- `sudo nusctl status` 和 `sudo nusctl doctor` 的输出；
- 相关日志：`sudo nusctl logs backend --since <时间> --error`、trace-id、升级时的 `/srv/nus/logs/upgrade/` 下的日志；
- 你已经做了哪些操作（照着运维记录写）。

**不要发**：`.env` 内容、`monitor-credentials` 的输出、口令、师生个人信息。
