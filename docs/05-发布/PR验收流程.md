# PR 验收流程（指导老师用）

> 面向：指导老师，以及将来被授权验收 PR 的人。
> 适用版本：V1.0.1.10 起
> 最后核对：2026-10-15

学生和智能体的开发流程见 [开发流程](../03-开发/开发流程.md)。本文写的是收到 PR 之后怎么验收、合并。

## 1. Gitee 上的设置（已完成，有变动时核对）

两个仓库（`shili-platform`、`shili-miniapp`）都要设置。

**保护分支**：在“管理 → 保护分支设置”里，`master`、`dev` 各建一条规则：

| 设置项 | 值 |
| --- | --- |
| 可推送代码成员 | 只选指导老师本人 |
| 可合并 Pull Request 成员 | 只选指导老师本人 |
| 要求门禁状态成功才能合并 | 不勾（没有配置 Gitee Go 流水线） |
| 模式 | 标准模式 |

**成员角色**：学生设为“开发者”，不要给“仓库管理员”。

**验证方法**：用学生账号直接 `git push origin dev`，应该被拒绝；学生打开 PR 页面，应该没有合并按钮。

## 2. 验收步骤

### 2.1 先看 PR 页面（不用拉代码）

- [ ] 目标分支是 `dev`。不是就关闭，让学生重新提交。
- [ ] 提交列表里只有本次任务的提交，没有混进别的分支的东西。
- [ ] 说明按模板填写，影响范围勾选清楚：迁移、权限、统计口径、打包脚本。
- [ ] 文件改动范围和说明相符，没有夹带无关修改，也没有提交 `.env`、口令、真实学生数据。
- [ ] 如果涉及数据库迁移，迁移只新增、不修改已发布的；基线和 check 脚本同步了。

### 2.2 拉到本地

学生的分支在本仓库里，直接拉：

```bash
cd /Users/lope1024/Devlop/shili-handover/shili-platform
git fetch origin
git switch --track origin/feature/学生的分支名
```

**需要确认学生的分支基于最新的 `dev`**：

```bash
git log --oneline origin/dev..HEAD      # 只应列出本次 PR 的提交
git merge-base --is-ancestor origin/dev HEAD && echo "基于最新 dev" || echo "落后于 dev，要求学生 rebase"
```

### 2.3 测试

按改动范围选择，命令说明见 [测试指南](../03-开发/测试指南.md)：

| 改动 | 必做 |
| --- | --- |
| 任何改动 | `scripts/check-all.sh`；读一遍代码改动 |
| 界面 | 按 [环境搭建](../03-开发/环境搭建.md) 起本机环境，在浏览器里用相应角色实际操作一遍，对照 PR 截图 |
| 后端接口、业务逻辑 | 后端单测；用接口或界面验证正常和异常两种情况 |
| 数据库迁移 | `scripts/check-all.sh --db`（运行最新的 check 脚本）；从基线起一次全新环境 |
| 权限、角色 | 权限矩阵 `check-permissions.py`；分别用相关角色登录验证 |
| 跨端流程、统计口径 | 加跑相关的 e2e |
| 打包、升级脚本 | `deploy/offline/tests/` 下的回归测试；必要时在测试服务器演练 |

本机已经有另一套测试环境在运行时，按环境搭建的“同一台机器上再起一套环境”换容器名和端口，不要直接 `up`、`down`。

### 2.4 结论

- **通过**：
  1. 在 Gitee 的 PR 页面点“审查通过”“测试通过”；
  2. 点“合并”。合并方式建议选“扁平化合并”（squash），一个 PR 在 `dev` 上只留一个提交，历史清楚；合并时勾选“删除源分支”。
  3. 切回本地 `dev` 并更新：`git switch dev && git pull --ff-only`。
- **不通过**：在 PR 里按文件、行写清问题和期望的改法，让学生在同一分支修改后再提交。不要替学生改代码后直接合并，除非是小到不值得来回的改动（改完在 PR 里说明）。

## 3. 从 `dev` 到 `master`

只在发版时由指导老师操作，完整清单见 [发版流程](发版流程.md)：

```bash
git switch master && git pull --ff-only
git merge --ff-only origin/dev          # dev 冻结、测试通过后
git push origin master
git tag -a v<版本> -m "V<版本>" && git push origin v<版本>
```

`master` 只接受从 `dev` 快进的提交。快进失败，说明有人绕过流程改了 `master`，先查清楚原因。

## 4. 常见情况

| 情况 | 处理 |
| --- | --- |
| 学生把 PR 提到了 `master` | 关闭 PR，让学生重新提到 `dev`。`master` 的合并权限只有指导老师，所以不会被误合并 |
| 学生分支落后 `dev` 很多、冲突多 | 让学生 `git rebase origin/dev` 解决冲突后 `git push --force-with-lease` |
| 两个 PR 改了同一处 | 先合并一个，另一个让学生 rebase 后重新验收 |
| 学生用了 Fork 提 PR | 让学生改为在本仓库推分支；确实需要时，可以在 PR 页面找到拉取命令 |
| 智能体想合并或推送 `dev` | 不允许，见 `AGENTS.md` 第 6 节 |
