# 发版流程

> 面向：负责发版的同学和协助的 AI 智能体；学校服务器升级需指导老师确认。
> 适用版本：V1.0.1.10（下一个版本 V1.0.1.11 起照此执行）
> 最后核对：2026-10-14

从冻结到上线按顺序做，每一步打勾。全部做完的一次真实发版，可以对照 [V1.0.1.10 测试报告](../99-历史/测试报告/RELEASE_V1.0.1.10_PVE107_TEST_REPORT.md)。

**智能体能做什么**：可以跑测试、起草版本说明和测试报告。合并到 `master`、打标签、构建正式升级包、连接任何服务器，都要人确认后由人执行或在人看着的情况下执行（`AGENTS.md` 第 6 节）。

## 1. 版本号

- 格式 `V主.次.修.补`，例如 `V1.0.1.11`。补丁版可以再加一位，例如 `V1.0.1.8.1`：代码与上一版相同或只有很小的修复，用于重新打包。
- **只增不重复**：服务器的升级脚本会拒绝已经装过的版本号；打坏的包也不能用原版本号重发，要换新号。
- 这些地方用同一个版本号：
  - Git 标签：小写 `v`，例如 `v1.0.1.11`；
  - 版本说明：`docs/05-发布/版本说明/V1.0.1.11.md`；
  - 镜像标签：`nus-backend:V1.0.1.11`、`nus-front:V1.0.1.11`；
  - 升级包：`nus-update-V1.0.1.11-ubuntu24.04-amd64.tar.gz`。
- 本版有新迁移时，在 CHANGELOG 的版本标题里写上迁移号，例如“（2026-11-01，迁移 V22）”。

## 2. 冻结

- [ ] 确定本版范围：`CHANGELOG.md` 的“未发布”一节列出的内容就是本版内容。
- [ ] 通知大家 `dev` 冻结，冻结期间只合并本版的修复。
- [ ] 确认没有挂着的、属于本版的 PR。
- [ ] 本版有迁移、权限、统计口径变化的，提前告诉指导老师。

## 3. 发版前测试

在冻结后的 `dev` 最新提交上做。每项都把结果记进测试报告（模板见文末），失败的修好后从头再跑受影响的项。

### 3.1 一键校验

- [ ] `scripts/check-all.sh --all` 全部“通过”，不能有“跳过”。

它包含：
- gitleaks 敏感信息扫描；
- 后端全部单元测试，含权限快照 `EndpointPermissionsSnapshotTest`；
- 前端类型检查、全部单元测试，含 `tests/copy` 文案扫描；
- 最新迁移的检查 `check-v<N>.py`（只在迁移或基线有改动时跑，没有改动时显示“跳过”，属正常）；
- 接口权限矩阵 `check-permissions.py`。

### 3.2 单独要跑的

- [ ] **db-it**（连接真实 MySQL 的后端集成测试，需要 Docker）：
  ```bash
  cd NUS-backend
  TZ=Asia/Shanghai mvn -q test -pl nus-module-edu -am -Pdb-it \
    -Dnus.it.baseline-sql=$PWD/../NUS-doc/3-数据库文件/ry261-test.sql
  ```
- [ ] **迁移检查**（本版有新迁移时）：`python3 deploy/database/tests/check-v<N>.py` 通过。要覆盖：
  - 全新安装；
  - 从上一版升级；
  - 重复执行；
  - 部分执行后恢复；
  - Flyway validate。

  写法见 [数据库迁移](../03-开发/数据库迁移.md)。
- [ ] **权限矩阵**（本版增删接口或改了 `@PreAuthorize` 时）：`endpoint-permissions.tsv` 和 `deploy/database/tests/permissions/expected-role-endpoints.tsv` 都已更新，并在测试报告里列出新增、移除的接口和开放给哪些角色。
- [ ] **打包、升级脚本测试**（`deploy/offline/` 有改动时必跑，没改动时建议也跑 `check-build-update.sh`）：
  ```bash
  bash deploy/offline/tests/check-build-update.sh
  bash deploy/offline/tests/check-upgrade-helpers.sh
  bash deploy/offline/tests/check-upgrade-flow.sh
  ```

### 3.3 4 套 e2e

在本机一次性环境跑，**严禁指向任何服务器**。

推荐用上一版的基线起环境，再经 Flyway 执行本版新迁移，这样和服务器升级的路径一致：

```bash
# 上一版标签里的基线（以 v1.0.1.10 为例）
git show v1.0.1.10:NUS-doc/3-数据库文件/ry261-test.sql > /tmp/baseline-prev.sql
cd NUS-backend && mvn -q -DskipTests package -pl nus-server -am && cd ..
BASELINE_FILE=/tmp/baseline-prev.sql deploy/tests/e2e/local-env.sh up
deploy/tests/e2e/local-env.sh bootstrap
deploy/tests/e2e/local-env.sh backend

export NUS_E2E_BASE_URL=http://127.0.0.1:48280
export NUS_E2E_ADMIN_USERNAME=admin
export NUS_E2E_ADMIN_PASSWORD_FILE=~/.cache/nus-e2e/admin.pw
```

按下面顺序跑，每套先 `--dry-run`：

- [ ] `python3 deploy/tests/e2e/e2e_v1018.py`
- [ ] `python3 deploy/tests/e2e/e2e_v10110.py`
- [ ] `python3 deploy/tests/e2e/e2e_v1017.py`（批改队列场景要 2～3 分钟）
- [ ] `python3 deploy/tests/e2e/e2e_v1015.py`

说明：
- 各套的前置条件见 `deploy/tests/e2e/README.md`。例如 `e2e_v1018` 要求教师汇总配置大于 0、库里没有待审批的公共课；迁移后要清权限缓存。
- 本版加了新的跨端流程时，新增一套 `e2e_v<版本>.py`，并写进 `deploy/tests/e2e/README.md`。
- 跑完 `deploy/tests/e2e/local-env.sh down`。

### 3.4 性能对比（本版改了统计、SQL、索引时必做）

- [ ] 按 `deploy/tests/perf/README.md`：同一份造数、同一台机器，先用上一版后端、再用本版后端各跑一次 `bench.py`，用 `compare.py` 对比。
- [ ] 测试报告里写清：
  - SQL 条数、耗时有没有退化；
  - 返回内容的每一处差异是否都在预期内，并说明原因。

`local-env.sh` 用 `BASELINE_FILE` 指定基线，用 `NUS_E2E_JAR` 指定后端 jar。perf README 里的 `FROM_BASELINE=16` 写法，脚本已不支持；具体怎么在同一个库上切换新旧后端，待确认后补进 perf README。

### 3.5 前端生产构建与浏览器实测

- [ ] 前端生产构建通过：
  ```bash
  cd NUS-front
  pnpm install --frozen-lockfile
  pnpm check:dep
  pnpm check:type
  pnpm build:production
  ```
  产物在 `NUS-front/apps/web-antd/dist`，打包时要用到。
- [ ] 浏览器实测：本版每个用户能看到的改动，都在本机环境里用对应角色走一遍，记进测试报告。

## 4. 写版本说明

- [ ] 新建 `docs/05-发布/版本说明/V<版本>.md`。它会以 `更新说明.md` 的名字放进升级包，**读者是学校的运维人员和老师**：用中文写，不写代码细节。

参照 [V1.0.1.10](版本说明/V1.0.1.10.md) 的结构：

1. 标题：`# 师砺平台 V<版本> 增量更新说明`。
2. **适用范围**：从哪个版本、哪个 Flyway 版本升级上来，升级后是哪个 Flyway 版本。跨版本升级要读哪些旧说明。
3. **本版主要内容**：几条要点。
4. **一、升级前必读**：
   - 统计数字会不会变；
   - 老师要核对什么；
   - 有没有迁移，能不能重复执行，大概多久；
   - 升级后要不要重新登录。
5. **二、三……**：每个功能、修正各一节，写现象、原因、现在怎么做。
6. **其他修正**。
7. **数据库变更（V<N>）**：加了哪些列、索引，改了哪些字典或数据。
8. **升级步骤**：`sudo ./upgrade.sh`、`sudo nusctl status`、回滚命令，并写明**回退会丢失升级后产生的数据**。
9. **已知限制**。

同时：
- [ ] `CHANGELOG.md`：把“未发布”改为 `## V<版本>（日期，迁移 V<N>）`，写一段摘要，末尾链接版本说明；再新建一个空的“未发布”一节。
- [ ] 用户能看到的操作变了，更新 [用户操作手册](../01-产品/用户操作手册/用户操作手册.md)。
- [ ] 运维方式变了，更新 [运维手册](../04-运维/运维手册.md)。

## 5. 合并与打标签

**需要人确认。**

- [ ] 由指导老师把 `dev` 快进合并到 `master`（`master` 只有指导老师能推送，学生和智能体不操作）：
  ```bash
  git switch master && git pull --ff-only
  git merge --ff-only origin/dev
  git push origin master
  ```
- [ ] 合并后在 `master` 上打标签：
  ```bash
  git checkout master && git pull
  git tag -a v<版本> -m "V<版本>"
  git push origin v<版本>
  ```
- [ ] 用打了标签的这个提交做下面的构建，不要用别的分支。

## 6. 打包与校验值

**需要人确认。** `build-update.sh` 只接受干净的工作区：
- `NUS-backend/`、`NUS-front/` 不能有任何未提交或未跟踪的文件；
- 其他目录不能有已跟踪文件的改动。

```bash
# 1. 后端：全新构建
cd NUS-backend && mvnd clean verify && cd ..      # 没装 mvnd 用 mvn，命令相同

# 2. 前端：按 3.5 节生产构建（dist 已是本提交的产物可跳过）

# 3. 打升级包（在仓库根目录）
NUS_RELEASE_VERSION=V<版本>
BACKEND_IMAGE="nus-backend:${NUS_RELEASE_VERSION}" \
FRONTEND_IMAGE="nus-front:${NUS_RELEASE_VERSION}" \
RELEASE_NOTES="$PWD/docs/05-发布/版本说明/${NUS_RELEASE_VERSION}.md" \
CLEAN_BACKEND_BUILD=true \
deploy/offline/build-update.sh "$NUS_RELEASE_VERSION"
```

说明：
- `CLEAN_BACKEND_BUILD=true` 只在 jar 来自 `clean` 构建时设置。
- 镜像标签必须是新的，不能用 `latest`，不能与服务器正在用的标签相同。
- 产物在 `releases/`（不进 git）：
  - `nus-update-<版本>-ubuntu24.04-amd64/` 目录；
  - 同名 `.tar.gz`；
  - 同名 `.tar.gz.sha256`。
- 包里的 `BUILD-METADATA.json` 记录：
  - 本仓库提交号；
  - 镜像标签；
  - jar、前端首页、最新迁移的 SHA-256。

检查：
- [ ] 脚本最后打印了三个产物路径，没有报错。
- [ ] `BUILD-METADATA.json` 里的 `repository.head` 是标签对应的提交，`clean_backend_build` 为 `true`。
- [ ] 包里有 `更新说明.md`。
- [ ] 把 `.tar.gz` 的 SHA-256（`.sha256` 文件里的值）记进测试报告。
- [ ] 把包和 `.sha256` 放到约定的存放位置（见 [交接清单](../06-交接/交接清单.md) 第 7 节）。

需要新服务器首次安装时，另用 `deploy/offline/build-release.sh` 打完整离线包，见 [运维手册](../04-运维/运维手册.md)。

## 7. 测试服务器演练（PVE 107）

**需要人确认后再连接测试服务器。** 地址每次向指导老师确认。建议在 `tmux` 或 `screen` 里执行，停机后 SSH 断开会触发自动回滚。

```bash
# 复制并校验
scp nus-update-<版本>-ubuntu24.04-amd64.tar.gz{,.sha256} <用户>@<测试服务器>:~/
ssh <用户>@<测试服务器>
sha256sum --check nus-update-<版本>-ubuntu24.04-amd64.tar.gz.sha256
tar -xzf nus-update-<版本>-ubuntu24.04-amd64.tar.gz
cd nus-update-<版本>-ubuntu24.04-amd64
sha256sum --check SHA256SUMS
```

按顺序做，每步记下日志文件名、耗时、结果：

- [ ] **升级**：`sudo ./upgrade.sh "$PWD"`。
  - 然后 `sudo nusctl status`（前后端 healthy）、`sudo nusctl doctor`（Flyway 版本是新的）。
  - 日志在 `/srv/nus/logs/upgrade/`。
- [ ] **回滚**：`sudo nusctl rollback previous --yes`。
  - 确认回到上一版；
  - 确认 Flyway 回到原版本；
  - 确认本版新增的列或表随备份恢复消失。
- [ ] **再升级**：再执行一次 `sudo ./upgrade.sh "$PWD"`，成功。
- [ ] **免登录验收**（在测试服务器上或能访问它的机器上）：
  - `/nginx-health`、首页、`/admin-api/system/auth/social-login-config` 返回 200；
  - 受保护接口匿名访问返回 401，**本版新增的接口要逐个测**；
  - `sudo nusctl doctor` 显示的 Flyway 版本正确；
  - 本版改的字典、参数是否生效（例如用只读 SQL 核对）。
- [ ] 登录实测：用测试账号把本版改动在 107 上看一遍。不在 107 上跑 e2e、性能脚本。
- [ ] 写测试报告：`docs/99-历史/测试报告/RELEASE_V<版本>_PVE107_TEST_REPORT.md`，模板见文末。

演练失败：不要在 107 上手工修。找到原因后修代码，换新版本号重新打包，重新演练。

## 8. 学校服务器升级

**正式环境，由指导老师确认时间并在场或知情。** 尽量选在没人用的时间，提前通知老师。

- [ ] 指导老师已确认：版本、时间、测试报告已看过。
- [ ] 升级前看版本说明的“升级前必读”。跨多个版本升级的，中间每个版本的说明都要看。
- [ ] **先备份**：`sudo nusctl backup`，`ls -lh /srv/nus/backups/` 确认有新备份和 `.sha256`；把备份拷一份到服务器以外的地方。
  - 升级脚本自己也会在停机后备份，这一份是额外的保险。
- [ ] 复制、校验、解压，同第 7 节。
- [ ] `sudo ./upgrade.sh "$PWD"`，在 `tmux` 里执行。
- [ ] `sudo nusctl status`、`sudo nusctl doctor`，免登录验收同第 7 节。
- [ ] 通知老师重新登录，并核对版本说明里要求核对的内容。
- [ ] 观察一天：`sudo nusctl logs backend --since 30m --error`。

**出问题时**：
- 先看日志，找指导老师；
- **不要直接回滚**。回滚会把数据库恢复到升级前，升级后老师、学生新写的数据全部丢失。是否回滚由指导老师决定；
- 升级过程中失败，脚本会自动回滚到原版本，按屏幕提示处理。
