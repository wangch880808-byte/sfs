# ADR-005 迁移只增不改，基线与迁移同步

- 状态：生效
- 相关版本：V1.0.1.0 起（离线部署方案），每个带迁移的版本都适用
- 日期：2026-09-03

## 背景

- 学校服务器离线部署，没有人在现场手工改库，数据库变更只能随升级包自动执行。
- 新服务器首次安装要导入一份完整的库，已有服务器要从任意旧版本逐级升上来。两条路径必须得到同样的结构。

## 决定

- 用 Flyway 执行前向增量迁移 `deploy/database/migrations/V*.sql`。**已发布的迁移永远不改，只新增。**
- 首次安装导入基线 `NUS-doc/3-数据库文件/ry261-test.sql`，基线文件头写明它对应的 Flyway 版本（目前 21），之后只执行比它新的迁移。基线不参与升级。
- 每个迁移必须**可以重复执行**：建列、建索引前先查 `information_schema`，插数据用 `NOT EXISTS`。改出厂数据（菜单名、字典、通知模板）时只改仍是默认值的行。
- 每次加迁移，同步更新基线，并提供 `deploy/database/tests/check-v<N>.py`，验证：全新安装、带数据升级、重复执行、部分执行后恢复、“基线 N”与“基线 N-1 + VN”逐表一致。
- 要删的列先停止写入、保留一个版本，再删除，保证能回退到上一版。

## 理由

- 改动已执行过的迁移会让 Flyway 校验和不一致，服务起不来。
- 可重复执行，升级中途失败后才能安全重跑。
- 基线和迁移逐表比对，保证新装和升级的库一样。

## 后果

- 写迁移比直接 `ALTER` 繁琐，要用 `information_schema` + `PREPARE` 的写法（参考 V16、V20）。
- **唯一的例外**：还没在任何环境发布过的迁移可以追加内容。V1.0.1.10 的字典改名就追加进了尚未发布的 V21。一旦打包发到任何服务器（包括测试服务器），就不能再动。
- 旧的助教 ID 串列（V18 起改用关联表）因此一直保留，V1.0.1.8 起停止写入班课上的那一列，删除留给后续版本。
- 具体写法见 [数据库迁移](../../03-开发/数据库迁移.md)。
