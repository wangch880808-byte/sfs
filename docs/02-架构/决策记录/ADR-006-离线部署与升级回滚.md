# ADR-006 离线 Docker 部署、升级失败自动回滚、版本号不重复

- 状态：生效
- 相关版本：V1.0.1.0 起（离线部署）、V1.0.1.7（升级流程改为预检 + 自动回滚）、V1.0.1.8.1（版本号不重复）
- 日期：2026-09-03（部署方案）、2026-10-09（回滚流程）

## 背景

- 学校服务器在校内网络，不能联网下载依赖，也不在现场编译。
- 维护人员不一定熟悉 Docker、MySQL。早期的升级脚本先备份再停机，失败后要手工按步骤回滚（V1.0.1.4、V1.0.1.5 版本说明里的手工回滚步骤）。
- 有服务器装过早期的 V1.0.1.8 包，之后又有修复。升级脚本会拒绝已安装过的版本号，同号的新包装不上。

## 决定

**部署形态**

- 前端、后端、MySQL、Redis、Elasticsearch、SkyWalking 全部用 Docker Compose 跑在一台 Ubuntu 24.04 amd64 上。
- 发布物是离线包：全量安装包（`build-release.sh`，新服务器首次安装）和升级包（`build-update.sh`）。镜像、Java Agent、FFmpeg、Vosk 模型、字体都打进包里。
- 每个版本不可变，镜像用唯一版本标签；`/srv/nus/current` 指向当前版本。数据放在 `/srv/nus` 下的固定目录。
- 口令只在服务器上权限为 0600 的 `.env` 里，不进镜像、jar、基线和 git。

**升级流程**（V1.0.1.7 起，`upgrade.sh`）

1. 预检（不停平台）：文件校验、版本是否已安装、MySQL 和 Redis 健康、磁盘空间、Flyway 能否在线上库通过校验。不通过就退出，平台照常运行。
2. 准备（不停平台）：构建新镜像。
3. 切换：停前端和后端 → **停机后备份数据库** → 换配置 → 执行迁移 → 清缓存。
4. 启动：健康检查通过后才把 `current` 指向新版本。
5. 停机后任何一步失败，**自动回滚**到原版本和停机时的数据库备份。
6. 升级成功后需要退回时，用 `nusctl rollback previous`。

**版本号**：只增不重复。补丁也用新版本号（如 V1.0.1.8.1）。下一个版本是 V1.0.1.11。

## 理由

- 离线包让学校服务器不依赖外网和构建工具，装出来的环境可重复。
- 停机后再备份，备份里才包含停机前最后写入的数据；失败自动回滚，降低维护人员的操作难度。
- 版本号唯一，服务器上装的是哪份代码一目了然；脚本据此拒绝重复安装。

## 后果

- **回滚会丢失升级后产生的数据**（提交、批改、留言、通知），这些只保存在回滚时另存的安全备份里。迁移不能单独回退。正式环境回滚前要先和学校确认。
- 每次改打包或升级脚本，要跑 `deploy/offline/tests/` 的回归测试，并在测试服务器上演练升级和回滚。
- 新增 Redis 缓存类别时，要同步升级脚本里的清缓存列表（`deploy/offline/lib/common.sh`）。
- 不要手工执行不带参数的 `docker compose up -d`，它不读 `/srv/nus/config/.env`。用 `nusctl start`。
- 操作细节见 [运维手册](../../04-运维/运维手册.md)、[发版流程](../../05-发布/发版流程.md)。
