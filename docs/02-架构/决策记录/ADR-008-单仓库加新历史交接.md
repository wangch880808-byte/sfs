# ADR-008 两个仓库、从新历史开始的交接方式

- 状态：生效
- 相关版本：V1.0.1.10 之后的交接
- 日期：2026-10-14

## 背景

- 交接前代码分在 5 个 git 仓库：父仓库（部署、迁移、测试、文档）用子模块组合后端、前端、文档三个仓库，小程序单独一个。改一个功能常常要在 3–4 个仓库分别提交，再更新子模块指针；V1.0.1.10 一次就改了 4 个仓库。
- 旧仓库的 git 历史里有不能公开的内容（早期提交过的配置和个人信息）。逐条重写历史容易漏，检查成本高。
- 接手的是学生和他们用的 AI 智能体，需要“克隆一次就能干活”、规则只有一份。

## 决定

- **两个仓库**：主仓库 `shili-platform`（后端、前端、需求与基线、部署、文档放在一起，目录名保持 `NUS-backend`、`NUS-front`、`NUS-doc`、`deploy`、`docs`），小程序单独为 `shili-miniapp`。
- **从新历史开始**：主仓库的第一个提交是“V1.0.1.10 交接基线”，打标签 `v1.0.1.10`。
  - 旧仓库的完整历史打包成 git bundle，由指导老师离线保管，不交接、不公开；
  - 旧提交的“日期、提交号、标题”导出为 [提交日志](../../99-历史/提交日志.md)，用来查“为什么这样改”；
  - 每个版本的原因已经整理在版本说明、历史计划和本目录的决策记录里。
- 升级包不进 git，按版本另存，在运维文档里写明位置和校验值。

## 理由

- 后端、前端、迁移经常一起改，放在一个仓库里一次提交就是完整改动；智能体只需读一份 `AGENTS.md`，打包也只检查一个仓库。
- 小程序用微信开发者工具开发、要走微信审核，节奏和负责人可能不同，单独成库更顺手。
- 新历史只需保证当前文件干净，可以用扫描工具（`gitleaks`）确认，结论确定。

## 后果

- 新仓库里看不到旧代码的逐行历史（`git blame` 只能追到交接基线）。查原因的顺序：提交日志按关键词找到版本 → 对应版本说明和计划 → 仍不够时找指导老师查 bundle。
- **服务器不受影响**：升级脚本只看升级包里的版本号和镜像标签，不读 git。但线上 `BUILD-METADATA.json` 记录的是旧提交号，对照表在 [当前状态](../../06-交接/当前状态.md)“线上旧提交号对照”。
- 版本号继续往后编，下一个是 V1.0.1.11（见 [ADR-006](ADR-006-离线部署与升级回滚.md)）。
- 部分脚本、文档里还会出现旧的子模块说法（例如 `deploy/database/tests/permissions/README.md` 提到“子模块”“worktree”），以新仓库目录为准。
