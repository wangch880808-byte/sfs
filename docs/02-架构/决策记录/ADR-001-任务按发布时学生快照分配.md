# ADR-001 任务按发布时的学生快照分配

- 状态：生效
- 相关版本：V1.0.1.5（引入）、V1.0.1.10（补齐用户管理入口）
- 日期：2026-09-26

## 背景

V1.0.1.5 之前，“应交人数”按班级**当前**人数推算（V1.0.1.5 版本说明“统计口径调整”的旧口径）。这样一来，学生进班、出班都会改变已有任务的应交人数和提交率，包括早已截止的任务。

## 决定

- 任务发布时，把班里当时的学生写进 `edu_homework_assignee`，这份名单就是这个任务的“分配快照”。
- 学生能不能看到、能不能提交一个任务，应交人数是多少，都以分配快照为准，不看班里现在有谁。
- 学生**进班**：给该班已发布、**未截止**的任务补分配。
- 学生**出班**：移除未截止任务中、该学生**还没有任何提交记录**的分配；已经有记录的保留。
- 所有让学生进出班的入口（班级管理、学生导入、用户管理改班）都必须调用 `EduClassStudentService.syncAssigneesForMembershipChange`。用户管理在 `system` 模块，通过 `StudentClassesChangedEvent` 通知 `edu`。

## 理由

- 往期任务的统计不再随班级名单变化。
- 插班学生只拿到还能做的任务，不会被已截止的任务拖低成绩或锁住等级（等级闯关的插班规则也依赖这一点，见 V1.0.1.7 `edu.unlock.late-joiner-pass`）。
- 出班时保留已有提交，成绩不会丢。

## 后果

- 每个新入班入口都要记得同步分配。V1.0.1.10 就修了一次漏洞：在“用户管理”里新建学生或改班级时没有补发，学生看不到已布置的任务。
- 统计 SQL 必须 JOIN 分配表，只统计仍在分配表里的学生的提交（V1.0.1.9 性能计划 C1 写明的语义）。
- 分配表随任务数 × 学生数增长。V1.0.1.9 实测（12 万条分配）它不是瓶颈；批量加学生时改为批量写入。
- 公共课补发、认领补发也按新班级学生生成快照。
