# ADR-007 统计查询靠索引、直方图和按范围选择子查询写法

- 状态：生效
- 相关版本：V1.0.1.9（迁移 V20）
- 日期：2026-10-10

## 背景

用户反馈学生多了以后查询变慢。本机造数（6000 名学生、2400 个任务、8.4 万条提交）实测发现：

- 关联表（班级学生、班课、任务分配）本身不是瓶颈；
- 慢在三类问题：按任务、按行重复查询（N+1）；把整门课的提交记录整行读进内存再统计；用户表、用户角色表、参数表缺索引。
- 加索引后，有几个接口仍会选错连接顺序：状态、删除标记这类取值很少的列，优化器估不准过滤后剩多少行。

## 决定

1. **不加统计结果表，也不缓存看板**。统计仍实时计算，看板保持实时（用户决定）。
2. **消除 N+1**：列表、详情接口改为批量查询或 SQL 聚合（`GROUP BY homework_id` 等），只取需要的列。
3. **V20 加索引**，并删除被新索引完全覆盖的旧索引。
4. **V20 给状态类列建直方图**：用户、班级、课程、任务、提交、留言、站内信等表的状态和 `deleted` 列（共 28 个），帮助优化器选对连接顺序。基线 20 起也包含这些语句。
5. **可见范围的子查询按场景选写法**（`StatisticsMapper.xml`）：
   - 管理员全量统计：先用派生表去重求出可见任务 ID，再 `IN`（`visibleHomeworkScope`、`analysisHomeworkScope`），避免对每条提交执行一次相关子查询；
   - 外层已经限定了教师、课程或任务的小范围查询：用**相关 EXISTS** 按班课键校验（`restrictedVisibleHomeworkScope`、`restrictedAnalysisHomeworkScope`），避免先扫全库任务。

## 理由

- 实测改后（6000 人规模）：课程详情 SQL 从约 125 条降到 13 条，响应约 220 ms 降到 70–90 ms；提交记录、批改列表约 100 条降到 7–8 条。
- 2 万名学生规模下，直方图让优化器走对顺序：学生“我的任务”49 ms → 17 ms（扫描 1.8 万行 → 143 行），教师任务列表 39 ms → 14 ms，教师看板 56 ms → 29 ms。
- 小范围用 EXISTS、全量用去重 IN，是实测两种写法后各取所长（提交 `31e0fa4`）。

## 后果

- 新加要过滤的状态类字段时，在迁移里建直方图，参考 V20；基线比对要排除末尾的直方图语句（提交 `5b0e3e2`）。
- 写权限范围条件时，小范围用相关 EXISTS，不要用全库 `IN (SELECT DISTINCT …)`（`NUS-backend/AGENTS.md`）。
- 新 XML SQL 要有走真实数据权限拦截器的测试；改复杂 SQL、索引时跑真实 MySQL 集成测试（`-Pdb-it`）。
- 学期匹配谓词（任一方为空即匹配，否则 TRIM 后相等）要原样保留，不能为了走索引改成等值。
- 管理员全校统计本身要汇总全校数据，仍随数据量线性增长（2 万人时管理员看板约 155 ms）。
- 性能对比工具在 `deploy/tests/perf/`，只能对本机一次性环境跑。
