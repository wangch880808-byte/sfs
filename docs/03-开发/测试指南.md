# 测试指南

> 面向：改了代码、准备提交或发版的开发同学和 AI 智能体。
> 适用版本：V1.0.1.10（数据库迁移 V21）。
> 最后核对日期：2026-10-14。

本页列出仓库里所有测试和校验工具：测什么、什么时候必须跑、命令、需要什么环境、大概多久。命令都在仓库根目录执行，除非特别说明。环境怎么搭见 [环境搭建](环境搭建.md)。

已实测的耗时（负责人本机）：`check-all --all` 约 9 分钟、后端单测约 5 分钟、前端单测约 2.5 分钟、权限矩阵约 75 秒、e2e_v10110 约 95 秒。其余命令是对照脚本、`pom.xml`、`package.json` 核对的；耗时写“待确认”的，以实测为准。

判断成败只看末尾的结果汇总。中间的警告、长报告、`ECONNREFUSED localhost:3000` 等输出是正常的，见 [环境搭建](环境搭建.md) 的“正常的输出噪音”。

> **e2e、性能、截图脚本只能对本机一次性环境跑。** 它们会造大量数据、切换当前学期；脚本只接受 `127.0.0.1` 或 `localhost`，严禁改代码绕过这个限制去连测试服务器或学校服务器。

## 速查：改了什么就跑什么

| 改动 | 必须跑 |
| --- | --- |
| 任何改动，提交前 | `scripts/check-all.sh` |
| 后端 Java | 后端单测（check-all 自动跑） |
| 手写 SQL、复杂查询、索引 | 后端单测 + db-it |
| 新迁移、基线 | `check-v<N>.py`（check-all 自动跑）+ db-it + 4 套 e2e |
| 接口新增、删除，`@PreAuthorize` 变化 | `EndpointPermissionsSnapshotTest` + `check-permissions.py` |
| 前端 | `check:type`、`test:unit`（含文案扫描）、改动文件的 eslint、prettier |
| 跨端流程、权限、统计口径 | 加跑相关的 e2e |
| 查询性能相关 | 性能对比 |
| `deploy/offline/`、`deploy/database/*.sh` | 对应的离线回归脚本 |
| 发版前 | `scripts/check-all.sh --all` + 4 套 e2e，见 [发版流程](../05-发布/发版流程.md) |

## 1. 一键校验 `scripts/check-all.sh`

- **测什么**：按改动范围自动选择检查，依次是：
  1. gitleaks 敏感信息扫描；
  2. 后端单测；
  3. 前端类型检查、单元测试，以及改动文件的 eslint、prettier；
  4. 迁移检查与权限矩阵（需要 Docker）；
  5. 提醒你同步 CHANGELOG 和交接记录（只提醒，不算失败）。
- **什么时候跑**：每次提交前、提 PR 前必跑。发版前用 `--all`。
- **命令**：

  ```bash
  scripts/check-all.sh                       # 按改动自动选（与 BASE 比较，含未提交和未跟踪文件）
  scripts/check-all.sh --all                 # 全部检查
  scripts/check-all.sh --backend --front     # 只跑指定部分，可选 --backend --front --db --docs
  BASE=origin/dev scripts/check-all.sh       # 指定比较基准；默认依次尝试 origin/dev、dev、master、HEAD
  SKIP_DOCKER=1 scripts/check-all.sh         # 跳过需要 Docker 的检查
  ```

- **自动选择规则**：
  - `NUS-backend/` 有改动时跑后端；`NUS-front/` 有改动时跑前端。
  - `deploy/database/`、`NUS-doc/3-数据库文件/`，或者 Controller、`endpoint-permissions` 文件有改动时，跑数据库检查。
  - 只有迁移或基线改动时，才跑最新的 `check-v<N>.py`。缺这个脚本直接算失败。
- **环境**：没装的工具会跳过并写明原因（gitleaks、Maven、pnpm、Docker）。跳过不等于通过，提交前要补上。
- **耗时**：取决于选中的部分。`--all` 约 9 分钟（迁移检查被跳过时）；其中后端单测约 5 分钟、前端单测约 2.5 分钟、权限矩阵约 75 秒；迁移检查见第 6 节。
- **“跳过 迁移检查”是设计如此**：即使用 `--all`，只要迁移（`deploy/database/migrations/`）和基线（`NUS-doc/3-数据库文件/`）都没有改动，汇总里就会显示“跳过 迁移检查 check-v21（迁移和基线没有改动）”。已发布的迁移不再改动，没必要每次重跑。权限矩阵照常跑。
- **要单独验证 V21**：`check-v21.py` 需要基线 20，新仓库里没有（git 历史里也没有），要用参数传入基线 20 文件，见第 6 节：

  ```bash
  python3 deploy/database/tests/check-v21.py --baseline20 /path/to/基线20.sql
  ```

  在 V22 出现之前改了迁移或基线，check-all 会自动跑 `check-v21.py`，也要先准备基线 20 文件（可用环境变量 `NUS_BASELINE20_SQL` 传入），否则这一项会失败。

## 2. 后端单元测试

- **测什么**：全部模块的 JUnit 测试，约 750 个。其中几个和规则直接相关：
  - `EndpointPermissionsSnapshotTest`：接口权限快照；
  - `ErrorCodeConstantsUniqueTest`：edu 错误码不重号；
  - `EduClassDataPermissionSqlTest` 等：H2 上走真实数据权限拦截器链。
- **什么时候跑**：改了后端就跑，check-all 会自动跑。
- **命令**（在 `NUS-backend/` 下）：

  ```bash
  TZ=Asia/Shanghai mvn -q test                                           # 全部
  TZ=Asia/Shanghai mvn -q test -pl nus-module-edu -am                    # 只跑一个模块
  TZ=Asia/Shanghai mvn -q test -pl nus-module-edu -am \
    -Dtest=EduClassDataPermissionSqlTest -Dsurefire.failIfNoSpecifiedTests=false   # 只跑一个类
  ```

  可以把 `mvn` 换成 `mvnd`，参数相同。一定要带 `TZ=Asia/Shanghai`，有些用例依赖时区。
- **环境**：JDK 17、Maven；不需要 Docker。
- **耗时**：全部约 5 分钟（实测）。

### 接口权限快照

新增、删除接口或改了 `@PreAuthorize` 时，快照测试会失败。审查改动合理后，重写快照：

```bash
cd NUS-backend
TZ=Asia/Shanghai mvn -q test -pl nus-server -am -Dtest=EndpointPermissionsSnapshotTest \
  -Dsurefire.failIfNoSpecifiedTests=false -Dnus.permission.snapshot.update=true
```

然后按第 7 节更新权限矩阵。新增匿名或只需登录的接口，要先在测试类里写明理由。

## 3. db-it：连真实 MySQL 的集成测试

- **测什么**：`nus-module-edu` 里打了 `@Tag("db")` 的测试（`dbit/` 目录下的 `*DbTest`）。用 Testcontainers 起 `mysql:8.4.6`，导入基线，再按顺序执行指定的迁移，验证 Mapper SQL、批改、提交、公共课回填、等级解锁等。
- **什么时候跑**：改了复杂 SQL、迁移、索引时必须跑。默认构建会排除这些测试（`pom.xml` 里 `excludedGroups=db`）。
- **命令**（在 `NUS-backend/` 下）：

  ```bash
  TZ=Asia/Shanghai mvn -q test -pl nus-module-edu -am -Pdb-it \
    -Dnus.it.baseline-sql=$PWD/../NUS-doc/3-数据库文件/ry261-test.sql
  ```

  还没同步基线、只想验证新迁移时，加 `-Dnus.it.migration-sql=<逗号分隔的迁移文件路径>`，迁移会在基线之后按顺序执行。
- **环境**：Docker，且本地已有 `mysql:8.4.6` 镜像（不会自动拉）。
- **耗时**：待确认。

## 4. 前端检查

在 `NUS-front/` 下执行。

| 检查 | 命令 | 测什么 | 耗时 |
| --- | --- | --- | --- |
| 类型检查 | `pnpm check:type` | `vue-tsc --noEmit`（经 turbo） | 首次待确认；命中 turbo 缓存时几秒 |
| 单元测试 | `pnpm test:unit` | `vitest run --dom`，全部 `*.test.ts`，含文案扫描、样式基线、antd 写法扫描 | 约 2.5 分钟（实测 140 个文件、1022 个用例）。stderr 里的 `ECONNREFUSED localhost:3000` 来自 vben 自带测试，用例照样通过 |
| 文案扫描 | `pnpm test:unit apps/web-antd/tests/copy` | 不规范用词，例如“归档”“新增”；规则在 `apps/web-antd/tests/copy/copyRules.ts`。已包含在单元测试里，这条命令只单独跑它 | 几秒 |
| eslint | `npx eslint <改过的文件>` | 代码规范 | 几秒到几十秒 |
| prettier | `npx prettier --check <改过的文件>` | 格式 | 几秒 |
| 生产构建 | `pnpm build:production` | 能否打包 | 待确认（几分钟） |

- **什么时候跑**：改了前端就跑前四项。check-all 会自动跑，eslint、prettier 只查改动文件。生产构建在发版或改了构建配置时跑。
- eslint 必须在 `NUS-front/` 根目录执行，在 `apps/web-antd` 下执行会报 tsconfig 解析错误。
- `pnpm lint` 会检查整个工作区，很慢，一般不用。
- `NUS-front/lefthook.yml` 配了提交时自动 lint。合并成单仓库后 git 根目录在上一级，这个钩子是否还会生效待确认。
- 文案扫描的其他测试文件也在 `apps/web-antd/tests/` 下：
  - `style/`：样式基线；
  - `antd/`：例如 `@after-close` 这类无效写法。

## 5. e2e：4 套本机 HTTP 端到端验收

- **测什么**：通过 HTTP 调后端接口，自建院系、班级、教师、学生、课程、任务，断言业务结果。各脚本的场景表见 [deploy/tests/e2e/README.md](../../deploy/tests/e2e/README.md)。

  | 脚本 | 覆盖 | 场景数 |
  | --- | --- | --- |
  | `e2e_v1015.py` | 强制改密、评分轨迹、封存与删除、公共课、留言、统计口径、解锁规则等 | 10 |
  | `e2e_v1017.py` | 批改队列、冲突、撤销、个别延期、催交、复制任务、学期收尾、成绩册导回等 | 16 |
  | `e2e_v1018.py` | 教师绑定班课、课程任务数、能力口径、看板待审批、通知文案、学院范围 | 7 |
  | `e2e_v10110.py` | 公共课认领、只看自己的班级、放弃与清除、统计越权、负责人、封存与删除 | 7 |

- **什么时候跑**：
  - 改了数据库、权限、跨端流程，跑相关的那一套；
  - 发版前 4 套全跑。
- **环境**：方式一的一次性环境，并且已经 `up`、`bootstrap`、`backend`。只需要 Python 3 标准库。
- **命令**：

  ```bash
  export NUS_E2E_BASE_URL=http://127.0.0.1:48280
  export NUS_E2E_ADMIN_USERNAME=admin
  export NUS_E2E_ADMIN_PASSWORD_FILE=$HOME/.cache/nus-e2e/admin.pw

  python3 deploy/tests/e2e/e2e_v1018.py      # 先跑：看板待审批场景要求库里没有待审批公共课
  python3 deploy/tests/e2e/e2e_v10110.py
  python3 deploy/tests/e2e/e2e_v1017.py
  python3 deploy/tests/e2e/e2e_v1015.py
  ```

  - `--dry-run`：只列场景和接口，不发请求，也不需要环境变量；
  - `--only <场景名>`：v1015 只能指定一个；v1017、v1018 可以重复写多个；v10110 不支持，因为场景按顺序共用数据；
  - `--debug`：打印调用栈，口令会遮蔽；
  - `--keep-data`：结束时不封存本次新建的班级和公共课。
- **结果**：每个场景输出 `PASS/FAIL 场景名：说明`，最后汇总。有失败时退出码非零。
- **耗时**：e2e_v10110 约 95 秒（实测）；其他三套和总时长待确认。已知较慢的场景：
  - v1017“批改队列不截断”约 2～3 分钟；
  - v1018“通知文案”最长约 5 分钟。
- **注意**：
  - e2e_v1018 的“看板待审批”需要干净的库。同一个库重复跑会因为前提不满足而失败，重来就 `down` 再 `up`。
  - 在已有的库上手工执行了迁移，要先按 e2e README 清除 Redis 里的权限缓存。新 `up` 的环境不用清。

## 6. 迁移检查 `deploy/database/tests/check-v*.py`

- **测什么**：在断网（`--network none`）、tmpfs 的一次性 MySQL 容器里验证某个迁移。不同脚本覆盖的场景略有差异，大致包括：
  - 旧基线全新导入后升级；
  - 带代表性业务数据升级；
  - 重复执行无副作用；
  - 新基线和“旧基线 + 迁移”的结构、数据逐表一致；
  - 部分执行后 Flyway repair、validate。
  它绝不连接现有数据库。
- **什么时候跑**：新增或修改迁移、基线时，必须跑最新的那个（check-all 会自动跑）。写法见 [数据库迁移](数据库迁移.md)。
- **环境**：Docker，本地已有 `mysql:8.4.6` 和 `flyway/flyway:10.20.1-alpine`。
- **耗时**：待确认（每个脚本几分钟级别）。

### 新仓库没有旧基线

每个脚本都需要“上一个版本的基线”。查找顺序是：

1. 命令行参数；
2. 环境变量 `NUS_BASELINE<N>_SQL`；
3. `NUS-doc` 工作区里的文件；
4. 本仓库 git 历史里标记为该版本的文件。

本仓库从 V1.0.1.10 开始，历史里**只有基线 21**，所以旧的检查脚本必须显式传入旧基线文件（`check-v21.py` 的基线 21 默认取 `NUS-doc` 里的当前基线，一般不用传）。旧基线文件由指导老师离线保管。

| 脚本 | 需要传入的旧基线 |
| --- | --- |
| `check-v21.py` | `--baseline20 /path/to/基线20.sql` |
| `check-v20.py` | `--baseline19 …`、`--baseline20 …` |
| `check-v19.py` | `--baseline18 …`、`--baseline19 …` |
| `check-v18.py` | `--baseline17 …`（`--baseline18` 可选） |
| `check-v17.py` | `--baseline15`、`--baseline16`、`--baseline17` |
| `check-v16.py` | `--baseline15`、`--baseline16` |
| `check-v15.py` | `--baseline14`、`--baseline15` |

```bash
python3 deploy/database/tests/check-v21.py --baseline20 /path/to/基线20.sql
# 或者
NUS_BASELINE20_SQL=/path/to/基线20.sql scripts/check-all.sh --db
```

传入的文件头必须有对应的 `-- Flyway baseline version: N` 标记，否则脚本拒绝执行。等 V22 加入后，`check-v22.py` 需要的基线 21 可以从本仓库历史读到，不用再传文件。

## 7. 接口权限矩阵 `check-permissions.py`

- **测什么**：用基线加上所有比它新的迁移建库，结合后端的接口快照 `endpoint-permissions.tsv`，算出“每个角色能调哪些接口”，再与 `deploy/database/tests/permissions/expected-role-endpoints.tsv` 比较。
- **什么时候跑**：接口、`@PreAuthorize`、菜单、角色授权有变化时必须跑；check-all 的数据库部分会自动跑。
- **命令**：

  ```bash
  python3 deploy/database/tests/check-permissions.py --self-test        # 只测表达式解析器，不需要 Docker
  python3 deploy/database/tests/check-permissions.py                    # 日常核对
  python3 deploy/database/tests/check-permissions.py --update --report /tmp/nus-permissions-report.md
  ```

  - `--update` 会重写预期矩阵。只有在人工审查过报告之后才能用。重点看从 0 变 1 的格子，以及 `PERMIT_ALL`、`AUTHENTICATED` 的变化。
  - 修改角色、权限点、菜单前要先问人，见 [AGENTS.md](../../AGENTS.md) 第 6 节。
- **环境**：Docker，`mysql:8.4.6`（可用 `NUS_TEST_MYSQL_IMAGE` 指定）。
- **耗时**：约 75 秒（实测）。会打印很长的报告，只看最后的结论。
- 详细说明见 `deploy/database/tests/permissions/README.md`。

## 9. 性能对比 `deploy/tests/perf/`

- **测什么**：在同一份造数、同一台机器上，比较改造前后各查询接口的耗时、SQL 条数、扫描行数，并逐项比对返回内容，确保“只变快、结果不变”。
- **什么时候跑**：改了列表、统计、看板等查询，或者索引、直方图时。
- **环境**：方式一的一次性环境。脚本直接 `docker exec` 进 `nus-e2e-mysql` 容器，只接受本机地址。
- **命令**：步骤见 [deploy/tests/perf/README.md](../../deploy/tests/perf/README.md)。

  那份 README 第一步还写着 `FROM_BASELINE=16`，现在 `local-env.sh` 已不支持这个变量，改成：

  ```bash
  deploy/tests/e2e/local-env.sh up                    # 基线 21，升到最新迁移
  # 要从“新迁移之前”开始测，用旧基线且不迁移：
  BASELINE_FILE=/path/to/旧基线.sql deploy/tests/e2e/local-env.sh up none
  ```

  “换成改造后的后端前先执行新的迁移”这一步，`local-env.sh` 没有单独的子命令。可以参照脚本里的 `flyway` 函数手动执行，更简便的做法待确认。
