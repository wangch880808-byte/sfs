# 环境搭建

> 面向：第一次在自己电脑上跑起师砺平台的开发同学和 AI 智能体。
> 适用版本：V1.0.1.10（数据库迁移 V21）。
> 最后核对日期：2026-10-14。

目标：从零装好工具，起一套本机数据库和后端，再起前端，用管理员账号登录。全程只连本机，不碰任何服务器。

### 先拉好 Docker 镜像

本机环境脚本、迁移检查、db-it 都带 `--pull=never`（或只用本地镜像），**不会自动拉取**，缺镜像会直接报错。第一次先手动拉：

```bash
docker pull mysql:8.4.6
docker pull redis:7.4.6-alpine
docker pull flyway/flyway:10.20.1-alpine
```

## 3. 方式一：一次性本机环境（推荐）

脚本：`deploy/tests/e2e/local-env.sh`。它在 Docker 里起 MySQL 和 Redis（只绑定 127.0.0.1），导入基线，用 Flyway 升到最新迁移，再以 `prod` 配置运行后端 jar。e2e、性能、截图脚本都默认连这套环境。

```bash
deploy/tests/e2e/local-env.sh up          # 建库：导入基线 21，再 Flyway migrate（约 2 分钟）
deploy/tests/e2e/local-env.sh bootstrap   # 一次性引导：把基线里的管理员口令换成随机口令（约 2–2.5 分钟）
deploy/tests/e2e/local-env.sh backend     # 后台启动后端，等到接口可用（约 0.5–1 分钟）
deploy/tests/e2e/local-env.sh status      # 看本套环境的容器和后端
deploy/tests/e2e/local-env.sh down        # 停本套环境的后端、删本套环境的容器（数据随之清空）
```

起之前要先打好后端 jar（第 2 节，约 3 分钟）。上面的耗时是负责人在本机实测的。

| 子命令 | 作用 |
| --- | --- |
| `up [flyway\|none]` | 默认 `flyway`：导入基线后升到最新迁移；`none` 只导入基线。**会先删除同名容器**（默认 `nus-e2e-mysql`、`nus-e2e-redis`）再新建 |
| `bootstrap` | 以引导模式启动后端，日志里出现 `Administrator bootstrap completed` 后自动停掉后端并返回。最长等 `NUS_E2E_BOOTSTRAP_TIMEOUT` 秒（默认 300），超时也会停掉后端并报错，见第 7 节。引导只能成功一次（只替换基线里那个固定口令），重做要先 `down` 再 `up` |
| `backend` | 先停掉本套环境之前启动的后端（记录在 `$STATE/backend.pid`），再正常启动，等接口可用，最长等 `NUS_E2E_BACKEND_TIMEOUT` 秒（默认 300） |
| `status` | 只列本套环境的容器（按容器名）和后端（按 `backend.pid`），别的环境不显示 |
| `down` | 停本套环境的后端，**删除同名容器** |

要点：

- **默认端口**：后端 48280（管理端口 48281）、MySQL 13306、Redis 16379。可以用 `NUS_E2E_APP_PORT`、`NUS_E2E_MGMT_PORT`、`NUS_E2E_DB_PORT`、`NUS_E2E_REDIS_PORT` 改。
- **端口被占用时直接报错**：脚本不按端口杀进程，只会停掉本套环境自己启动的后端（`backend.pid` 里记录的那个）。启动后端前发现后端端口已被别的程序占用，会列出占用进程并退出，请换端口，或自己确认后停掉那个程序。
- **状态目录**：默认 `~/.cache/nus-e2e`（权限 0700，可用 `NUS_E2E_STATE` 改），下文用 `$STATE` 指代。里面有：
  - `db.pw`、`redis.pw`、`monitor.pw`：随机口令；
  - `admin.pw`：管理员口令；
  - `backend.pid`：本套环境启动的后端进程号；
  - `logs/stdout.log`、`logs/nus.log`：后端日志。
  - 后端就在这个目录里启动，本地存储的上传文件也落在这里，不会往仓库里写 `.upload`。
- **容器名**：默认 `nus-e2e-mysql`、`nus-e2e-redis`，可用 `NUS_E2E_MYSQL_NAME`、`NUS_E2E_REDIS_NAME` 改。
- **基线**：默认用 `NUS-doc/3-数据库文件/ry261-test.sql`，版本从文件头 `-- Flyway baseline version: N` 读取（当前为 21）。要从旧基线开始，用 `BASELINE_FILE=/path/to/旧基线.sql deploy/tests/e2e/local-env.sh up`。旧的 `FROM_BASELINE=16` 写法已不支持。
- **数据不持久**：MySQL 数据放在容器的 tmpfs 里，`down`、删容器、重启 Docker 后都会丢。
- **jar 位置**：默认 `NUS-backend/nus-server/target/nus-server.jar`，可用 `NUS_E2E_JAR` 指定。改了后端代码要重新打包再 `backend`。
- **后端配置**：脚本关闭了验证码和接口加密。AI 初评在 `prod` 配置里默认关闭（`NUS_AI_REVIEW_ENABLED=false`），需要时在 `backend` 前设置该环境变量为 `true`。

### 3.1 验证能登录

`backend` 打印 `backend up on 127.0.0.1:48280` 后，可以用下面的命令确认管理员能登录。口令从 `admin.pw` 读取，不在终端回显，也不出现在命令行参数里（不要用 `curl -d` 把口令写进命令）：

```bash
python3 - <<'PY'
import json, os, urllib.request, uuid
state = os.environ.get('NUS_E2E_STATE', os.path.expanduser('~/.cache/nus-e2e'))
port = os.environ.get('NUS_E2E_APP_PORT', '48280')
with open(os.path.join(state, 'admin.pw'), encoding='utf-8') as fh:
    password = fh.read().rstrip('\r\n')
req = urllib.request.Request(
    f'http://127.0.0.1:{port}/admin-api/system/auth/login',
    data=json.dumps({'username': 'admin', 'password': password}).encode(),
    headers={'Content-Type': 'application/json', 'X-Idempotency-Key': str(uuid.uuid4())},
    method='POST')
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))   # 不走代理
body = json.load(opener.open(req, timeout=10))
token = (body.get('data') or {}).get('accessToken')
print('登录成功，已拿到 accessToken' if token else f"登录失败：code={body.get('code')} msg={body.get('msg')}")
PY
```

接口是 `POST /admin-api/system/auth/login`，请求体 `{"username":"admin","password":...}`，成功时返回 `data.accessToken`，后续请求带 `Authorization: Bearer <accessToken>`。不要把令牌打印出来或贴进报告。

### 3.2 同一台机器上再起一套环境

例如另开一个工作区，或者别人正在用默认那套环境做测试。下面这些变量**要一起换掉**，漏掉任何一个，都可能删掉别人的容器、停掉别人的后端，或者让请求打到别人的服务上：

| 变量 | 默认值 | 第二套示例 |
| --- | --- | --- |
| `NUS_E2E_STATE` | `~/.cache/nus-e2e` | `~/.cache/nus-e2e-b` |
| `NUS_E2E_MYSQL_NAME` | `nus-e2e-mysql` | `nus-e2e-b-mysql` |
| `NUS_E2E_REDIS_NAME` | `nus-e2e-redis` | `nus-e2e-b-redis` |
| `NUS_E2E_DB_PORT` | 13306 | 23306 |
| `NUS_E2E_REDIS_PORT` | 16379 | 26379 |
| `NUS_E2E_APP_PORT` | 48280 | 58280 |
| `NUS_E2E_MGMT_PORT` | 48281 | 58281 |
| `NUS_E2E_JAR` | 本工作区的 `NUS-backend/nus-server/target/nus-server.jar` | 状态目录里的一份副本 |

起之前**先看一眼已有的容器**，确认要用的容器名和端口没有被占：

```bash
docker ps --filter name=nus-e2e
```

完整示例（在仓库根目录执行，所有命令在同一个终端里）：

```bash
export NUS_E2E_STATE=$HOME/.cache/nus-e2e-b
export NUS_E2E_MYSQL_NAME=nus-e2e-b-mysql
export NUS_E2E_REDIS_NAME=nus-e2e-b-redis
export NUS_E2E_DB_PORT=23306 NUS_E2E_REDIS_PORT=26379
export NUS_E2E_APP_PORT=58280 NUS_E2E_MGMT_PORT=58281

# jar 复制一份到自己的状态目录；文件名必须保留 nus-server.jar，脚本靠它识别自己的后端进程
mkdir -p "$NUS_E2E_STATE" && chmod 700 "$NUS_E2E_STATE"
cp NUS-backend/nus-server/target/nus-server.jar "$NUS_E2E_STATE/nus-server.jar"
export NUS_E2E_JAR=$NUS_E2E_STATE/nus-server.jar

deploy/tests/e2e/local-env.sh up
deploy/tests/e2e/local-env.sh bootstrap
deploy/tests/e2e/local-env.sh backend          # 后端在 127.0.0.1:58280
deploy/tests/e2e/local-env.sh status

# e2e 指向这一套
export NUS_E2E_BASE_URL=http://127.0.0.1:$NUS_E2E_APP_PORT
export NUS_E2E_ADMIN_USERNAME=admin
export NUS_E2E_ADMIN_PASSWORD_FILE=$NUS_E2E_STATE/admin.pw

# 用完，在设置了同样变量的终端里执行
deploy/tests/e2e/local-env.sh down
```

注意：

- **`up` 和 `down` 会删除同名容器**（`docker rm -f`），不管是谁起的。容器名没换就执行 `up` 或 `down`，会直接删掉别人那套正在用的数据库。
- **多个工作区不要共用同一个 jar**。重新打包会覆盖 `target/nus-server.jar`，正在用这个文件运行的后端可能因此出错。每套环境用自己的副本，如上例；改了代码就重新打包、重新复制，再 `backend`。
- 新开的终端没有这些变量，会回到默认那套。建议把上面的 `export` 存成自己的一个文件，每次先 `source`。
- 前端要连这一套时，`NUS_DEV_API_TARGET` 改成 `http://127.0.0.1:58280/admin-api`。
- 性能脚本 `deploy/tests/perf/seed.py`、`bench.py` 写死了容器名 `nus-e2e-mysql`，只能对默认容器名的那套环境跑。

## 4. 方式二：在 IDE 里以 local 配置启动后端

适合要断点调试后端的时候。配置细节见 [NUS-backend/README.md](../../NUS-backend/README.md)。

1. 数据库和 Redis 最省事的做法是借用方式一的容器：

   ```bash
   deploy/tests/e2e/local-env.sh up
   deploy/tests/e2e/local-env.sh bootstrap   # 引导完成后自动停掉引导用的后端，容器保留
   ```

   这里不用再执行 `local-env.sh backend`，后端改由 IDE 启动。

2. IDE 运行配置：
   - 主类：`nus-server` 模块的 `cn.nus.zknu.server.NusServerApplication`；
   - 工作目录：`NUS-backend`（AI 初评的转写脚本路径是相对它的）；
   - 环境变量（口令从状态目录里的文件取值，不要写进仓库）：

   | 变量 | 值 |
   | --- | --- |
   | `SPRING_PROFILES_ACTIVE` | `local` |
   | `NUS_LOCAL_DB_PORT` | `13306` |
   | `NUS_LOCAL_DB_NAME` | `nus` |
   | `NUS_LOCAL_DB_PASSWORD` | `~/.cache/nus-e2e/db.pw` 的内容 |
   | `NUS_LOCAL_REDIS_PORT` | `16379` |
   | `SPRING_DATA_REDIS_PASSWORD` | `~/.cache/nus-e2e/redis.pw` 的内容 |

3. 启动后端口是 48080，前端不用设代理目标。

这套组合（借用方式一的容器，再在 IDE 里以 local 配置启动）是按配置文件推出来的，待负责人实测。

也可以用自己装的 MySQL、Redis：把基线导入名为 `ry261-test` 的库（`application-local.yaml` 的默认值）。这时管理员口令还是基线里的占位值，需要引导一次：

- 准备一个权限 0600 的口令文件。口令要求 12～16 位，含大小写字母、数字和特殊字符，且不含账号名。
- 启动参数加 `--nus.admin-bootstrap.enabled=true --nus.admin-bootstrap.password-file=<口令文件>`。
- 成功后去掉这两个参数。

## 5. 起前端并登录

```bash
cd NUS-front
pnpm dev:antd                                                          # 后端在 48080（方式二）
NUS_DEV_API_TARGET=http://127.0.0.1:48280/admin-api pnpm dev:antd      # 后端在 48280（方式一）
```

- 浏览器打开 http://localhost:5666（端口来自 `apps/web-antd/.env.development` 的 `VITE_PORT`）。
- 代理规则在 `apps/web-antd/vite.config.mts`：`/admin-api` 转发到 `NUS_DEV_API_TARGET`，默认 `http://localhost:48080/admin-api`。注意目标地址要带 `/admin-api`。
- **管理员账号**：用户名 `admin`，口令在 `~/.cache/nus-e2e/admin.pw`（由 `bootstrap` 随机生成）。基线里没有其他可登录的账号；教师、学生账号自己在“用户管理”里建，或者跑 `deploy/tests/ui/seed_demo.py` 造一套演示数据（账号写入状态目录的 `demo-accounts.json`）。

## 6. AI 初评的本机依赖（可选）

不装 ffmpeg 和 vosk，平台照常运行，只是**音频附件拿不到转写文字**。

核实过的行为（`HomeworkReviewEvidenceService`）：

- **音频**：先用 ffprobe 取时长，再用 ffmpeg 转成 16 kHz 单声道 wav，最后用 vosk 转写。任何一步失败，只记日志并给初评结果加风险标记 `audio_evidence_failed`，初评继续。
- **视频**：本来就不转写，只标记 `video_manual_review_only`，留给教师人工看。
- **图片**：本机默认不做 OCR（`image-ocr-command: []`）。
- **AI 模型**：初评要调大模型，需要在管理后台的 AI 模型里配好模型和密钥。仓库里没有密钥，本机一般不配，e2e 也不调真实 AI。

需要本机转写时：

```bash
cd NUS-backend
brew install ffmpeg                                    # 默认路径 /opt/homebrew/bin/ffmpeg、ffprobe
python3 -m venv .venv-vosk && .venv-vosk/bin/pip install vosk
scripts/install_vosk_model.sh                          # 下载中文小模型到 ~/.local/share/nus-ai/vosk-model-small-cn-0.22
```

- `install_vosk_model.sh` 从 hf-mirror.com 下载 `vosk-model-small-cn-0.22.zip`，会断点续传、失败重试，直到解压成功。可以用 `NUS_AI_MODEL_ROOT` 改下载目录。
- 配置项见 `application-local.yaml` 的 `nus.edu.ai-review`。路径不同时用环境变量改：`NUS_FFMPEG_COMMAND`、`NUS_FFPROBE_COMMAND`、`NUS_VOSK_PYTHON`（默认 `.venv-vosk/bin/python`）、`NUS_VOSK_SCRIPT`（默认 `scripts/vosk_transcribe.py`）、`NUS_VOSK_MODEL_DIR`。
- vosk 的 Python 包版本仓库里没有锁定，待确认。
- 方式一的后端用 `prod` 配置，路径默认值是服务器上的（例如 `/usr/bin/ffmpeg`、`/opt/nus/venv/bin/python`），本机要转写就得用上面的环境变量覆盖。

## 7. 常见问题

| 现象 | 处理 |
| --- | --- |
| `Unable to find image` / `No such image` | 镜像没拉。按第 1 节手动 `docker pull`，脚本不会自动拉 |
| `up` 卡住不动 | MySQL 在等就绪日志。`docker logs nus-e2e-mysql`（换过容器名就用自己的）看原因，常见是 Docker 内存太小 |
| `端口 48280 已被其他程序占用` | `backend`、`bootstrap` 启动前的检查，脚本不会去杀那个进程。看它列出的占用进程：是别人的环境就用 `NUS_E2E_APP_PORT`、`NUS_E2E_MGMT_PORT` 换端口（见 3.2 节），是自己忘了停的就自己确认后停掉。前端同步改 `NUS_DEV_API_TARGET` |
| 其他端口被占用（13306、16379、48080、5666） | `lsof -i :13306` 找占用进程。方式一可以用 `NUS_E2E_*_PORT` 换端口；`up` 时 MySQL、Redis 端口冲突会让 `docker run` 报错 |
| `bootstrap 在 300 秒内没有完成，已停掉后端` | 机器较忙（同时在打包、跑测试），后端启动慢。先看引导是否其实已经成功：`grep 'Administrator bootstrap completed' $STATE/logs/*.log`（`$STATE` 默认 `~/.cache/nus-e2e`），有这一行就说明口令已经换好，直接 `backend`；没有就设 `NUS_E2E_BOOTSTRAP_TIMEOUT=600` 再 `bootstrap` 一次，同时看日志里有没有报错 |
| `bootstrap failed` / `administrator password was already changed` | 这个库已经引导过了。直接 `backend`；要重来就 `down` 再 `up` |
| `backend failed, see logs` | 看 `$STATE/logs/stdout.log`。常见原因：没打 jar、jar 太旧、容器没起、机器忙导致超过 300 秒（可设 `NUS_E2E_BACKEND_TIMEOUT=600`） |
| `后端 jar 不存在` | 先按第 2 节打 jar；换过 `NUS_E2E_JAR` 的检查路径 |
| 登录提示口令错误 | 用户名是 `admin`，口令看 `admin.pw` 文件，末尾换行不算 |
| 前端请求 404 或 502 | `NUS_DEV_API_TARGET` 没带 `/admin-api`，或者端口不对 |
| `pnpm install` 很慢或失败 | 确认 Node、pnpm 版本对；已用 npmmirror 镜像。网络不好时可以多试几次；还不行就删掉 `node_modules` 后执行 `pnpm install` |
| `pnpm install` 提示只能用 pnpm | 不要用 npm、yarn |
| 后端单测里时间相关的用例失败 | 加 `TZ=Asia/Shanghai`，见[测试指南](测试指南.md) |
