# 数据库迁移

> 面向：要改表结构、字典、菜单、权限或参数的开发同学和 AI 智能体。
> 适用版本：V1.0.1.10（已发布到 V21，下一个是 V22）。
> 最后核对日期：2026-10-14。

**新增迁移前先问人**（[AGENTS.md](../../AGENTS.md) 第 6 节）。涉及权限、统计口径的，还要指导老师确认。

## 1. 三样东西要一起改

| 文件 | 作用 |
| --- | --- |
| `deploy/database/migrations/V22__<说明>.sql` | Flyway 增量迁移，升级已有的库 |
| `NUS-doc/3-数据库文件/ry261-test.sql` | 基线，全新安装时导入；必须等于“基线 21 + V22” |
| `deploy/database/tests/check-v22.py` | 在一次性 MySQL 里证明上面两者正确、可重跑 |

少任何一样，`scripts/check-all.sh` 都会失败，或者漏掉检查。

## 2. 已发布的迁移永远不改

V1–V21 已经在测试服务器和学校服务器上执行过。

- Flyway 在 `flyway_schema_history` 里记录了每个迁移文件的 checksum。启动或升级时会校验（validate），文件内容只要变了一个字节，校验就失败，服务起不来。
- 学校服务器上的库已经是按旧内容改过的，改旧文件也不会重新执行。

所以，发现旧迁移有错，也只能在新迁移里修正。注释写错了也不要改旧文件。

## 3. 命名

格式：`V<编号>__v<版本号用下划线>_<英文简述>.sql`，双下划线。例如：

```
V20__v1_0_1_9_query_indexes.sql
V21__v1_0_1_10_public_course_claim.sql
V22__v1_0_1_11_<简述>.sql        ← 下一个
```

- 编号连续，不跳号。一个版本只有一个迁移文件，同一版本的多处改动按小节写在同一个文件里（参考 V18、V19）。
- 文件开头用中文注释写清楚：哪个版本、做什么、为什么；需要先合并哪些后端改动；迁移后要做什么（例如清缓存、重新登录）。

## 4. 幂等写法

迁移必须**可以重复执行**，而且**部分执行后能接着执行**。MySQL 的 DDL 不在事务里，一个迁移执行到一半失败时，前面的 DDL 已经生效了。

### 加列、加索引：先查 information_schema，再 PREPARE

每个对象单独判断，不要用一个条件跳过多条 DDL。下面是 V21 的写法：

```sql
SET @nus_v22_ddl = IF(
    EXISTS (SELECT 1 FROM information_schema.columns
            WHERE table_schema = DATABASE() AND table_name = 'edu_xxx'
              AND column_name = 'new_col'),
    'SELECT 1',
    'ALTER TABLE `edu_xxx` ADD COLUMN `new_col` BIGINT NULL COMMENT ''说明'' AFTER `old_col`'
);
PREPARE nus_v22_stmt FROM @nus_v22_ddl;
EXECUTE nus_v22_stmt;
DEALLOCATE PREPARE nus_v22_stmt;
```

- 索引查 `information_schema.statistics` 的 `index_name`。
- 删索引反过来写：存在时执行 `DROP INDEX`，否则 `SELECT 1`。参考 V20。
- 变量名、语句名带版本号（`@nus_v22_ddl`、`nus_v22_stmt`），check 脚本会按这个名字切分“部分执行”的场景。
- 新列一般允许 NULL 或给默认值，这样已有的行不用逐行填值。
- 删列、删表要慎重。V19 为了能回滚到 V1.0.1.7，保留了已不用的旧列。

### 改数据：带条件，只改该改的行

- `UPDATE` 的 `WHERE` 里写上“还没改过”的条件，第二次执行就不会命中。例如：`AND claim_teacher_id IS NULL`；`AND label = '已归档'`，只改出厂文字，管理员改过的保持不变。
- `INSERT` 一律用 `INSERT … SELECT … WHERE NOT EXISTS (…)`。
- 每张表都要写逻辑删除条件。注意两类表的字段类型不同：
  - `system_*`、`infra_*` 表的 `deleted` 是 bit，写 `deleted = b'0'`；
  - `edu_*` 表写 `deleted = 0`。
- 大表回填先用临时表压缩数据再 JOIN，不要每行跑一次子查询，参考 V21 的 `nus_v21_homework_teachers`。用完 `DROP TEMPORARY TABLE`。

## 5. 不写 updater、不动 update_time 的场景

有些表的 `creator`、`updater`、`update_time` 是业务逻辑的判断依据，迁移改这些行时要原样保留：

- **`edu_class_course`**：公共课同步靠 `creator = 'system' AND updater = 'system'` 判断“自动关联、从未人工改动过”，靠 `updater = 'system-sync'` 判断“同步封存”（见 `EduClassCourseMapper`）。迁移里改了 `updater`，同步就会把人工的关联当成自动的，或者反过来。
- **`ON UPDATE CURRENT_TIMESTAMP` 的列**：MySQL 会自动改 `update_time`。要保留原值，就在 SET 里显式写 `update_time = update_time`（V21 的写法）。

V21 的例子：

```sql
UPDATE edu_class_course cc
JOIN nus_v21_claims b ON b.class_course_id = cc.id
SET cc.claim_teacher_id = b.teacher_id, cc.claim_time = b.claim_time, cc.update_time = cc.update_time
WHERE cc.deleted = 0 AND cc.status = 0 AND cc.claim_teacher_id IS NULL;
```

角色、参数这类配置行可以写 `updater = 'system', update_time = CURRENT_TIMESTAMP`，参考 V19。拿不准时按“保留原值”处理，check 脚本也会逐列比对。

后端代码里同样的规则：认领字段只能用条件 UPDATE 写，不能用 `updateById`，见 [NUS-backend/AGENTS.md](../../NUS-backend/AGENTS.md)。

## 6. 字典、菜单、权限、参数的增量写法

| 对象 | 写法 | 参考 |
| --- | --- | --- |
| 字典类型 | `INSERT INTO system_dict_type … SELECT … WHERE NOT EXISTS (… type = 'xxx' AND deleted = b'0')` | V15 |
| 字典数据 | 按 `dict_type + value` 判断是否存在；改标签时只改仍是出厂文字的行 | V15、V21 |
| 新菜单、按钮 | **不写死 ID**（学校可能自己加过菜单），由自增分配。按 `permission` 判断是否存在；父菜单按 `id + type + path` 定位并校验 | V16 |
| 已有菜单 | 按 `id + permission`（或 `name`）一起匹配，防止学校库里 ID 对应的不是同一个菜单 | V19 |
| 角色授权 `system_role_menu` | `role.id` 和 `role.code` 都要匹配，`NOT EXISTS` 防重复 | V19 |
| 参数 `infra_config` | 按 `config_key` 判断是否存在；`remark` 写清取值范围 | V18 |
| 通知模板 | 按 `code` 定位；内容不一致时才更新 | V19 |

改了菜单、角色、权限、字典之后：

1. **缓存**：离线升级脚本会自动清参数、学期、指标、字典、权限缓存。新增了缓存类别，要同步改 `deploy/offline/lib/common.sh`。在本机已有的库上手工迁移后，按 [e2e README](../../deploy/tests/e2e/README.md) 清 Redis 权限缓存，并重新登录。
2. **权限矩阵**：跑 `check-permissions.py`，按需 `--update`，见 [测试指南](测试指南.md) 第 7 节。
3. **术语**：菜单名、字典标签用 [术语表](../01-产品/术语表.md) 的叫法，例如“封存”，不要写“归档”。

## 7. 直方图

状态、删除标记这类取值很少的列，如果查询要按它过滤，就要建直方图。没有直方图时，优化器按 5% 估算命中率（实际接近 100%），会选错连接顺序。V20 就是因此给 14 张表建了直方图。

```sql
-- 直方图只是统计信息，不改数据，可以重复执行
ANALYZE TABLE edu_xxx UPDATE HISTOGRAM ON status, deleted;
```

- 写在迁移末尾，`ANALYZE` 只用于建直方图。
- 基线末尾也要加同样的语句。导出的表结构里不含直方图，基线末尾有一段“与 V20 一致”的 `ANALYZE TABLE` 语句，新的追加在后面。
- 在 check 脚本里查 `information_schema.column_statistics`，确认直方图存在。参考 `check-v20.py` 的 `assert_final`。

## 8. 同步基线

基线文件 `NUS-doc/3-数据库文件/ry261-test.sql` 必须等于“基线 21 + V22”的结果：

1. 把 V22 的效果写进基线：
   - 表结构改 `CREATE TABLE`，列顺序要和 `AFTER` 一致；
   - 新增的数据行写进对应的 `INSERT`；
   - 新的直方图追加到末尾。
2. 把文件头第 24 行附近的标记改成：

   ```sql
   -- Flyway baseline version: 22
   ```

   整个文件只能有一处这个标记。`local-env.sh`、`check-permissions.py`、各个 check 脚本都从这里读版本号。
3. 基线里不能有真实数据、口令、密钥。管理员账号保留原来的占位口令哈希，引导功能靠它判断“还没设置过口令”。
4. 基线版本变了，下面这些写死 21 的地方要一起改，并跑对应的回归测试：
   - `deploy/offline/build-release.sh`：`BASELINE_VERSION=21`；
   - `deploy/database/baseline-gate.sh`：默认 `BASELINE_VERSION:-21`；
   - `deploy/offline/tests/test-v1018-release.py`：断言基线 21；
   - 说明文字：根目录 `README.md`、`NUS-doc/README.md`。

   `build-release.sh` 会检查“基线版本 = 最新迁移编号”。
5. 编辑基线的工具和流程目前没有固定下来，以前是手工编辑。是否有更好的生成方式待确认。不管怎么生成，都以 check 脚本里“新基线与旧基线 + 迁移逐表一致”的比较为准。

## 9. 写 `check-v22.py`

复制 `deploy/database/tests/check-v21.py` 改。它会加载 `check-v20.py`（进而加载 `check-v18.py`）里的公共函数。check-v22 最好也用同样的方式加载 check-v21，复用它的 `assert_final`，保证 V21 的效果没被破坏。

要改的地方：

| 位置 | 改成 |
| --- | --- |
| 文件头说明 | 基线 21 → V22，列出覆盖的场景 |
| 容器名 `v18.NAME` | `'nus-v22-check-' + …` |
| `baseline(…)` | 旧基线 21，`history=True`，可以从本仓库历史读到；新基线 22 要求工作区已同步 |
| `migration()` | `glob('V22__*.sql')` |
| 代表性数据 `fixture()` 和预期 `EXPECTED` | 按 V22 的规则**独立**写出预期，不要用和迁移一样的 SQL 再算一遍 |
| `UPDATED_TABLES` | V22 会改动行的表；其余表的全表校验和必须不变 |
| `assert_final` | 新列、索引、字典、直方图等的最终状态；末尾调用 V21 的 `assert_final` |
| `partial_columns` | 正则里的语句名改成 `nus_v22_stmt` |
| Flyway 参数 | `-target=22`；`-baselineVersion=21` / `22`；历史记录断言 `['21\t1', '22\t1']` |
| 命令行参数 | `--baseline21`、`--baseline22` |

必须保留的场景，check-v21 都有：

- `fresh21 + V22` 和重跑无改动；
- `fresh22` 与“21 + V22”结构、数据逐表一致，V22 在 fresh22 上无改动；
- 代表性数据升级；
- 部分执行后再执行；
- Flyway 记录失败 → validate 拒绝 → repair → 重跑；
- migrate、validate 不改业务数据。

可选：照 `test-v21-check.py` 写一个不需要 Docker 的 `test-v22-check.py`，测检查脚本本身。

运行：

```bash
python3 deploy/database/tests/check-v22.py
scripts/check-all.sh --db      # 会自动选中最新的 check-v22.py，并跑权限矩阵
```
