# 开发流程：从拉分支到合并

> 面向：所有参与开发的学生和他们使用的 AI 智能体。
> 适用版本：V1.0.1.10 起
> 最后核对：2026-10-15

本文是**强制规范**。不按流程提交的改动不会被合并。

## 1. 规则一览

| 规则 | 说明 |
| --- | --- |
| 只从最新的 `dev` 拉分支 | 不从 `master`、不从别人的功能分支、不从过时的本地 `dev` 拉 |
| 只往自己的功能分支推送 | `dev`、`master` 是保护分支，只有指导老师能推送；学生推送会被 Gitee 拒绝 |
| 只能通过 PR 合并，PR 只提到 `dev` | 目标分支选错（例如选了 `master`）的 PR 直接关闭 |
| 只有指导老师能合并 PR | 指导老师把分支拉到本地测试，没问题才合并到 `dev`。学生、智能体都不能合并 |
| `dev` 到 `master` 只由指导老师操作 | 发版时进行，见 [发版流程](../05-发布/发版流程.md) |
| 不用 Fork | 学生是仓库的“开发者”成员，直接在本仓库推功能分支，方便指导老师拉取测试 |

两个仓库（`shili-platform`、`shili-miniapp`）规则相同。

## 2. 权限是怎么保证的

Gitee 上已经为 `master` 和 `dev` 设置了保护分支：

- **可推送代码成员**：只有指导老师；
- **可合并 Pull Request 成员**：只有指导老师。

学生的仓库角色是“开发者”：可以推送自己的分支、创建 PR，但不能推送 `dev`、`master`，PR 页面上也没有合并按钮。

## 3. 完整步骤

### 3.1 开始一个任务

1. 先在 Gitee 上建一个 Issue 或认领一个已有的 Issue，写清要做什么。
2. 从最新的 `dev` 拉分支：

   ```bash
   git fetch origin
   git switch -c feature/简述 origin/dev
   ```

3. 分支命名：
   - 新功能用 `feature/`，修复用 `fix/`，只改文档用 `docs/`；
   - 后面用小写英文和短横线写简述，例如 `fix/course-analysis-tie-order`。
4. 一个分支只做一件事。顺手发现的其他问题，另开 Issue，不要混在同一个分支里。

### 3.2 开发与提交

- 提交信息格式：`类型: 中文说明`，见 [协作约定](../../CONTRIBUTING.md)。不符合格式的提交会被本地钩子拒绝。
- 遵守 [AGENTS.md](../../AGENTS.md) 第 4 节“不可违反的规则”和 [编码规范](编码规范.md)。
- 开发中可以随时推送自己的分支做备份：

  ```bash
  git push -u origin feature/简述
  ```

### 3.3 提 PR 之前

1. **同步最新的 `dev`**。别人的 PR 可能已经合并，要在最新的 `dev` 上验证你的改动：

   ```bash
   git fetch origin
   git rebase origin/dev
   ```

   - 有冲突就逐个解决，再执行 `git rebase --continue`。
   - rebase 后推送自己的分支要用 `git push --force-with-lease`。**只对自己的功能分支这样做。**
2. **跑校验**：

   ```bash
   scripts/check-all.sh
   ```

   全部通过才能提 PR。涉及数据库、权限、跨端流程的，按 [测试指南](测试指南.md) 加跑 e2e。
3. **同步文档**：
   - 用户能看到的变化，写进 `CHANGELOG.md` 的“未发布”一节；
   - 操作方式变了，更新用户操作手册；
   - 运维方式变了，更新运维手册；
   - 更新 `docs/06-交接/当前状态.md`。

### 3.4 提 PR

在 Gitee 上新建 Pull Request：

- **源分支**：你的 `feature/…` 或 `fix/…`；
- **目标分支**：**`dev`**（再三确认，不要选 `master`）；
- **审查人、测试人**：指导老师；
- **说明**：按 PR 模板填写：改了什么、为什么、怎么验证的、影响范围（迁移、权限、统计口径）。界面改动附截图。关联的 Issue 写上编号。

### 3.5 等待验收

- 指导老师会把你的分支拉到本地测试。流程见 [PR 验收流程](../05-发布/PR验收流程.md)。
- **被打回**：按评论修改，在同一个分支上继续提交并推送，PR 会自动更新。不要关掉 PR 重新开一个。
- **验收期间 `dev` 有了新提交**：指导老师可能要求你重新 rebase。

### 3.6 合并之后

PR 由指导老师合并到 `dev` 后：

```bash
git switch dev 2>/dev/null || git switch -c dev origin/dev
git pull --ff-only origin dev
git branch -d feature/简述                 # 删除本地分支
git push origin --delete feature/简述      # 删除远端分支（合并时已勾选“删除源分支”的可以跳过）
```

下一个任务重新从 3.1 开始。

## 4. 会被打回的情况

- 目标分支不是 `dev`；
- 分支不是从最新的 `dev` 拉的，或者 rebase 后混进了别的分支的提交；
- 一个 PR 里混了多件无关的事；
- `scripts/check-all.sh` 不通过，或者新逻辑没有测试；
- 违反 `AGENTS.md` 第 4 节的规则，例如改了已发布的迁移、手写 SQL 漏了 `deleted = 0`、提交了口令；
- 用户可见的变化没写进 `CHANGELOG.md`，或者文档没同步；
- PR 说明没按模板填写，说不清改了什么、怎么验证的。

## 5. 紧急修复

线上出了紧急问题，也走同样的流程：从 `dev` 拉 `fix/…` 分支，提 PR 到 `dev`，在 PR 说明开头写“紧急”。

指导老师验收合并后，自己决定是否立即从 `dev` 发一个补丁版本。学生不直接改 `master`。

## 6. 给 AI 智能体的补充

- 可以：拉功能分支、提交、推送**自己的功能分支**、起草 PR 说明。
- 不可以：
  - 推送 `dev`、`master`；
  - 合并任何 PR；
  - 对 `dev`、`master` 做 `--force` 推送；
  - 替学生在 Gitee 上点“审查通过”“测试通过”。
- 推送分支、创建 PR 之前，先告诉使用者要推送什么、PR 的目标分支是什么，得到确认再做。
