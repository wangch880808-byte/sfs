## 查询性能（`deploy/tests/perf`）

**数据规模**：6000 名学生、2400 个任务、12 万条任务分配、8.4 万条提交、18 万条站内信，含移出班级、归档、打回重交、空分数等边界数据。

**测法**：

- 同一份数据、同一台机器；
- 每个接口先完整预热两轮，再测 3 次取中位数；
- SQL 条数与扫描行数来自 `performance_schema`。

| 接口 | 改前 | 改后 |
| --- | --- | --- |
| 课程详情（管理员） | 224 ms，125 条 SQL | 69 ms，13 条 |
| 课程详情（教师） | 207 ms，127 条 | 89 ms，14 条 |
| 班课详情 | 114–144 ms，89–95 条 | 45–53 ms，13–15 条 |
| 提交记录分页（含任务） | 164 ms，97 条 | 24 ms，8 条 |
| 批改分页（含任务） | 169 ms，97 条 | 25 ms，8 条 |
| 提交记录分页（不限任务） | 542 ms，105 条，扫描 7.7 万行 | 39 ms，7 条，扫描 9600 行 |
| 课程分析 | 40 ms，21 条 | 20 ms，4 条 |
| 权限信息（每次刷新页面） | 扫描 6472 行 | 扫描 451 行 |
| 精简用户列表（教师） | 41 ms，扫描 6024 行 | 12 ms，扫描 22 行 |

**返回内容比对**：65 个接口中，新增字段 `canGrade`、`canManage` 之外，有 62 个与改前逐项一致。其余 3 处差异都是预期内的：

- 课程分析中同分学生的先后顺序不同。原 SQL 本来就没有规定同分时的顺序；
- 管理员查看提交记录：改前报“实训任务不存在”，改后能查看（F1 修复）。

**2 万名学生规模**：放大后约 7900 个任务、40 万条分配、28 万条提交、59 万条站内信。

- 课程详情、记录分页、班课详情等的 SQL 条数与 6000 人时相同，不随数据增长；
- 加入直方图后：

  | 接口 | 无直方图 | 有直方图 |
  | --- | --- | --- |
  | 学生“我的任务” | 49 ms，扫描 1.8 万行 | 17 ms，扫描 143 行 |
  | 教师任务列表 | 39 ms，扫描 1.75 万行 | 14 ms，扫描 591 行 |
  | 教师看板 | 56 ms，扫描 2.7 万行 | 29 ms，扫描 5204 行 |

- 管理员全校统计（看板、总通过率）和“全部学生”列表，本身就要汇总全校数据，随数据量线性增长：2 万人时管理员看板约 155 ms。
